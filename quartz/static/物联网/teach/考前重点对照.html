第 5 章低功耗无线通信协议

📖 小课 0501–0509 🗂 速查卡：通信协议

★★ 计算① 有效数据率：实际 vs 最大已掌握

小课 0501
  • 最大数据率：802.15.4 = 250kbps，BLE = 2Mbps
  • 802.15.4 发送前主动退避（initialbackoff ∈ (0, CWinit]，CWinit ≈ 10ms），实际数据率一般为最大数据率的 1/3
公式（课件原文）
η = 数据载荷传输时间 ÷ (退避时间 + 包头传输时间 + 数据载荷传输时间)
R_real = η × R
快速估算：802.15.4 实际 ≈ 250kbps × 1/3 ≈ 83.3kbps

★★ 计算② 802.15.4 物理层：DSSS + O-QPSK 时间计算已掌握

小课 0502
  • DSSS：每 4 bit 数据 → 32 位码片（查表扩频）
  • Chip rate = 2M chip/s → data rate = 250kb/s
  • O-QPSK：码片分奇/偶两相位，每相位 chip rate = C/2 = 1M chip/s；每个码片持续 1μs；两相位半码片偏移 0.5μs
例题重算：验证 250kbps
每 4bit 符号 = 32 码片；总速率 2M chip/s → 每符号时间 = 32 ÷ 2M = 16μs
数据率 = 4bit ÷ 16μs = 250 kb/s ✓（与课件一致）

★★ 计算③ LoRaWAN 参数表计算（Chirp 调制）已掌握

小课 0509
  • BW：带宽，中国取 125kHz，美国可取 125kHz 和 500kHz
  • SF：spreading factor，一个 chirp 表示 SF 个 bits，取值 7–12
  • 频率偏移等价于时间偏移；数据由起始频率 offset 调制
公式 + 例题重算（课件原文）
Ts = 2^SF ÷ BW（一个 chirp 的发送时间）
SF=8、BW=125kHz：Ts = 2⁸ ÷ 125000 = 256/125000 s = 2.048ms
课件案例：SF=8、BW=125kHz 发送 [0, 0, 50] → 频率偏移等价时间偏移 0/256Ts、0/256Ts、50/256Ts（2⁸=256）
并发性：同一信道 6 个用户选 6 个不同 SF，相互正交可并发传输

LoRaWAN 设备类型 Class A / B / C（课件 225–237 页 · 老师点名）
总纲（225 页）：按能耗与下行时延的不同需求分三类——A＝默认设备类型；B＝减小下行通信时延；C＝以终端设备的能耗为代价，进一步减小下行时延。167 页：三种 MAC 中 A、B 是低功耗的 MAC（A＝设备初始化，B＝设备初始化＋监听窗口）。
Class A（226–232）＝想发即发、上行后才收：每次上行后开 RX1/RX2（RXDelay 通常默认上行完成后 1s / 2s，因地区频段而异）；RX1 信道与数据率与上行相关、RX2 由网关指定；窗口长度至少能检测 5 个 symbol（无则休眠，有则接收→解调→地址匹配→一致性校验）；RX1 成功接收则 RX2 不打开；网关下行只能等设备发上行后在 RX1/RX2 发。确认上行未收 ACK 重传次数 [1,15]；确认下行由设备立刻回空 ACK 或上行捎带 ACK。
Class B（233–235）＝beacon 同步 + 定时 ping slot：在 A 的 RX1/RX2 基础上给网关更多下行窗口；所有网关同时广播 beacon，设备收最强信号作时间参考，网络服务器按信号强度选发 ping 帧的网关；设备均以 A 入网，搜到 beacon（可用 DeviceTimeReq 加快）后把上行帧 Class B 位置 1 通知网关再切 B，此后所有上行该位都置 1；设备设 ping slot 周期、网关设其信道与数据率（PingSlotChannelReq）；改周期需先切回 A 用 PingSlotInfoReq 通知网关再切回 B；2 小时内没再收到 beacon → 切回 Class A；确认下行未收 ACK 可用 RX1、RX2 和 slot 重传。
Class C（236–237）＝常开接收、几乎随时可下行：设备供电、不必考虑能耗时始终开启接收窗口；在 RX1/RX2 基础上，不发送数据且不在 RX1 时按 RX2 参数持续接收；RX1 开启时若网关仍在发，设备停止当前接收；网关不能频繁发请求确认的下行——Time_out 后或收到上行确认才能再发，期间可发任意不需要确认的下行数据。
一句话：A 等上行才收（最省电、时延最大）→ B 按 beacon 定时多开窗口（时延减小）→ C 常开 RX2（时延最小、耗电）。教材 PPT 的 BEACON_PERIOD 128s / 4096 slot / FPending 属补充，不划考点；课件未给出三类功耗绝对排序与适用场景的标准答案，建议向老师确认。
平均功耗四步通式（与第 1 章 T=C/I 同一骨架，数字全部出自课件第五章）
① 单状态功率 P = U×I：CC2420@3.0V、17.4mA → 52.2mW
② 占空比 D = t活跃 ÷ t总　③ 平均功耗 P̄ = P活跃×D + P休眠×(1−D)：10mW×0.1% + 10μW×99.9% = 19.99μW（课件例）
④ 寿命 T = C ÷ Ī：1500mAh（两节 750mAh）÷ 17.4mA ≈ 86h（课件"最多工作 86h"）

计算题：冷启动时延账（★★ 有题目，校课件第 119–133 页）

冷调用构成（第 123 页，业务执行 40 ms）：10 调度 + 50 环境 + 350 初始化 + 40 业务 = 450 ms；热调用 10 + 40 = 50 ms；额外准备 = 50 + 350 = 400 ms。课件结论：初始化越长、业务越短，冷启动对响应时间的影响越显著。顶层语句（读配置、建 SDK 对象）只在初始化时执行一次，热调用复用已导入模块。
三种优化（第 129 页：100 次串行调用、10 次需新环境）：从头启动平均 50 + 10%×400 = 90 ms（新环境 450 ms）｜快照恢复 SnapStart 50 + 10%×60 = 56 ms（新环境 110 ms）｜预先保温 50 ms，但代价是环境驻留（例 0.5 GiB × 60 s = 30 GiB·s）。必答：同时比较平均时延、慢调用和资源占用，平均值不能替代时延上限；SnapStart 与预置并发是不同策略，不能在同一函数上同时启用（第 128 页）。

★★ 计算云边计算卸载（老师写"是图"，图+计算都备）已掌握

小课 0607
  • 比较原则：同一任务完成时间；输入上传、网络往返、计算都计入；忽略项先明确
  • 临界判据：若 E ≤ L + C，则云端不可能更快
课件例题重算：D=2Mbit，L=30ms，C=10ms，E=100ms（忽略排队重传）
通式（课件第 145–146 页）：T_cloud = 1000D/R + L + C、T_edge = E；D 单位 Mbit、R 单位 Mbit/s、L/C/E 单位 ms，D/R 是秒，乘 1000 换成 ms。
云端更快 ⟺ 1000D/R < E − L − C ⟺ R > R* = 1000D/(E − L − C)；可行解要求 E > L + C（分母为正）。
R=20Mbit/s：1000×2/20 = 100ms → 100+30+10 = 140ms > E=100ms → 边缘更快 ✓
R=50Mbit/s：1000×2/50 = 40ms → 40+30+10 = 80ms < 100ms → 云端更快 ✓
阈值 R* = 2000/60 ≈ 33.33 Mbit/s；R < R* 边缘快、R > R* 云端快、R = R* 两条路径时间相同。课件：链路变化会改变最优执行位置，时延只是选型指标之一。

MQTT 特点四连（教材 PPT）：轻量级（包头短）· 支持广播（发布-订阅一对多）· 支持双向通信（两个话题互为 pub/sub）· 灵活（三种可选 QoS）。

课件收尾句（必背）：MQTT 适合以 Broker 为中心的消息分发；CoAP 适合受限网络中的资源访问。
"数据获取"角度（老师原话划的题）：HTTP 是拉——应用主动发请求去要，一问一答、一对一，必须知道服务端地址，数据不请求就拿不到；MQTT 是推——应用先 SUBSCRIBE 订阅主题，之后设备每次 PUBLISH 都由 Broker 自动送达（课件报文顺序：CONNECT→CONNACK→SUBSCRIBE→SUBACK→PUBLISH→PUBLISH），一份数据同时供看板、告警、存档，发布者不需要知道订阅者地址；消费者新增/变化时设备端零改动（课件设计需求原话："消费者还会不断变化……减少生产者与消费者的地址耦合"）。
三个 QoS 等级：区别 / 开销 / 什么时候用（课件第 22–27 页）
等级交付语义机制与开销课件使用场景
QoS 0至多一次（可能缺失）无协议确认重发，开销较低持续温度等周期采样——允许少量缺测，后续采样及时更新
QoS 1至少一次（可能重复）确认与必要重发（PUBACK）重要告警——降低丢失风险，消费端应能处理重复
QoS 2恰好一次额外交互与协议状态，避免同次交换重复交付，成本最高严格交付需求——平台支持且可接受更多交互与状态
选择依据（课件原句）：缺失容忍度、重复后果、时效与资源开销；QoS 等级提高通常增加交互与状态成本；协议交付不等同于业务动作执行一次。
两段连接（易考坑点）：设备→Broker 与 Broker→看板是两次独立交付；下行 QoS 不高于订阅要求（发布 QoS 1 + 订阅最大 QoS 0 → 下行按 QoS 0 交付）；一次控制的执行结果仍须由设备回报。
配套计算：QoS 1 吞吐上界 = C / RTT（C=在途未确认上限；课件例 C=20、RTT=80ms → 250 条/s；目标 500 条/s 需 C≥40）
直接控制 vs 设备影子（执行模式区别，课件第 38–43 页 + 习题答案第 5 题）
一句话（课件原句）：直接控制处理一次操作；设备影子同步期望状态与最近上报状态。

维度直接控制设备影子
模式请求—响应（类似立即成功/失败的 HTTP 调用）云端保存 desired（期望）/ reported（上报）两份状态
设备离线时操作无效——必须考虑设备是否在线仍可先更新期望状态，设备上线后读取影子→执行→回报
指令顺序无法保证排序，不支持并发语义按指令发出顺序排序，重连后只取最新目标，不必重放中间状态
适用需要立即确认结果的交互幂等的目标状态同步
状态文档（课件风机例）：{"state":{"desired":{"fan":"ON"},"reported":{"fan":"OFF"}},"version":12} —— 应用改 desired → 设备执行后更新 reported → 二者相等即已同步；version 保证晚到的旧版本不能覆盖新目标。
经典例子（习题答案原解）：对一盏灯先后调用"开红光""开蓝光"——用影子，最终一定是蓝光；用直接控制，若第二条指令先到，最终是红光。
适用边界（课件思考题）：影子适合目标状态同步，一次性动作不能只保留最终状态——"灯最终为蓝色"和"投药一次"不能用同一种状态同步（"开一次门"不能无限期保留重放，短期命令应有有效期）。
OTA 与差分包（课件第 44–49 页）
是什么（定义原文）：OTA = 空中（Over The Air）升级技术，在线检测设备是否需要升级并管理升级过程。
版本闭环（怎么判断要不要升、升没升成）：云端记录固件当前版本号 → 设备系统启动时上报版本号（不需要周期循环上报）→ 按"当前版本 vs 最新发布版本"判断是否需要升级 → 升级后主动上报新版本号，云端据此判断升级是否成功。
启动上报版本 → 判断升级 → 下载升级包 → 升级后上报版本

② 设备下载与合成下载差分包，将旧版本数据与补丁组合得到新版本

流计算 vs 批处理 + 滑动窗口（★★ 简答，课件第 88–107 页）
核心区别（课件原句）：历史查询按请求读取数据，流计算随事件到达持续维护计算状态。同一批采样既用于历史分析，也用于持续更新告警、统计和控制结果。
流计算定义（教材 PPT）：严格定义＝对数据流进行一次扫描，并对其特征进行计算；一般定义＝只对每个数据在短时间内做数次简单计算，使用的内存空间通常较少。典型场景：高速路由器数据流特征统计、金融数据实时分析。典型框架：Flink、Spark Streaming、Kafka、Storm、Samza；云厂商 AWS Kinesis、Azure 流分析、阿里云实时计算。
对比答法：批/历史查询＝数据先落库、按请求触发、读一段区间重算、结果有延迟；流计算＝事件一到就算、持续维护窗口状态、单遍处理、低时延但要管理状态规模。课件收尾："选型依据是数据规模、结果时效、状态规模与运行保障，不是是否使用了流式算法"。

滑动窗口（课件第 89 页定义）：窗口长度 k 按点数计，不按秒计；窗口满后每到一个新采样输出一次。例：20、22、24、30、28；k=3 → 22、76/3≈25.33、82/3≈27.33。
算法做法新结果运算全部输入窗口空间
直接重算每窗口重新扫描 k 个值求和k−1 次加法O((n−k+1)k)O(k)
增量维护保留上窗总和 S，删旧加新：S += x新 − x旧2 次加减O(n)O(k)
增量算法依据：相邻窗口共享 k−1 个采样；不变式＝每次更新后 S 恰好等于当前窗口总和。必须配环形缓冲记住"哪个旧值退出"——课件原句："O(1) 更新依靠 O(k) 窗口存储，不能只保留总和"。
课件例题数字：n=10,000、k=1,000 → 加减次数 8,991,999 → 18,999，两者都输出 9,001 个结果；10 万设备 × k=1000 × 8 字节/值 → 窗口状态约 0.8 GB（"时间优化不会消除状态规模"）。
评测方法（第 105 页）：① 固定任务与资源（设备数 D、窗口 k、输入分布、CPU/内存、状态与输出方式）→ ② 校验结果（与直接算法比较每个输出及数量，逐步增加输入速率）→ ③ 测量系统代价（持续吞吐、P95 结果时延、状态大小、恢复耗时）。算法运算次数与端到端性能分别报告。

IFTTT 速记（课件第 51–61 页 · 老师标"了解"）
定义：IFTTT = If This Then That，一种简单的基于条件语句的程序逻辑。例：IF soil_moisture <= threshold THEN start irrigation；IF temp >= threshold1 && humidity <= threshold2 THEN start alert。
三个特点：① 简单条件语句即可表达多种应用逻辑；② 一般在云端执行，解耦设备端代码与应用逻辑；③ 支持多设备联动。
四个问题（第 52 页）：规则冲突 · 实时性 vs 能耗 · 公平性问题 · 应用逻辑与执行操作的耦合性。

规则冲突判定（教材 PPT 学习目标是"掌握"，课件给了方法）——两个条件同时满足才算冲突：
① IF 条件能够同时成立；② THEN 控制同一设备且动作相反。
四个课件例题：>10000lux 关灯 + <500lux 开灯 → 不冲突（条件不可能同时真）；>10000 关 + <20000 开 → 冲突（10000~20000 区间同时触发且动作相反）；>10000 关 + <20000 关 → 不冲突（动作相同）；>10000 关 + 19:00–24:00 开 → 冲突（如 20:00 且 15000lux）。
检测方法：转为可满足性问题——xᵢ 表示第 i 个条件是否成立，判断 x1 && (x2 || x3) 是否可为 1（候选 (1,1,1)/(1,1,0)/(1,0,1)），再检查同一传感器的条件交集、排除不可能的赋值。课件例：R1 temp>30→fan=ON 与 R2 temp>=28→fan=OFF，取 temp=31 可同时触发 → 冲突。工具层：SAT（布尔可满足性）→ SMT（SAT 的推广，含实数/整数/数组等非布尔变量）→ Z3（微软研究院的 SMT Solver）。

实时性 vs 能耗：查询频率高=实时性高但能耗过大；频率低=能耗小但实时性低（关窗不及时可能淋雨）。解法：自适应调整查询间隔——传感数据接近阈值时缩小间隔，反之扩大；增强语法 WITH time < 60 and missratio < 0.01（RT-IFTTT）。
公平性：某应用规则过多或单条执行频率过高会挤掉其余规则 → 课件解法：优先级、配额与公平调度约束执行频率。
耦合性 → 规则引擎：规则引擎只筛选消息、其他服务执行操作；按 Topic 与条件筛选提取字段后转发给：时序数据库（存储）· 函数计算（处理）· 推送服务（通知用户）· 机器学习服务（预测）。
时序数据与时序数据库（★ 了解，课件第 72–87 页 + 教材 PPT）
定义（教材 PPT）：时序数据 = 带有 timestamp 的数据（例：某工厂温度传感器每秒采集的室内温度）；时序数据库 = 高效存取时序数据的数据管理系统。课件补充：连续采样形成随时间增长的历史记录，常见任务 = 区间统计、趋势分析、异常检测；"访问重点从单条业务记录，转向设备序列与时间范围"。
传统关系库管时序数据的四个问题（教材 PPT）：写入吞吐低（频繁插入效率低）· 存储成本大（压缩不佳）· 维护成本高 · 查询性能差。
时序库四个特点（教材 PPT）：① 没有更新操作，一般只支持插入/查询/删除；② 支持高并发写入——借 LSM 树先写内存再顺序写磁盘；③ 低查询延时、高查询并发（分布式查询 + 数据预处理）；④ 存储成本低（分级存储：内存/SSD/HDD + 编码压缩算法）。典型产品：InfluxDB、KairosDB、OpenTSDB、Beringei、TimeScaleDB；云厂商 AWS Timestream、阿里云 TSDB。
LSM vs B+树（习题答案第 6 题）：B+ 树按主键有序且叶子相连，查找删除高效、范围扫描快；LSM 先查内存 MemTable，未命中再逐层查磁盘 SSTable，数据存放位置不确定导致读放大。优化：在内存放一份索引记录每个文件的 Level、min/max key，快速定位 SSTable。

规模例题（课件第 72 页，注意数字）：10,000 台设备 × 每台每秒 1 点 = 10,000 点/秒，每点 16 字节（8B 时间戳 + 8B 浮点）→ 8.64 亿点/天 = 13.824 GB/天；查最近 10 分钟：单设备 600 点，全设备 600 万点。
容量估算题（第 84 页）：数值压缩为平均 2B、时间戳仍 8B → 10 字节/点；整条记录空间减少 (16−10)/16 = 37.5%，每日容量 8.64 亿×10B = 8.64 GB/天。课件提醒："只压缩数值字段时，整条记录的空间减少比例应按全部字段计算"、"字段压缩收益不能直接当作数据库总容量下降比例"。
压缩与数据分布：Gorilla 利用相邻采样位模式相关性记录差异、无损（不降低浮点精度）；5 个浮点 40B→23B（减 17B，占 42.5%）；1000 点合成数据（原 8000B）：固定值 144B / 规则缓变 1,465B / 随机噪声 6,767B → 越规律压缩收益越大。
选型（第 84–85 页）：时序库＝连续测量、趋势与区间统计；关系库＝业务事务、约束与复杂关联；同一平台可组合使用。三种负载：当前温度（设备 A 最新一条）/ 历史趋势（A 最近 24h 均值）/ 业务关联（告警关联维修工单）。依据＝写入率、保留量、查询时延。课件强调："时序优化针对持续追加与时间范围分析，不等于关系库不能查询时序数据"（关系库可用联合索引 (device, ts)）。

硬件安全机制 · 补全（13–20 页）
机制课件要点
看门狗 WDT(14)本质是电子或软件计时器，正常时定期喂狗，故障/程序错误导致无法重置→超时系统重启；HW WDT＝独立时钟驱动、CPU 故障仍工作；SW WDT＝操作系统定期喂狗（Zephyr wdt_feed()）。示例 max=3000＝3 秒超时、WDT_FLAG_RESET_SOC 超时自动重启
PUF(15)晶圆制造中在芯片内创建的独特物理性质模块，提供唯一身份标识＝IC「指纹」；不可复制（同工艺同材料重造也不同）；密钥在系统启动时重新生成、不存闪存→天然安全优势
RoT 信任根(15)建立信任链的来源、SoC 中安全根基，后续组件可信性都依赖其初始可信状态；常见例子＝硬件安全模块 HSM
Secure Boot(16)确保启动阶段执行代码的完整性与可信性；链：Root Key（存 OTP/eFuse/HSM）→1st Bootloader（ROM，最先执行，用 Root Key 验 2nd 签名并解密加载）→2nd Bootloader（验 Boot Image 签名与完整性）→Boot Image（层层验签通过才可执行）
TEE 补充(18–20)厂商：高通/三星/LG、展讯/联发科/威盛/华为海思；OP-TEE（移动）、TF-M（低端 IoT）；各家 OS 实现不同但都提供 GlobalPlatform 规范 API，二级厂商接口统一
TEE 五个核心组件（19 页，GP 标准）：CA（REE 中应用，发起安全请求）｜TA（TEE 中可信应用，执行密钥生成/指纹比对等敏感操作）｜TEE Client API（REE 侧接口库，连接 TA、传参、取结果）｜TEE Internal API（TEE 侧接口库，内存管理、加密服务）｜TEE Manager（TEE 核心，TA 加载、生命周期、CA↔TA 通信路由）。
手机指纹解锁 5 步（20 页）：① CA 经 TEE Client API 发请求 → ② TEE Manager 验证 CA 合法性（签名校验）、确认有权调目标 TA → ③ TEE 加载启动 TA，用内部加密算法与安全存储（预存指纹模板）在隔离环境完成采集比对 → ④ TA 经 TEE Manager 把结果传回 CA，同时销毁原始指纹图像等临时敏感数据 → ⑤ CA 执行后续逻辑；全过程指纹模板始终不暴露在 REE 中。
软件安全机制 · 补全（21–26 页）
数据安全存储（21）：设备侧＝TEE 等新型硬件特性 + 数据加密；云侧＝访问控制、授权管理、安全日志与审计、冗余与容错等传统技术，发展重点是数据加密以及在加密后的数据上进行计算（安全多方计算、隐私计算、加密数据库）。
漏洞（21，★ 手写"溢出"对应处）：漏洞＝功能性或安全性的逻辑缺陷，是系统在硬件、软件、协议的具体实现或安全策略上的缺陷不足；挖掘＝综合各种技术工具（符号执行等静态分析、Fuzzing 等动态分析）找未知潜在漏洞；分析＝对已发现漏洞细节深入分析，为利用、补救铺垫。本页另有标题「软件混淆与加密技术」，课件未展开。
沙盒（22–24）：为运行中程序提供隔离环境；例 Harbor 内存沙盒、WebAssembly 轻量虚拟机。无沙盒时内核与用户模块共享内存堆，用户模块乱写内存会破坏内核状态致崩溃；用沙盒后划分保护域（内核域可读写任何域；其他模块只能驻留一个域且只能写自己的域）。安全域＝存函数返回地址与跨域调用帧，防返回地址被破坏导致回调跳转到别处；栈界限 stack bound＝限制被调用函数可使用栈的内存范围。
蜜罐（25）：诱饵环境＝重定向器 + 协议进程（提供入侵通信接口；重定向器收 TCP 连接请求转发至协议进程子模块，协议进程实现相应协议并把子进程与 TCP 连接转发至监视器）；监控模块＝监视器，采集攻击者威胁数据并维护蜜罐安全。
OTA 安全（26）：OTA＝借无线网络/移动网络实现系统在线升级，能及时修复漏洞，但过程易遭攻击；安全性需求 4 项＝传输安全性、OTA 操作权限、OTA 更新完整性、回滚机制。
无线安全机制 · 完整流程（27–32 页）
蓝牙（27）：4 种安全模式（数字越大越高）；配对 5 步＝① 发配对请求 → ② 直接交换配对信息 → ③ 认证与加密（先交换公钥生成对称密钥，再按②约定的配对方案认证彼此）→ ④ 据对称密钥生成长期密钥 → ⑤ 建立加密通道，之后所有信息由长期密钥加密发送。
ZigBee（28）：刷新计数器（新密钥建立时重置，防重放）｜CRC 完整性检查（防改包）｜认证（网络层+设备层，防模仿）｜128 位 AES（防窃听）｜3 密钥＝主密钥/链接密钥/网络密钥。
RFID（29–30）：Hash-Lock 用 metaID 代真实 ID 防泄露，但无刷新机制、ID 与 key 明文→易重放、假冒、追踪；7 步＝查询→标签回加密 metaID→读写器查库→得真实 ID 与 key→读写器发 key→标签验 key 后回真实 ID→读写器比对认证。随机化 Hash-Lock 加随机数询问-应答防重放假冒，但 ID 仍明文可追踪；5 步＝查询→标签生成 R 并回 h(R||ID) 与 R→读写器查所有 ID→逐个与 R 哈希比对找到正确 ID→读写器发 ID、标签验证后可访问。
LoRaWAN（31）：唯一 128 位 AES AppKey + DevEUI 认证；派生 NwkSKey（终端↔网络服务器完整性）、AppSKey（终端↔应用服务器加解密/隐私），共同建立网络层与应用层双向认证；每帧另设帧计数器（防重传）+ MIC（完整性）+ CMAC（AES 真实性）。
NB-IoT（32）：① 授权频段保传输效率、减少被攻击；② 凭证存 SIM 卡（全球认可）；③ 基于标准 3GPP AKA 与 DTLS 做网络层/传输层认证；④ HKDF 派生密钥，两层密钥由不同机制生成且彼此独立、互不影响。
认证与传输 + 隐私保护 · 补全（33–39 页）
口令认证（33）：注册＝用户名口令 + 系统生成盐值（随机数）经散列函数变固定长度散列值，散列值与盐值分别存库；登录＝按用户名取散列值与盐值 → 口令加盐再散列 → 新旧散列值相等即合法。
设备认证（34）：阿里云三元组＝ProductKey + DeviceName + DeviceSecret，平台颁发、全球唯一，连用时用 DeviceSecret 加签设备信息由平台验证；射频指纹＝功率放大器非线性指纹 + 帧间时间分布指纹，用来鉴别 ID 相同的伪 AP。
TLS 握手 4 阶段（36，老师点名）：① 客户端发 client_hello，服务器回 server_hello（建安全功能、初始化逻辑连接）→ ② 服务器传证书、密钥信息、证书请求，发完再发 server_hello_done → ③ 客户端回证书、密钥信息、证书验证 → ④ 按②③交换信息实现密码组合交换完成握手。作用＝协商加密建立可信连接、相互验证并协商加密 MAC 算法及密钥。
安全版 MQTT（37）：身份分发布者 / 代理（服务器）/ 订阅者，多层设防——应用层＝设备标识符+密码；传输层＝基于 TLS 的单向（仅服务器证书）/ 双向（双方证书）加密认证；网络层＝专线或 VPN 专用物理/虚拟线路。
隐私（38–39）：身份隐私＝假名/匿名技术（用户 A 用 Alice 看医生、Amy 找保险，不出具真实身份，两假名不可关联）；位置隐私＝假位置信息技术（发多个位置仅一个为真，服务提供者为每个位置算反馈，攻击者不知哪个是真）。
攻击分类 · 完整定义（6–11 页）
被动式（不引起觉察，目标＝端口/信道/潜在漏洞）：嗅探＝用嗅探器侦听流经数据包；扫描＝对端口发消息、从响应包探漏洞或攻击渠道并侵入；窃听＝无线信道开放，任何有适当设备者均可窃听且难发现。

硬件 4 类：故障注入（引外部因素使运算出错泄密，常见于攻击加密机制、据状态变化直接得/算出密钥；手段＝激光注入、降压或干扰供电触发异常→打开受保护寄存器，另有改频率、植入错误触发信号、改系统时钟电平）｜接口植入（UART/JTAG/I2C 调试接口保持打开；找 RX/TX 引脚→电平转换接电脑→xshell/secureCRT 设端口波特率→拿启动信息、执行命令、获取 shell 与日志）｜逆向工程（固件＝硬件中只读软件留存的数据或指令集合；读 Flash 固件得用户关键信息，可重打包刷回执行修改后固件）｜侧信道 SCA（声音/温度/功耗/电磁等附带物理量体现计算特征；SPA 采单条功耗曲线推断密钥位，适用 RSA、ECC 等有密钥相关跳转且功耗差别大的算法）。
