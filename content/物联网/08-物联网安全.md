# 第八章 物联网安全

> [!info] 阅读说明
> 依据《第八章-v2(2).pdf》整理，页码指 PDF 文件页序。围绕威胁—机制—边界—案例组织；课件中的协议版本、简化图和实验代码需结合上下文理解。本章提供防护原理与计算，不代表已运行课件中的可信环境实验。

## 1. 全章地图：从芯片到云端保护什么

| 安全目标 | 英文 | 物联网例子 |
|---|---|---|
| 机密性 | Confidentiality | 摄像头画面与密钥不泄露 |
| 完整性 | Integrity | 温度、固件和控制命令不被篡改 |
| 可用性 | Availability | 遭遇异常流量仍能维持关键服务 |
| 身份认证 | Authentication | 确认设备和平台身份 |
| 授权 | Authorization | 设备只能访问自己的主题 |
| 新鲜性 | Freshness | 拒绝旧的开锁命令重放 |
| 隐私 | Privacy | 限制身份、位置和行为关联 |

设备部署分散、容易物理接触，受算力和能耗约束，生命周期长，软件与网络异构，且能驱动物理执行器。因此需要设备、通信、云服务和应用共同防护。

## 2. 威胁分类：攻击者能够观察或改变什么

### 2.1 网络攻击

| 类型 | 机制 | 主要影响 | 防护思路 |
|---|---|---|---|
| 窃听／嗅探 | 观察链路中的数据 | 机密性与隐私 | 加密传输、限制敏感元数据 |
| 身份假冒 | 冒充合法设备或用户 | 认证与授权 | 唯一凭据、挑战应答、证书 |
| Sybil | 一个实体伪装多个身份 | 信任、投票、资源分配 | 身份绑定、接入约束 |
| 中间人 | 介入双方交互 | 机密性、完整性 | 认证密钥交换、证书验证 |
| 重放 | 再次提交合法旧消息 | 新鲜性、重复动作 | nonce、序号、时间窗与去重 |
| 拒绝服务 | 耗尽链路、CPU、内存或电量 | 可用性 | 限流、配额、隔离与降级 |

课件把扫描放在被动攻击列表里，但主动向端口发送探测报文的扫描属于主动探测；判断应看是否主动交互。一般身份假冒与 Sybil 也应区分，后者突出“一实体多身份”。

### 2.2 硬件攻击

故障注入通过电压、时钟等扰动使计算异常；调试接口暴露可能泄露 shell 或日志；逆向固件可发现硬编码秘密；侧信道从功耗、电磁、时间等间接信息推断秘密。

区分：故障注入主动改变执行，侧信道侧重观察附带信息。加密算法正确不意味着实现对侧信道安全；攻击面也包含制造、调试、存储和升级过程。

## 3. 硬件防护：信任根、安全启动与运行隔离

### 3.1 熔丝与看门狗

eFuse／OTP 可保存生命周期配置、启动密钥摘要或读保护状态，具体功能由芯片决定；课件“熔断后程序不可读写”是简化描述，不能认为所有芯片一烧熔丝就锁住全部内容。

看门狗 Watchdog 要求系统在超时前喂狗，失去响应时触发复位或恢复。它改善可用性，不验证消息来源；不应让独立喂狗线程在关键任务卡死后仍持续喂狗。

**超时例题**：最长合法处理 200 ms，调度和通信抖动上界估计 50 ms，可把 250 ms 作为设计下界再留余量；若选 300 ms 且刚喂狗后发生故障，最长约 300 ms 后检测到超时，再加启动恢复时间。实际还需考虑时钟误差与任务故障模式。

### 3.2 PUF 与 RoT

PUF（Physical Unclonable Function，物理不可克隆函数）利用制造微差异形成器件相关响应。响应受噪声和环境影响，需要稳定化、纠错等设计，不能当成不需保护的万能秘密来源。

RoT（Root of Trust，信任根）是可信验证和密钥保护的起点，可由不可变代码、安全存储或专用硬件支持。

### 3.3 Secure Boot：启动信任链

![安全启动](物联网/pictures/08-物联网安全/课件-p016.png)

RoT 验证引导程序 → 引导程序验证 OS → 后续可信组件按链条验证。验证失败按策略拒绝启动或恢复。签名验证来源和完整性，**不自动加密固件**，也不保证已签名代码无漏洞。防回滚还需可信版本状态与策略。

### 3.4 TEE 与 TrustZone

TEE（Trusted Execution Environment）隔离敏感代码和数据；REE（Rich Execution Environment）运行普通应用。TrustZone 提供安全／非安全资源划分，TEE OS、驱动和安全配置利用它建立可信环境。

![TEE交互架构](物联网/pictures/08-物联网安全/课件-p017.png)

CA（Client Application）在 REE 发起调用；TA（Trusted Application）在 TEE 执行；返回必要结果。指纹例：普通应用请求验证 → TA 读取受保护模板并比较 → 返回匹配结果，避免导出原始模板。

GlobalPlatform 的 TEE Client API 面向 CA，TEE Internal API 面向 TA。TEE 仍有可信计算基（TCB），安全世界代码、外设归属和共享内存边界若配置不当，仍可能出问题。普通 PC 也不会因运行一个用户程序就自动拥有课件所需 TEE。

## 4. 软件安全：隔离、存储与更新

### 4.1 存储与漏洞管理

设备存储结合加密、访问控制和受保护密钥；云端结合授权、日志、冗余和容错。密钥与密文放在同一可读文件中，不能有效抵御整盘复制。减少不必要服务、修复依赖漏洞、校验输入长度，都是基础防护。

### 4.2 沙盒、WebAssembly 与蜜罐

沙盒限制程序可访问的内存、接口和系统资源。课件以 Harbor 和 WebAssembly 说明轻量隔离，核心是控制读写边界、调用边界与越权行为。运行 Wasm 不自动保证宿主接口安全，授权过宽的宿主调用仍会暴露资源。

蜜罐 Honeypot 用诱饵资源记录和分析攻击，帮助发现攻击方式与修复漏洞。它是观测手段，应与生产网络隔离，不能替代业务系统本身的认证和补丁。

### 4.3 OTA 的安全要求

认证更新源 → 下载 → 验证签名、型号与版本 → 可靠切换 → 启动确认 → 失败恢复。加密包保护内容，签名保护来源和完整性，两者目标不同。A/B 分区可以支持切换与回退，但恶意旧固件需由防回滚策略限制。

## 5. 无线协议的安全机制与边界

| 技术 | 课件重点 | 需要记住的边界 |
|---|---|---|
| Bluetooth | 配对、鉴权与链路加密 | 经典蓝牙与 BLE 的模式体系不同，不能统一按数字大小比较；配对方式影响中间人防护 |
| ZigBee | 网络／链路密钥、AES、帧计数 | 密钥分发和入网是关键；计数器必须正确维护 |
| RFID | Hash-Lock、随机化 Hash-Lock | 静态标识可能被跟踪，完整安全性取决于协议交互 |
| LoRaWAN | 根密钥、入网与会话密钥、帧计数 | 1.0 与 1.1 密钥体系不同，区分网络与应用职责 |
| NB-IoT | 蜂窝认证、接入安全与专网能力 | 授权频段不保证无攻击，链路安全不替代端到端应用保护 |

### 5.1 Hash-Lock 为什么还需要随机化

静态 Hash-Lock 用 `metaID=H(key)` 代替真实身份，由后端查找关联。若每次暴露相同 metaID，仍可关联跟踪；协议若在后续交互明文发送秘密或 ID，也不能仅靠一次哈希保证安全。

随机化版本引入随机数，使应答随交互变化，后端据候选秘密匹配。应观察完整协议：谁生成随机数、谁验证、返回哪些信息、是否抵御重放与伪造。仅在消息里加随机数字但不进行认证绑定，没有相同效果。

### 5.2 防重放不是“加密后就有了”

加密后的合法旧包也可能再次通过校验。可把设备 ID、命令、序号、有效期等一起纳入 MAC／签名，并保存已经处理的序号或请求 ID。设备重启后如果计数状态丢失，需要防止接受旧命令；双方状态重置必须符合协议设计。

## 6. 认证、密码工具与 TLS

### 6.1 各工具分别解决什么

| 工具 | 保护目标 | 不自动提供 |
|---|---|---|
| 哈希 Hash | 计算内容摘要 | 无可信参照时的来源认证 |
| HMAC | 共享密钥下的完整性和来源校验 | 机密性、独立防重放 |
| 对称加密 | 保护载荷机密性 | 所有模式下的完整性 |
| 数字签名 | 私钥持有者对内容的认证 | 内容保密、代码无漏洞 |
| TLS | 经认证的受保护通信通道 | 应用权限和执行幂等性 |

口令应配合盐值和专用的慢速口令派生／哈希方案保存，不能只保存可快速穷举的普通摘要。课件三元组 `ProductKey、DeviceName、DeviceSecret` 中，DeviceSecret 是秘密，不应出现在前端或公开日志。

### 6.2 挑战应答与证书

平台发随机挑战 nonce → 设备对挑战及上下文计算认证结果 → 平台验证并将挑战标为已用。攻击者即使录到旧响应，也无法应答新的挑战。

证书将公钥与身份关联；验证链、有效期、目标身份等条件后，还需证明对端持有私钥。平台随后依据主题、设备、操作执行授权，不能止于“证书有效”。

### 6.3 TLS 与 MQTT 的关系

![TLS握手示意](物联网/pictures/08-物联网安全/课件-p036.png)

TLS 大体完成参数协商、服务器身份验证、密钥建立与握手完整性确认，随后保护应用数据。客户端证书按配置参与双向认证。课件握手图需要按具体 TLS 版本解读，不能把旧版流程用于所有版本。

MQTT 客户端标识不是秘密；用户名和密码也不会因为放在 CONNECT 中就自动保密。使用 TLS 并验证服务器身份，再配置设备级认证与 Topic ACL。端口号只是部署约定，不是安全证明。

### 6.4 基础安全计算

理想均匀 $b$ 位秘密，穷举平均需 $2^{b-1}$ 次。真实安全还取决于随机源、协议和实现，不能把“128 位密钥”理解为整个系统无漏洞。

均匀独立的 $b$ 位随机 nonce，使用 $n$ 次且碰撞概率较小时，生日近似：

$$P_{collision}\approx\frac{n(n-1)}{2^{b+1}}$$

例：64 位随机数使用 $10^6$ 次，约 $2.71\times10^{-8}$。这只估计碰撞，不证明认证安全；挑战还需不可预测、与会话绑定、只接受一次。

## 7. 隐私：隐藏标识之外还要限制关联

身份假名可隔离不同场景，但两个假名若共享稳定设备指纹、时间规律或账户关系，仍可能关联。匿名化不等于删除姓名即可。

位置隐私可采用模糊位置、降低精度、减少频率或发送多个候选位置；这些措施影响服务精度，并可能被轨迹约束推断。温度、电量、运动和用电量等数据也可能暴露作息与居家状态。

设计时明确采什么、为谁采、保留多久、谁能访问、如何删除；展示统计结果时避免不必要地公开单个设备的连续行为。

## 9. 温度监控安全版：CA、TA 与 MQTT 分工

### 9.1 数据经过哪些边界

![可信温度监控架构](物联网/pictures/08-物联网安全/课件-p052.png)

设备 TEE 采集／加密 → REE CA 发布 MQTT → Broker 转发 → 云侧 CA 收到密文 → 云侧 TA 解密 → 输出温度。课件使用树莓派 3B 和 OP-TEE 环境，接收侧也需要实际提供所需可信执行能力。

REE 负责网络与交互，TEE 保护敏感处理和密钥；pseudo TA 在课件中承担特权传感器访问。传感器输入和物理连线本身也属于可信路径，给普通数据“套一个 TEE 调用”不会自动让源头可信。

### 9.2 API 调用生命周期

`TEEC_InitializeContext` → `TEEC_OpenSession` → `TEEC_InvokeCommand` → `TEEC_CloseSession` → `TEEC_FinalizeContext`。

TA 对应入口包括创建、打开会话、命令分发、关闭和销毁。CA 与 TA 的命令编号、参数类型、方向、长度必须一致；校验失败应返回错误。课件示例通过安全监控调用等机制跨世界切换，TA 根据 command ID 分发操作。

共享缓冲区来自非安全世界，TA 不能直接信任长度、指针或内容；必要时复制和再次校验，避免越界和检查后被修改。

### 9.3 课件代码审读要点

RSA 密文是二进制，不可用 `strlen` 推断长度，也不能直接以 `%s` 输出。网络层传递显式字节长度；若 JSON 承载，应使用 Base64 等编码再解码。

**Base64 计算**：$n$ 字节编码长度为 $4\lceil n/3\rceil$。256 B 密文得到 $4\times86=344$ 个字符，额外增长 88 B，另加 JSON 与协议头。

教材中的直接 RSA 加密短温度数据用于展示跨世界流程；它不自动证明数据来自可信设备，也不提供重放防护。工程设计还需消息认证、设备身份、新鲜性和错误处理；大数据常采用经过认证的混合加密方案。

若采用 RSA PKCS#1 v1.5 加密，长度为 $k$ 字节的模数允许明文至多 $k-11$ 字节；2048 位模数 $k=256$，上限 245 B。这是格式长度上限，不能据此推导该模式适合所有新设计。

### 9.4 按边界验证案例

先验证传感器原始值和读取权限，再验证 CA—TA 参数、加解密长度、MQTT 密文传输和接收结果。随后验证被篡改包、重复消息、错误身份和设备重启等异常路径。编译成功、运行在 REE、运行在真实 TEE 是不同状态，不能混报。

## 10. 前沿研究：隔离、互通与传感器安全

课件介绍 dTEE 的声明式安全开发，WebAssembly／MiTEE 的受限设备隔离，以及 Matter 的设备认证与生命周期安全。学习时分别追问：缩小了哪些信任边界、增加了哪些运行时成本、凭据如何配置和撤销。课件只提供研究线索，本笔记未复现论文结果。

### 10.1 海豚音攻击为何可以产生可听指令

课件展示超声调制与麦克风链路非线性的关系。设抽象输入：

$$x(t)=[1+m(t)]\cos(\omega_ct)$$

器件近似 $y(t)=a_1x(t)+a_2x^2(t)$，利用 $\cos^2\theta=(1+\cos2\theta)/2$，平方项包含：

$$\frac{a_2}{2}[1+2m(t)+m^2(t)]\,[1+\cos(2\omega_ct)]$$

低通后的低频分量含 $a_2m(t)$，说明非线性可能把高频调制包络搬回基带。真实效果受器件、带宽、声学路径等限制。关键是失真在滤波之前已生成低频，单看“后面有低通”不足以排除风险。

![器件非线性](物联网/pictures/08-物联网安全/课件-p077.png)

防护需结合模拟前端设计、异常信号检测、指令来源验证与敏感动作的额外确认。语音被识别为一条命令，不等于已经证明说话者有权执行。

## 11. 综合题：为环境监测与风机控制设计安全链

设备唯一凭据存于受保护位置；启动验证固件；TLS 保护上报和命令；ACL 限制每台设备主题；温度消息绑定设备、时间与事件 ID；服务端验证范围和新鲜性；风机目标状态与一次性动作采用不同语义；OTA 验签、防回滚并可恢复；网关掉线仍能本地告警并可靠缓存。

每种机制必须对应威胁：TLS 对付链路观察与篡改；最小权限限制凭据泄露后的范围；签名和版本策略保护升级；请求 ID 和结果回报限制重复执行；看门狗帮助故障恢复。它们共同组成保护链。

## 12. 易错点与自测

1. **加密和签名分别做什么？** 加密保护秘密，签名验证来源和内容。
2. **合法旧命令为何危险？** 它可能通过完整性校验，但缺乏新鲜性。
3. **Secure Boot 后为什么仍需修补漏洞？** 已签名代码仍可能含可被利用的错误。
4. **TEE 是否保护所有外设输入？** 取决于外设归属、驱动和输入路径。
5. **授权频段能否替代 TLS？** 不能，频谱许可与应用端到端安全目标不同。
6. **看门狗能防止密钥泄露吗？** 其主要目标是故障检测与恢复。
7. **蜜罐是否应共享生产权限？** 应隔离，避免诱饵成为进一步入侵通道。
