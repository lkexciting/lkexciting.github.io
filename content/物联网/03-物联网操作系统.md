# 第三章 物联网操作系统

> 本章解释资源受限设备的软件组织、任务调度、远程升级和硬件抽象，并用可复算的调度与差分编码例题说明机制。

> [!info] 阅读说明


## 1. 为什么物联网也需要操作系统？

OS 将处理器、外设、网络等资源组织起来，提供统一接口与运行时环境，使应用开发者不必每次从寄存器和驱动开始写。核心价值是**硬件抽象、资源管理、任务调度和服务复用**。

![应用到硬件的分层关系](%E7%89%A9%E8%81%94%E7%BD%91/pictures/03-%E7%89%A9%E8%81%94%E7%BD%91%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E7%B3%BB%E7%BB%9F%E5%88%86%E5%B1%82.png)

与桌面 OS 相比，许多物联网 OS 面对 KB 级内存、无 MMU、较弱的隔离机制、无人值守、电池供电和无线更新等约束。这里是“许多受限平台”的特点，不能把所有 IoT 设备都说成没有 MMU：运行 Linux 的网关就可能有完整虚拟内存与权限隔离。

### 1.1 三种常见组织思想

| 概念 | 核心思想 | 优点与代价 |
|---|---|---|
| Library OS | 把部分 OS 功能作为库与应用链接 | 可裁剪、调用轻；隔离能力依具体实现 |
| 微内核 | 内核保留少量核心机制，其他服务模块化 | 模块清晰，需协调 IPC 与服务交互 |
| 宏内核 | 多种服务集成在内核空间 | 调用直接，但内核耦合与故障影响范围可能较大 |

在资源受限 MCU 上，“微内核设计思想”不意味着必然具有桌面系统那样的用户态进程隔离；底层硬件保护能力仍然重要。

## 2. 编程模型：从两个维度比较

### 2.1 按程序组织划分

- **非模块化**：作为整体开发和编译，结构简单，但复用与局部更新较困难。
- **源码组件化**：源码按组件组织，编译后可以仍是一个完整镜像。TinyOS 是代表。
- **二进制模块化**：编译后保留模块边界，可支持独立加载。SOS 是代表。

**源码模块化 ≠ 一定能动态加载。** 动态加载还需要二进制格式、符号解析、重定位与 OS 支持。

### 2.2 按执行方式划分

| 模型 | 如何表达等待 | 好处 | 难点 |
|---|---|---|---|
| 事件驱动 | 请求后返回，完成时触发事件 | 栈占用小，利于处理多个短事件 | 一个逻辑任务被分散成多个回调 |
| 多线程 | 在线程中按顺序调用、阻塞 | 业务逻辑连续，容易理解 | 每个线程有栈，同步和切换有开销 |

例：无线发送。事件模型是 `send()` 发起请求，稍后在 `sendDone()` 统计完成；线程模型可以等待发送结束后继续下一句。异步请求返回成功通常仅表示**请求被接受**，不能据此认为数据已经送达。

## 3. 调度与同步：最容易出计算题的部分

| 方式 | 何时换任务 | 关键约束 |
|---|---|---|
| 非抢占式 | 当前任务完成、阻塞或主动让出 | 长任务可能使其他任务等待 |
| 抢占式 | 高优先级就绪时可抢占 | 共享数据需同步，低优先级可能饥饿 |
| 协作式 | 任务主动 yield 或在等待点让出 | 某任务一直不让出会拖住系统 |
| 时间片轮转 | 片用完后转给下一个就绪任务 | 需明确片长、队列和同刻事件顺序 |

### 3.1 原子操作与临界区

```text
读取 x → 修改 x → 写回 x → 写外存
```

这一串步骤不是天然不可分割。在抢占式或多核环境中，应使用适当互斥锁等机制覆盖需要一致性的完整操作。协作式中不能在临界步骤之间随意 `yield()`。

讲解补充：单核非抢占式线程之间虽不会被随意切换，但中断仍可能访问共享数据。锁的作用范围也不自动包括中断，因此不能背成“非抢占式永远不用同步”。

### 3.2 调度题：逐段算

![线程调度思考题](%E7%89%A9%E8%81%94%E7%BD%91/pictures/03-%E7%89%A9%E8%81%94%E7%BD%91%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%AF%BE%E4%BB%B6-p013.png)


三个线程运行时间 a=10 s、b=20 s、c=30 s。假设单核、无切换开销、无额外 I/O 阻塞。

**（1）非抢占式：0 s 全部就绪，按 a、b、c 顺序。**

| 区间 | 任务 | 结束时刻 |
|---|---|---:|
| 0–10 | a | a 在 10 s 完成 |
| 10–30 | b | b 在 30 s 完成 |
| 30–60 | c | c 在 60 s 完成 |

**（2）抢占式：优先级 c>b>a，就绪时刻 a=1、b=2、c=15。**

- 0–1：CPU 空闲。
- 1–2：a 执行 1 s，还需 9 s。
- 2–15：b 执行 13 s，还需 7 s。
- 15–45：c 完成。
- 45–52：b 完成。
- 52–61：a 完成。

答案按 a、b、c 顺序是 **61 s、52 s、45 s**。完成时刻是绝对时间；周转时间还需减去各自到达时刻。

**（3）时间片 10 s：a 在 0 s、b 在 10 s、c 在 20 s 到达。**

0–10 a；10–20 b；20–30 c；30–40 b；40–60 c。

按“同刻新到达任务先入队、再把时间片用完的任务放队尾”的约定，a、b、c 完成时刻为 **10 s、40 s、60 s**。若 20 s 时先将 b 重新入队，b 会在 30 s 完成。题目没有说明这个边界约定，答题应写明自己的队列规则。

## 4. I/O 与内存管理

**阻塞式 I/O**：调用方等待操作完成后再返回；在多线程 OS 中，阻塞某线程不代表 CPU 必须停止处理其他线程。

**分阶段 I/O**：发起和完成分离，完成后由事件/回调通知。优点是等待时可处理其他工作，难点是状态管理、缓冲区有效期和错误处理。

| 分配方式 | 时机 | 优点 | 代价 |
|---|---|---|---|
| 静态 | 编译/链接阶段确定 | 占用可预测、无分配器碎片 | 不够灵活，可能预留过多 |
| 动态 | 运行时 malloc/free 等 | 按需使用 | 失败、泄漏、碎片、时间不可预测 |

固定内存池是讲解补充：以有限规格的块进行分配，常用于兼顾可预测性和一定灵活性。它不能让物理 RAM 变多。

## 5. OTA 与差分更新

### 5.1 Bootloader 和更新流程

示例流程：启动时查找升级文件 → 擦除旧 Flash → 写入新镜像 → 校验 → 启动或重试/回滚。

讲解补充：许多 MCU 会直接从 Flash 执行代码，不是所有系统都把完整固件装入 RAM。可靠 OTA 还应检查签名、版本和完整性，并考虑断电恢复、双镜像或回滚空间。CRC/哈希检错与“验证固件来自可信发布者”也不是同一件事。

| 方法 | 传输对象 | 优点 | 成本 |
|---|---|---|---|
| 整镜像 | 完整固件 | 实现直接 | 流量和写入量大 |
| 模块更新 | 改变的二进制模块 | 更新粒度小 | 需要模块边界与兼容机制 |
| 差分更新 | 新旧镜像差异指令 | 相似度高时传输少 | 需旧版本与重建过程，未必总更小 |

### 5.2 COPY/ADD 字节预算

本例的差分编码规则：`COPY n old_addr` = 1 B 操作码 + 2 B 长度 + 2 B 地址 = **5 B**。

`ADD n <literal>` = 1 B 操作码 + 2 B 长度 + n B 新内容 = **3+n B**。

例：旧 `ABCDEACBC`；新 `WABCDEACBC`。

```text
ADD 1 <W>     4 B
COPY 9 0      5 B
合计          9 B
```

注意 `COPY 9 0` 的地址是旧文件位置；不能把 COPY 的复制长度 9 当作 9 B 的指令开销。

### 5.3 原题

新文件 `WABCDEACBCXDEACB`：

```text
ADD 1 <W>     4 B
COPY 9 0      5 B
ADD 1 <X>     4 B
COPY 5 3      5 B
总大小       18 B
```

也可以用 `ADD 1 <W>`、`COPY 9 0`、`ADD 6 <XDEACB>`，成本同为 4+5+9=18 B。

这里新文件只有 16 B，直接用一条 `ADD 16` 也要 19 B，**传完整的 16 B 文件反而比上述差分包小**。差分适合大型、相似度高的文件，不能只看“改动少”。

“头部插入函数 vs 尾部插入函数”：实际二进制中头部插入可能使后续地址与重定位结果变化更多，从而增大补丁；但如果是仅按字节复制的理想字符串插入，两者成本未必不同。应区分程序布局影响和抽象 COPY 模型。

## 6. 网络与 TinyML 支持

受限节点需要低开销网络服务：链路接入、邻居发现、调度、路由和传输。理解层次：**802.15.4 是底层，6LoWPAN 负责适配 IPv6，RPL 负责路由，UDP/TCP 提供传输服务。**

TinyNet 通过所说的 2.5 层 uniMAC 抽象，把邻居发现、通信调度等功能与具体无线技术解耦。

TinyML 把小型机器学习模型部署到 MCU 等资源紧张设备，常用量化、剪枝和蒸馏控制 Flash、RAM 与计算需求。OS 支持不能只看“能否链接某框架”，还要看芯片、算子、模型和内存是否实际匹配。

## 7. 典型 OS：抓住“机制—作用”

### 7.1 Contiki：事件驱动与 Protothreads

Protothreads 用很少的状态保存执行位置，提供接近顺序程序的书写方式，通常多个过程共享一个 C 栈；遇到等待点返回调度器，之后再从逻辑位置继续。

**最重要的限制**：普通自动局部变量不能可靠地跨等待点保留。需要跨等待保存的变量用 `static` 或进程状态对象。“不能使用局部变量”应这样理解，而非所有临时局部变量都绝对禁止。

```c
/* 教学结构：省略具体头文件和平台配置 */
PROCESS(sample_process, "sample");
AUTOSTART_PROCESSES(&sample_process);
PROCESS_THREAD(sample_process, ev, data)
{
    static struct etimer timer;
    PROCESS_BEGIN();
    while (1) {
        etimer_set(&timer, CLOCK_SECOND);
        PROCESS_WAIT_EVENT_UNTIL(etimer_expired(&timer));
        read_and_process_sensor();
    }
    PROCESS_END();
}
```

| 机制 | 用途 |
|---|---|
| PROCESS | 声明过程 |
| AUTOSTART_PROCESSES | 设置自动启动过程 |
| PROCESS_THREAD | 定义过程体 |
| PROCESS_BEGIN/END | 管理逻辑入口、结束 |
| WAIT_EVENT_UNTIL | 条件未满足时让出执行 |

`mt_thread` 与 Protothreads 要区分：前者提供基于多个栈的线程机制，资源开销与能力不同。

网络：uIP 提供轻量 TCP/IP；6LoWPAN 做分片、重组、头部压缩；RPL 支持低功耗有损网络中的 IPv6 路由；Shell 支持交互操作。

### 7.2 RIOT：原生多线程、GNRC 与 SAUL

RIOT 面向 IoT 实时多线程，按优先级调度，各线程有自己的栈。模块化构建允许按需裁剪。

**GNRC**：通用网络协议栈，通过独立线程承载协议层。最底层 `gnrc_netdev` 将底层设备接口抽象，应用可使用 socket。不要把“支持多种无线协议”误认为网络层代码需要逐一重写。

**SAUL**：Sensor Actuator Uber Layer，统一传感器和执行器接口。

| 对象 | 作用 |
|---|---|
| `saul_reg_t` | 注册并描述一个设备，含设备指针、名称、驱动等 |
| `saul_driver_t` | 统一 read、write 与 type |
| `phydat_t` | 保存测量结果或控制参数 |
| `next` | 串联注册设备，便于遍历 |

答 ：一个外设对应 `saul_reg_t`；数据/参数用 `phydat_t`；GNRC 底层抽象是 `gnrc_netdev`。

### 7.3 AliOS Things：Rhino 内核

特点：小 Footprint、实时、多任务、低功耗；支持优先级抢占与时间片轮转、静态与动态分配，提供丰富的连接、OTA 和安全组件。

- Yloop：异步事件框架。
- uMesh：示例中的自组织网络组件。
- LwIP：轻量 TCP/IP。
- 空闲低功耗：预计一段时间无任务时进入合适睡眠状态，并减少不必要的周期时钟中断。

实时性是任务在时间约束内完成的可预测性，不是“主频越高越实时”。

### 7.4 HarmonyOS / OpenHarmony：按此版本理解

这里介绍多内核、组件裁剪、分布式软总线、LiteOS-A/M 等。应将这些视作这些系统设计思想，不把某页列出的调度与内核特征推广到所有产品版本。

- LiteOS-M：面向资源受限 MCU，强调轻量、硬件抽象与实时任务。
- LiteOS-A：面向具备更丰富资源的设备，提供更完整的系统能力。
- 分布式软总线：屏蔽底层连接差异，提供设备发现、连接与通信协同，让跨设备调用更容易。

**复习对照表**：

| OS | 核心记忆点 | 抽象与服务 |
|---|---|---|
| TinyOS | 事件、组件、静态资源 | 组件编译成镜像 |
| Contiki | Protothreads、协作、共享栈 | uIP、6LoWPAN、RPL |
| RIOT | 实时多线程、独立栈 | GNRC、SAUL |
| AliOS Things | Rhino、Yloop、OTA | uMesh、LwIP、安全组件 |
| HarmonyOS 体系 | 多内核、分布式 | LiteOS-A/M、软总线 |

## 8. AntiTheft 防盗案例：理解代码里的时间与并发

任务：周期读取加速度，判断波动是否异常，超过阈值点亮红灯。

![AntiTheft 防盗场景](%E7%89%A9%E8%81%94%E7%BD%91/pictures/03-%E7%89%A9%E8%81%94%E7%BD%91%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%AF%BE%E4%BB%B6-p065.png)


### 8.1 方差判断

$$\bar x=\frac{1}{N}\sum_i x_i,\qquad v=\frac{1}{N}\sum_i(x_i-\bar x)^2$$

避免最后除法，使用 $\sum(x_i-\bar x)^2>4N$ 判断是否方差大于 4。

- 采样频率 100 Hz → 采样间隔 10 ms。
- 检测每 1 s 执行一次。
- 缓冲区仅 10 个样本 → 表示最近约 0.1 s 的采样窗口；首末样本时刻相差 90 ms。

所以它不是每秒都把完整 100 个样本用于方差计算；100 Hz 采样、10 点滑窗、1 Hz 检测是三个不同参数。若要求检测完整 1 s 内的波动，应调整窗口或用在线统计。

### 8.2 代码阅读要指出的问题

1. 初始化时样本不足 10 个，不能把未填满的零值当成有效观测；应记录有效样本数。
2. 示例的 16 位平方和可能溢出；差值、平方与累加应使用足够宽的类型。
3. RIOT 采样线程与检测线程共享缓冲区，需要锁或一致性快照；否则可能读到半更新窗口。
4. 每次把 9 个数据前移有开销，可改环形缓冲区。
5. 定时 sleep 加处理时间会带来周期漂移；严格采样应采用周期定时机制。
6. 片段有大小写、分号、引号等教学排版问题，不能当作未经修改即可编译的工程。

## 9. 研究进展

低代码/大模型辅助 OS 开发；更强安全隔离；多语言、多协议可扩展性；间歇计算。

**间歇计算**：采能节点可能反复掉电，需要检查点、持久状态和幂等操作保证恢复后结果正确。它与“普通 sleep 后唤醒”不同：断电可能丢失易失内存。
