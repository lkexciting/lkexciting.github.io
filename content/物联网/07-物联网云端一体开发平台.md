# 第七章 物联网云—端一体开发平台

> [!info] 阅读说明
> 依据《第七章.pdf》整理，页码指 PDF 文件页序。平台名称、界面、SDK 和支持范围按课件历史版本理解；重点掌握开发模式、设备模型、约束与三端联调方法。

## 1. 全章地图：三端各做什么，靠什么接起来

![一体开发主要功能](物联网/pictures/07-物联网云端一体开发平台/课件-p010.png)

设备端感知与执行 → 云端存储、规则与业务 → Web／移动端展示和控制。三端通过统一设备模型、身份、主题、数据格式和命名约定协作。

| 开发部分 | 要做的事 | 常见困难 |
|---|---|---|
| 设备 | 驱动、采样、网络、控制 | 硬件异构、工具链、引脚与接口 |
| 云服务 | 接入、数据、规则、API | 多协议、复杂流程、认证与权限 |
| 应用 | 曲线、仪表盘、控制按钮 | 数据绑定、状态同步、交互 |
| 三端集成 | 统一能力与消息契约 | 标识、类型、单位、错误和时序不一致 |

平台封装可复用能力，降低重复开发量；真实硬件连接、语义一致性和业务验证仍需完成。

## 2. 设备端开发的三条路线

| 路线 | 流程 | 优点 | 约束 |
|---|---|---|---|
| 本地编译 | 本地 SDK／OS → 交叉编译 → 烧录 | 工具可控，便于底层调试 | 配置工具链与驱动 |
| 云端编译 | 上传代码与配置 → 云构建 → 下载／烧录 | 集中管理编译环境 | 网络、平台支持范围与版本 |
| 解释型语言 | 安装运行时 → 加载脚本 | 开发快，接口简洁 | 运行时内存、性能、硬件支持 |

SDK 包含 API、文档和工具；OS 还提供任务调度、资源管理、更新等能力。云端编译得到的设备固件仍在设备上运行，不等于把设备业务搬到云端。MicroPython 也会涉及字节码等内部实现，课件“无需编译”主要指用户不必执行传统固件交叉编译流程。

### 2.1 MicroPython 的模块分工

`machine` 控制 GPIO、定时器和总线；`network` 配置网络；`bluetooth` 面向支持平台的 BLE。具体接口与硬件能力取决于运行时版本和移植端。

```python
# 课件风格示意：GPIO2 是否接 LED、是否低电平点亮需查板卡
from machine import Pin
import time
led = Pin(2, Pin.OUT)
while True:
    led.value(not led.value())
    time.sleep(1)
```

中断处理尽量短，不把打印、分配大对象或联网直接放在硬中断里。Wi-Fi 连接应设置超时、失败状态和重连路径，不能无限忙等后假设连接成功。

### 2.2 Node-RED：事件流式编程

用节点接收、转换、判断和输出消息，连线表达事件流。基于 Node.js 的事件驱动机制，既可运行在网关也可运行于云端。课件的社交消息触发 LED 是历史示例，学习重点是“输入节点 → 触发节点 → GPIO 输出”，不要把某外部接口可用性视为长期保证。

## 3. 云服务与应用端开发

### 3.1 接入设备的三个步骤

发现设备 → 确认控制关系和身份 → 注册设备与能力。发现不等于已认证，注册成功不等于已有任意控制权限。

### 3.2 IFTTT 与服务编排

IFTTT 适合简单“条件—动作”；服务编排把查询、计算、分支、存储、API 等节点连接成流程，便于表达多步骤逻辑。节点之间传递什么结构、失败时走哪条路径，需要明确。

**条件顺序例题**：检测房间无人耗时 $t_A=500\,ms$，检测灯亮耗时 $t_B=10\,ms$，无人概率 $p_A=0.2$，灯亮概率 $p_B=0.1$。在可短路且先后观察不改变语义的假设下：

$$E[T_{A\to B}]=t_A+p_At_B=502\,ms$$
$$E[T_{B\to A}]=t_B+p_Bt_A=60\,ms$$

先做便宜且容易判假的判断通常有利。一般比较 $t_A+p_At_B$ 与 $t_B+p_Bt_A$；不能只凭单个处理时间判断。并行求值可能降低时延，但增加资源和能耗；异步结果还需保证时间一致性。

### 3.3 应用端三种复用方式

| 方法 | 核心机制 | 使用重点 |
|---|---|---|
| 从设备代码生成框架 | 从接口／注解推导 UI 与调用 | 生成的控件仍需配置语义 |
| 可视化拖拽 | 组件库 + 数据源绑定 | 产品、设备、属性、单位与刷新 |
| 插件 | 自定义界面嵌入宿主应用 | 接口、生命周期与权限 |

曲线要绑定测量值和时间，开关要区分“用户请求”和“设备回报”。不能在按钮刚点击时就把 UI 当作实际执行结果。

## 4. 设备模型：让设备与应用可以分别开发

![基于设备模型的开发](物联网/pictures/07-物联网云端一体开发平台/课件-p041.png)

先定义能力契约，再由硬件人员实现、云端人员开发服务、应用人员绑定组件。灯泡模型可有光照、声音强度属性，开／关服务和属性上报事件。

SmartThings 在课件中用设备—组件—能力—属性／命令组织；IoT Studio 用属性、事件、服务组织。应比较抽象层次，而不是把两个平台的字段名互换。

| 物模型元素 | 英文 | 含义 | 空调示例 |
|---|---|---|---|
| 属性 | Property | 可读取／设置的状态或数据 | temp，float，℃ |
| 事件 | Event | 已发生的事情及参数 | TemperatureAlarm |
| 服务 | Service | 可调用的动作及输入输出 | open，返回成功状态 |

模型要统一 identifier、数据类型、单位、量程、步长、访问方式、服务参数和错误含义。显示名可中文，协议标识应一致。模型标了 0.1 的步长，不代表物理传感器准确度达到 0.1。

## 5. 命名机制：名字如何定位数据或动作

传统路径把应用对象映射为 URI／设备身份，再经 DNS、IP 等定位网络服务；平台还需维护设备与业务对象关系。

NDN（Named Data Networking，命名数据网络）以数据名称请求内容：Interest 请求，Data 携带名称、内容和签名。课件示例：

```text
/MyHome/Bedroom/Lighting/sensing/Intense/时间戳
/MyHome/Bedroom/Lighting/TableLamp/action/ON
```

分层前缀支持聚合，减少应用对位置的依赖。NDN 不是简单“把 IP 改成长字符串”；它改变数据检索和转发模型。用于动作时，还需新鲜性和防重放，缓存中的旧 ACK 不能证明本次动作执行。

## 6. TinyLink 1.0：从功能需求生成软硬件

### 6.1 自底向上与自顶向下

传统：需求 → 选板和外设 → 接线 → 驱动与业务代码 → 编译烧录。

TinyLink：用硬件无关 API 描述需求 → 分析代码 → 查硬件数据库并求解配置 → 生成接线与固件 → 组装烧录。

![TinyLink使用流程](物联网/pictures/07-物联网云端一体开发平台/课件-p064.png)

`TL_Temperature.read()` 表达温度功能，不把某个 DHT11 引脚写死在业务逻辑里。选择方案后，硬件配置头文件和对应驱动把统一 API 落到真实设备。

### 6.2 硬件生成的约束建模

设候选组件 $i$ 是否选择为 $x_i\in\{0,1\}$，成本为 $c_i$，提供功能 $f$ 的能力为 $a_{if}$，接口 $p$ 的提供量和占用量分别为 $s_{ip},d_{ip}$。

$$\min\sum_i c_ix_i$$
$$\sum_i a_{if}x_i\ge r_f\quad\text{（各功能需求）}$$
$$\sum_i s_{ip}x_i\ge\sum_i d_{ip}x_i\quad\text{（各类接口）}$$

还需板卡组合、电压、电平、地址、引脚复用、驱动和资源约束。I²C 多设备能共享总线，但仍受地址冲突等限制，不能机械地按“一个设备占一整条总线”套所有情况。

**选型例题**：板 A 40 元、1 路 UART；板 B 60 元、2 路 UART；两个不可共享 UART 的传感器各 20 元；扩展模块 25 元并提供净增 1 路可用 UART，假设电气和驱动均兼容。

- A + 两传感器：80 元，UART 不够，不可行。
- A + 扩展 + 两传感器：105 元，可行。
- B + 两传感器：100 元，可行，三者中成本最低。

先排除不可行方案，再优化价格。用户要求“有 Wi-Fi”通常表示至少一个可用实现，写成 $\sum a_{i,WiFi}x_i\ge1$；课件个别文字“大于 1”不宜理解为必须配两块 Wi-Fi 模块。

### 6.3 软件生成与调试

硬件无关用户代码 + 硬件配置头文件 + 驱动／库 + 目标工具链 → 固件。基础调试需要预留串口；交互调试要求板卡、系统和调试接口支持。把调试需求写入约束，否则最低价方案可能无法满足调试要求。

## 7. TinyLink 2.0：扩展到三端协同

设备侧引入微应用、任务、通信等高层抽象；云侧把规则转换成配置，由事件／时间触发器驱动；客户端生成器把相关代码生成 WebView 程序。

课件规则引擎使用消息队列、规则队列、命令队列组织工作，队列由 Redis 实现。它们分别承接输入、待评估规则和待执行命令；需要考虑积压、顺序和重复处理。

四个关键概念：微应用模型描述数据、事件和服务；隐式交互减少显式通信细节；云定义节点行为用规则安排任务；虚拟传感器组合多个数据源形成推断。自动交互仍依赖身份、连通性和明确的一致性边界。

## 8. IoT Studio：物模型与服务编排

### 8.1 工作台与三端分工

课件涵盖设备开发、业务逻辑、Web、移动应用与数据分析。Bone 框架提供应用端组件；可视化工作台绑定物模型数据。设备端可采用 SDK、OS 或脚本；支持范围以课件所示版本为背景。

### 8.2 物模型消息格式

属性上报主题：

```text
/sys/{productKey}/{deviceName}/thing/event/property/post
```

```json
{
  "id":"123",
  "version":"1.0",
  "params":{"temp":30.0},
  "method":"thing.event.property.post"
}
```

事件主题包含事件 identifier，服务调用主题包含服务 identifier。课件代码中的弯引号、注释和尾逗号是排版示意，真正 JSON 使用英文双引号且不含注释或尾逗号。

### 8.3 温度告警编排

设备触发 → Node.js 提取温度 → 路径判断 → 通知机器人。先确认 `payload.props.temperature.value` 对应真实输入结构，再检查有限数值和量程。

![温度告警服务编排](物联网/pictures/07-物联网云端一体开发平台/课件-p118.png)

课件案例文字写“温度大于 30”，后续节点配置写“大于等于 30”。两者在 30℃ 时不同；笔记统一用需求中的 **$T>30℃$**，并测试 29.9、30.0、30.1。不能把边界差异略去。

触发节点包括设备、定时、空间、HTTP、MQTT；功能节点包括脚本与计算；输出可为 HTTP 返回、通知；数据节点访问表格、关系库或键值存储；API 节点调用其他服务。课件出现的 Node.js 运行时版本属于历史环境。

## 9. Tuya IoT：按产品复杂度选择开发方式

| 课件开发路线 | 适用情况 | 开发内容 |
|---|---|---|
| 零代码 | 标准插座、照明等 | 配置产品功能和通信模组，生成固件 |
| 低代码 | 产品含自定义 MCU | 接 MCU SDK，编写产品逻辑 |
| 多代码 | 网关、摄像头等复杂产品 | 基于设备 SDK 深度开发 |

云端创建项目、授权设备、调用 API；应用端以面板表达产品 UI，可使用公版应用、OEM 应用或 SDK。课件还介绍边缘网关、行业硬件方案与 SaaS 框架。课件中的开发者数量和生态覆盖范围是历史统计，不用于判断当前服务状态。

## 10. 案例：智能教室座位使用统计

### 10.1 原始链路

树莓派 4B + PIR → 每 10 秒采集 → 上报 `deviceID`、`motionState` → 物模型 → Web 指示灯。

![座位监测系统](物联网/pictures/07-物联网云端一体开发平台/课件-p135.png)

创建项目和产品 → 定义属性 → 硬件接线 → 配置凭据／SDK → 采样上报 → 拖拽界面 → 绑定设备属性 → 预览验证。

课件接线为 VCC、GND、GPIO18 信号，实际组装需核对模块输出电平与树莓派 GPIO 输入允许范围。PIR 检测红外变化，静坐可能无运动信号，**motionState=0 不足以证明座位无人**。真实占用统计可引入保持时间、其他传感器或置信度。

### 10.2 上报速率与界面新鲜度

假设 100 座位、每 10 s 一条、每条序列化后 120 B：

$$\lambda=100/10=10\text{条/s},\quad V_{day}=10\times120\times86400=103.68\,MB$$

是十进制纯载荷，不含 MQTT、TCP、TLS 等开销。均匀相位的周期采样平均等待约 5 s，最坏接近 10 s，再加网络、云处理和 UI 刷新。统一整点上报还可能形成瞬时突发。

### 10.3 TinyLink 与 IoT Studio 联合开发

TinyLink 生成设备固件与硬件配置；IoT Studio 负责云逻辑和界面。关键是接入同一物模型：主题一致、字段一致、类型一致、身份一致。

课件认证参数由 productKey、deviceName、deviceSecret、clientId、timestamp 等形成，用户名示例 `deviceName&productKey`，签名基于规范串计算 HMAC。不能用普通字符串拼接代替签名，也不能认为 HMAC 自动加密传输。示例中的 TCP 1883、固定凭据和旧签名算法是教材配置，实际环境应核对平台对应安全连接要求。

## 11. 易错点与自测

1. **云端编译和云端执行有什么区别？** 前者只把构建搬到云，固件仍在设备运行。
2. **统一 API 为什么还需要驱动？** API 屏蔽硬件差异，驱动负责真实寄存器和协议操作。
3. **云—端一体的关键为何不只是三个工作台？** 三端还要共享模型、标识和消息契约。
4. **接收 motionState 能否直接算真实上座率？** 先证明该传感器输出与占用语义对应。
5. **按钮能调用服务是否算成功？** 还需设备执行与实际状态回报。

联调按设备原始读数 → 本地序列化 → MQTT 认证与主题 → 云端解析 → 服务节点 → UI 数据源逐段检查，保留设备 ID、消息 ID、采集时间和错误日志。
