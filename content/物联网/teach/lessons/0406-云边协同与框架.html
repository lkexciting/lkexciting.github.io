一、云边协同：两种协同模式

概述（课件第 107 页）：云边协同推理将边缘侧的本地计算能力与云端的远程计算能力结合，根据任务需求和运行条件安排模型推理，协调响应时延与资源开销。两种模式：

智能路由（以推理请求为单位）

根据请求特点、模型能力和运行条件，为每个推理请求选择由边缘侧或云端的模型处理。典型部署：边缘运行轻量模型、云端运行能力更强的模型。
决策依据：① 任务需求（任务类型、结果质量、响应时间）；② 模型能力（本地是否适合、云端能改善多少）；③ 运行状态（边缘负载、可用内存、云端服务状态）；④ 网络与使用约束（网络是否可用、传输耗时、调用成本、数据能否上传）。
策略：前置路由（主要推理开始前就选好模型）；级联回退（先本地处理，根据结果是否满足接受条件再决定是否调云端）。

分割计算（以模型内部计算为单位）

将同一个模型的不同部分安排在边缘侧和云端执行：边缘推理模型前部分，中间结果传输到云端，云端继续推理并返回结果。核心思想：协同利用云端强大算力与边缘即时响应，对 DNN 模型战略性划分，实现低延迟、低能耗、高效率。设计思想：不是简单一分为二，而是基于 DNN 结构与计算特性，在本地计算与网络通信开销之间寻找最优平衡点。

二、分割计算的两个规律与最佳切分点（必背）

规律课件结论（第 114–116 页）
数据量：先增后减网络前段中间数据维度急剧膨胀（conv1/conv2 输出量远大于原始输入）；随着网络深入，池化层（pool）通过下采样压缩特征图，显著减少数据量 → 呈「先增后减」趋势
计算延迟：后端急剧上升全连接层（fc）处理的数据量虽小，但内含海量参数和密集矩阵乘法——AlexNet 中 fc6/fc7 占据超过 90% 的计算时间，推理瓶颈位于后端
与剪枝章节「卷积层占 90% 计算量」不矛盾（课件第 116 页，易考辨析）

本实验环境为 NVIDIA Tegra K1（GPU）：卷积操作局部性强、可并行，GPU 延迟低；全连接层密集矩阵计算无法用 GPU 加速，延迟高。总结：小而多的计算（卷积层）GPU 能并行加速、延迟低；大而密的计算（全连接层）发挥不了 GPU 特性、延迟高。

最佳切分点：位于数据量经池化层大幅压缩之后、计算最密集的全连接层开始之前。对 AlexNet，这个点恰好出现在 pool5 层之后——边缘只做前半部分特征提取，传输已大幅压缩的中间数据（远小于原始图像），云端接手计算量最大的全连接层，实现「最小化数据传输」+「最大化计算卸载」双重目标。

关键应用场景（第 118 页）：① 智能个人助理（Hey Siri）——边缘本地完成唤醒词识别（极速响应），云端处理语音识别与 NLU（高算力）；低延迟高频任务在边缘，高算力低频任务在云端。② 自动驾驶——边缘执行行人检测、紧急制动等毫秒级任务，云端更新车队高清地图并训练感知模型。③ 实时 IoT 与可穿戴——资源受限设备（如 MCU 执行器）本地执行最基本功能（阈值触发安全关闭），复杂分析卸载云端。

三、主流端侧推理框架对比与选型

类型代表框架主要模型核心技术
通用端侧推理LiteRT（TFLite）CNN、Transformer模型转换与量化，CPU/GPU/NPU 加速
跨平台推理ONNX RuntimeCNN、Transformer 等计算图优化、算子融合，执行后端适配不同硬件
端侧大模型推理llama.cppLLM、部分视觉语言模型低比特量化、CPU 指令优化、CPU/GPU 混合推理
瑞芯微 NPU 部署RKNN / RKLLM视觉、语音模型及 LLM专用格式转换、量化与图优化、NPU 加速
高通平台部署QNNCNN、Transformer 等计算图构建、量化、Hexagon NPU 加速

TFLite 要点

Google 研发，2017 年发布。转换器把模型转为 .tflite（基于 FlatBuffers，可内存映射直接使用、无需解析），转换时做算子融合与量化两大优化；解释器靠 Delegate 委托机制把计算交给 GPU/DSP/NPU（如 NNAPI、Core ML 委托）。核心运行时仅约 1 MB；TFLite Micro 面向超低资源 MCU——无需操作系统、文件系统和动态内存分配，运行时核心仅约 20 KB Flash，可跑在 ARM Cortex-M0+ 至 M7 全系列（TinyML 标杆）；官方示例 micro_speech 在仅 256 KB 内存的 Arduino Nano 33 BLE 上离线关键词检测。局限：仅支持约 60 个算子、不支持动态形状输入；PyTorch 模型需先转 ONNX。

ONNX Runtime 要点

ONNX 格式由 Meta 与 Microsoft 联合发起；ONNX 是开放标准格式、通用中间表示（IR），将模型定义与训练框架解耦，实现「一次转换，随处部署」。图优化：常量折叠、节点消除（如推理时移除 Dropout）、节点融合（MatMul+Add 融合）。最具特色机制：执行提供程序（EPs）——把计算图执行无缝委托给专用硬件加速库，不改模型、运行时指定 EP 即可换硬件（默认 CPU / CUDA EP / TensorRT EP），与 TFLite 委托机制类似。

llama.cpp 与厂商工具链

llama.cpp：最流行的本地大模型运行工具（Ollama、LM Studio、LocalAI 底层依赖它）。五大技术：GGUF 单文件格式（权重+分词器+架构参数+量化元数据封装在一文件）、量化位宽 2~8-bit（「Q4_K_M」＝4-bit + K-quant 混合精度）、CPU SIMD 优化（x86 AVX2/AVX-512、ARM NEON）、GPU 按层卸载（Metal/CUDA/Vulkan/OpenCL）、mmap 内存映射按需加载（模型文件大于物理内存也能运行）。实测：香橙派 3B（4GB RAM）跑 Qwen-1.8B INT4，四步、不超过 10 分钟、无需 Python。局限：不支持 CNN/RNN 等传统视觉模型。厂商工具链解决「如何把 NPU 算力用满」：RKNN 面向视觉模型（RK3588 三核 NPU）、RKLLM 面向 LLM；高通 QNN 面向骁龙 Hexagon NPU。

选型小结（课件第 143 页，必背）

跨平台通用部署 → ONNX Runtime / TFLite；端侧大语言模型 → llama.cpp；特定 NPU 极致能效 → 厂商工具链（RKNN / RKLLM、QNN）。

课程实验——离线识物挑战（第 146 页）：以 ResNet-50 V1 为基础，通过结构化剪枝（Group-L1，计算量约 4.1 GMACs 降至 2.9 GMACs）→ 恢复微调（20 万张图微调 20 轮）→ 转换与量化（PNNX 转 ncnn 格式，5,000 张图 KL 校准，生成混合 INT8 模型）→ 部署评测（香橙派 Mali-G610 GPU，固定 10,000 张验收图统一测试）。提交 .param、.bin 和 model.json 三个文件；进阶挑战：改进剪枝与量化策略或引入知识蒸馏。
