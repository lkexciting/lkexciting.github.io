MQTT：发布订阅、主题通配符与 QoS 等级

一句话：这节讲设备连接的核心协议 MQTT——发布订阅模型、+/# 通配符、三级 QoS 与吞吐估算，本章最重的计算与对比考点都在这里。

本课依据

考试内容以 PPT（课件）为准。本课对应课件《第六章-2026》6.2 主要功能之"设备连接"节【教材 PPT 补充单独标注】。原始课件：D:\学习文件\大三上\物联网技术基础与应用开发\第六章-2026.pdf

一、为什么用发布订阅 + 三种协议怎么选

设计动机：同一设备的数据要同时供看板、告警与存档使用，消费者还会不断变化。核心区别：设备按主题发布，应用按需求订阅，减少生产者与消费者的地址耦合。

协议定位课件要点
HTTP/1.1通用请求—响应Web 生态成熟，小载荷需关注首部开销
CoAP轻量资源访问面向受限网络；Observe 可订阅资源变化
MQTTBroker 发布—订阅主题匹配、一对多分发、可选交付保障

课件结论：MQTT 适合以 Broker 为中心的消息分发；CoAP 适合受限网络中的资源访问。

教材 PPT 补充：MQTT 报文类型（节选必背）

CONNECT(1, C→S 连接请求)、CONNACK(2, S→C 连接确认)、PUBLISH(3, 双向，向话题发布)、PUBACK(4, 双向，发布确认)、SUBSCRIBE(8, C→S 订阅请求)、SUBACK(9, S→C 订阅确认)、DISCONNECT(14, C→S 断开请求）。PUBLISH 报文标志位：Bit3 DUP（1=重传）、Bit1~2 QoS（0~2）、Bit0 RETAIN（1=代理保留消息）。

二、报文顺序与主题通配符（与课件一致）

一次发布订阅的报文顺序（以温度看板订阅设备 A 为例）：① 连接建立：看板→Broker CONNECT，Broker→看板 CONNACK；② 订阅登记：SUBSCRIBE / SUBACK，Broker 登记主题过滤器；③ 发布分发：设备 A→Broker PUBLISH，Broker→看板 PUBLISH。订阅建立与数据发布是不同步骤；发布者不需要知道看板地址。

主题组织：发布主题如 campus/b1/A/temp；一号楼全部温度 = campus/b1/+/temp；一号楼全部层级 = campus/b1/#。

发布主题：factory/A/temp（发布主题本身不能含通配符） factory/+/temp → 匹配 factory/A/temp（+ 匹配一个层级） factory/# → 匹配 factory/A/temp（# 匹配后续多个层级，位于过滤器末尾） factory/B/temp → 不匹配 factory/+/temp factory/+/state → 不匹配 factory/A/temp 主题层级用于业务组织；订阅过滤器用于选择消息。

三、三个 QoS 等级与两段连接（必背表）

等级语义机制代价
QoS 0至多一次无协议确认重发可能缺失，开销较低
QoS 1至少一次确认与必要重发可能重复交付
QoS 2恰好一次额外交互与协议状态避免同次交换重复交付

QoS 描述相邻 MQTT 端点间的消息交付语义；等级提高通常增加交互与状态成本；协议交付不等同于业务动作执行一次。

两段连接：设备→Broker 与 Broker→看板是两次交付，看板订阅时也提出 QoS 要求；下行 QoS 不高于订阅要求——发布 QoS 1、订阅最大 QoS 0，则下行按 QoS 0 交付。较高的上行 QoS 不会自动提升所有下游交付的保障。

选择依据：缺失容忍度、重复后果、时效与资源开销。持续温度→QoS 0（允许少量缺点，后续采样及时更新）；重要告警→QoS 1（消费端应能处理重复）；严格交付需求→QoS 2（平台支持且可接受更多交互与状态）。

四、确认等待与吞吐估算（计算题）

QoS 1 下：在途上限 C（未确认消息数），确认往返时延 RTT 理想吞吐上界 ≈ C / RTT 课件例：C = 20，RTT = 80 ms = 0.08 s → 20 / 0.08 = 250 条 / 秒 变式（课件思考）：目标 500 条/秒 → 需要 C ≥ 500 × 0.08 = 40 条在途容量 长距离链路例：RTT=100ms、每条 1 KB、W=20 → 20/0.1 = 200 条/s，载荷 ≈ 200 KB/s

注意：扩大窗口还需考虑内存和 Broker 处理能力；窗口增大，客户端状态也增大；实际吞吐仍受网络与 Broker 限制。

教材 PPT 补充：Paho Python 接口（课件 28–29 页同款）

发布：publisher.publish("campus/b1/A/temp", payload, qos=1)；订阅：subscriber.subscribe("campus/b1/+/temp", qos=1)，回调 subscriber.on_message = handle_temperature。连接成功回调 on_connect 中 rc==0 再订阅；on_message 打印 message.topic 与 payload.decode()；启动网络循环不等于订阅已成功。

延伸了解（课件 30–33 页）：Sparkplug 3.0（2022）/ ISO/IEC 20237:2023 为 MQTT 提供工业语义互通，规范消息含义但不替代传输；MQTT over QUIC 探索连接迁移与弱网恢复（需客户端与 Broker 共同支持），标准 MQTT 3.1.1 以 TCP 为基础。案例：吉利/亿咖通车联网（200 万+ 接入车辆、平均同时在线 35 万+）；上汽大众 2020 年上线的车联网平台用 MQTT 解耦车机与云端业务。

课件思考题（本课相关）

思考题（教材 PPT 第 41 页）：对比 MQTT、CoAP、HTTP。

点开看参考答案

（教材 PPT 第 42 页原表，三列均为应用层协议）MQTT：传输层 TCP；可靠；传输代价小；支持多播；支持双向通信（资源受限设备）；需要中间代理（Broker）转发；温度上传示例报文长度 20（MQTT）+32（TCP）字节。CoAP：传输层 UDP；可靠可选；传输代价小；支持多播；支持双向通信；无中间代理；32（CoAP）+8（UDP）字节。HTTP：传输层 TCP；可靠；传输代价大；不支持多播；资源受限设备难做双向；32+824（HTTP）字节。
