边缘计算（Greengrass）与四大典型云平台

一句话：这节讲计算放到现场的机制与取舍（Greengrass 组件、计算卸载、断网缓存补传），并对比 AWS IoT / Azure IoT / 阿里云 IoT / ThingsBoard 四大平台。

一、边缘计算：Greengrass 的云边协作

同一任务（设备异常→本地告警）：云端路径是 设备→网络→Lambda→结果返回；现场路径是 传感器→EdgeAlarm 组件→本地告警。执行位置改变的是通信依赖与资源条件，业务判断可以保持一致；同一数据仍可上传作历史分析。Linux 网关运行 Greengrass nucleus，采集、处理和上传是可部署的组件。

课件三个组件分工：采集组件（读取设备 → factory/temp）、com.example.EdgeAlarm（订阅 temp → 判断阈值 → 写 outbox → 发布 factory/alarm）、MQTT Bridge（本地消息 → IoT Core）。业务处理不等待云端往返；SQLite 补传需另设上传器。组件配方（recipe）描述版本、所需文件和生命周期（如 Run: python3 -u {artifacts:path}/alarm.py），代码作为 artifact 随组件交付；本地 IPC 权限（如 SubscribeToTopic 资源 factory/temp）与云端 IoT 策略分别配置。

采集适配器数值解码（课件例）： raw = bytes([0x00, 0xFD]) value = int.from_bytes(raw, "big", signed=True) * 0.1 # 字节顺序 bigendian；有符号 16 位；比例 0.1℃/单位 → 253 → 25.3℃ 协议适配必须保留数据语义，不能只把字节搬到云端。

二、计算卸载与断网缓存（两道计算模板）

① 计算卸载的带宽临界条件： 上传 D Mbit，网络往返 L ms，云端处理 C ms，边缘处理 E ms 边缘路径 ≈ E + D/R（R 单位 Mbit/s）；若 E ≤ L + C，则云端不可能更快 课件数值例：D=2 Mbit、L=30 ms、C=10 ms、E=100 ms → 20 Mbit/s 时边缘更快；50 Mbit/s 时云端更快；阈值处两条路径时间相同 先统一单位再解带宽阈值；分母符号决定是否存在可行解。
② 断网缓存的容量与补传： 容量预算：50 KB/s × 4 × 3600 s = 720,000 KB = 720 MB（十进制）→ 数据库预算 > 720 MB 缓存上限例：600,000 KB / 50 KB/s = 12,000 s ≈ 3 小时 20 分（满盘策略：背压/丢最旧/降采样） 补传：现场 200 条/s，上传能力 500 条/s，积压 10,000 条 → 净清理速率 300 条/s，清空 ≈ 33.33 s 重传沿用原 event_id；本地发送成功不等于业务确认，确认后才删除 outbox 记录。

outbox 表用 event_id 作主键（INSERT OR IGNORE 去重）；MQTT Bridge 只处理配置的消息路由，桥不会自动读取 SQLite。断网测试观察三处：本地功能是否继续、记录是否跨进程重启（outbox 行数增加、重启后仍在）、云端结果是否完整对应。

平台课件关键词协议支持特色
Amazon AWS IoT2015 年推出的托管物联网云平台；支持数十亿设备和数万亿条消息MQTT、WebSockets、HTTP 1.1设备影子、规则引擎、注册表；身份验证支持 SigV4、X.509 证书、自定义令牌；Lambda 无服务器计算；配套 Kinesis（流计算）、S3（存储）、DynamoDB（NoSQL）、SNS（消息收发）

本章总结（课件 6.5，六句话）

① MQTT 以主题解耦消息生产与消费，QoS 在可靠交付与通信成本之间取舍；② 时序存储围绕持续采样与范围统计优化，压缩收益取决于数据与负载；③ 流计算复用窗口状态减少重算，Flink 支持多设备持续处理；④ Lambda 以代码与资源配置承接事件，权衡初始化、环境复用与快照恢复；⑤ Greengrass 把组件、消息和缓存部署到现场，并按端到端时延选择云边分工；⑥ ThingsBoard 用实际界面回应接入、规则、展示与控制。四平台一句话：AWS IoT——云基础设施与 Lambda；Azure IoT——机器学习服务及交互式模型构建；阿里云 IoT——Link ID2 设备认证与 IoT Studio 一站式开发；ThingsBoard——开源、私有化部署、可视化规则引擎与拖拽式仪表盘。

案例：语音控制智能灯（8 步）：① 注册登录平台（ThingsBoard Cloud，设备 ESP32_LED，MQTT Basic 凭据）→ ② 验证 MQTT 连通性（mosquitto_pub 发 temperature=25，收到 CONNACK(0) 与 PUBACK）→ ③ 硬件接线（ESP32：GPIO26→R、GPIO25→G、GPIO27→B，各通道串联 220Ω）→ ④ 设备端代码（Makefile + LEDController + main.cpp）→ ⑤ 编译烧录 → ⑥ 手动测试 RPC（setLed，Params {"value":true/false}）→ ⑦ Web 端语音控制（录音→16kHz PCM→百度识别 dev_pid=1537→关键词匹配→JWT Token→oneway RPC）→ ⑧ 完整联调。设备端要点：订阅 v1/devices/me/rpc/request/+（+ 匹配任意 requestId）；回调匹配后 msg_send 交给 LED 线程，不在回调中直接 MQTTPublish（MQTTYield 持有 client.mutex，重入会死锁）；Keepalive 设 0 并靠 TCP keepalive 与每 5 秒重连检查（RIOT Paho 移植层检查 PINGRESP 窗口约 10 ms，云端往返可能超 200 ms 会误判断连）。

研究前沿（课件 156–157 页）：MELT（MobiCom 2024）系统测量端侧模型推理，联合评估时延、内存、能耗与精度；PowerInfer-2 以神经元簇为粒度协调 CPU、NPU 与存储，重叠数据加载与计算。

课件思考题（本课相关）

思考题（教材 PPT 第 118 页）：简述 Amazon AWS IoT、Microsoft Azure IoT、阿里云 IoT 的功能。

点开看参考答案

（按课件 6.3 整理）AWS IoT：设备通信支持 MQTT/WebSockets/HTTP 1.1；设备影子包含最新状态、离线也可交互；规则引擎按业务规则转换并转发入站消息；身份验证支持 SigV4、X.509 证书、自定义令牌；注册表为设备建立唯一身份并跟踪元数据；可利用 Lambda、Kinesis、S3、DynamoDB、SNS 等服务。Azure IoT：设备连接支持 MQTT/HTTPS/AMQP；设备管理含直接管理、设备影子、智能网关；数据存储用 Cosmos DB/MySQL/PostgreSQL/MariaDB；认证用对称密钥/安全令牌与 X.509 CA 证书；Azure Functions 无服务器计算；通过无服务器计算下沉实现边缘计算；提供机器学习服务。阿里云 IoT：设备通信支持 MQTT/CoAP/HTTPS；支持直接管理、设备影子、网关子设备与 OTA；时序存储与基于 Flink 的实时计算；规则引擎可转发到存储服务、函数计算或其他 Topic 实现 M2M；ID² 芯片级安全与一机一密认证；函数计算支持多语言；Link Edge 支持设备接入、边缘函数计算、消息路由和断网续传。

思考题（课后习题答案第 11 题）：为边缘计算场景设计寻找计算下沉锚点的算法（边缘节点只知道自身父节点），并求复杂度。

点开看参考答案

（习题答案第 11 题原解要点）该问题即寻找两点的最近公共祖先（LCA）：设 depth[x] 为深度、pre[x] 为父结点，则 depth[lca(u,v)] ≤ min{depth[u], depth[v]}。算法：depth[u]<depth[v] 时 lca(u,v)=lca(u,pre[v])；depth[u]>depth[v] 时 lca(u,v)=lca(pre[u],v)——u、v 不断向根步进直到 u==v。复杂度：预处理 O(nlogn)，查找 O(depth(u)+depth(v))。
