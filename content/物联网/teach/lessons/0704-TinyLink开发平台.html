TinyLink 开发平台

一句话：浙大出品、自顶向下 + 云端编译的快速开发平台——从"写代码"到"自动生成硬件配置 + 二进制程序"，硬件/软件两大生成系统是本节最深的考点。

本课依据

考试内容以 PPT（课件）为准。本课对应课件《第七章》第 3 节【典型平台：TinyLink（1.0 + 2.0）】（教材 PPT 补充单独标注）。原始课件：D:\学习文件\大三上\物联网技术基础与应用开发\第七章.pdf

一、TinyLink 是什么：从自底向上到自顶向下

简介：2017 年 3 月浙大 EmNets 实验室推出软硬件一体快速开发平台 TinyLink 1.0；2017 年 12 月推出 TinyLink 2.0——在 1.0 设备端开发的基础上，集成 Web 端应用和手机端应用开发，构成物联网一体化开发平台（设备端 + 云端 + 手机端）。

传统物联网应用开发（编程模式：自底向上）：构思应用功能逻辑 → 选开发板/外设/扩展板并设计硬件连接图组装平台 → 开发程序（写入网络配置和外设管脚连接信息）→ 交叉编译得二进制文件 → 烧录开发板 → 观察运行结果并调试。课件以室内环境监测应用（Arduino+SDS018+Light+DHT11）为例，指出 PM2.5 传感器需自行封装读取函数（读串口→提取数据→CRC 校验→存缓冲区→返回滑动平均）。

传统开发的不便（三方面，简答高频）：硬件选择——需要硬件知识、掌握硬件特性以保证兼容性；软件设计——需要掌握各外设在不同平台的驱动编写、选择合适的驱动库；软硬件协同——选型要考虑驱动库兼容性，软件要按硬件连接确定引脚端口，且物联网没有固定硬件平台、更换平台时软件迁移工作量大。

TinyLink 1.0 开发过程（自顶向下）：应用需求分析 → 节点软件编程（TL_WiFi、TL_Light 等 API）→ 系统分析用户代码 → 硬件平台搭建。（论文：G. Guan, W. Dong*, et. al, TinyLink, ACM MobiCom 2017。）

二、TinyLink 使用流程（五步，必背）

准备：①下载 TinyLink 客户端并注册（http://tinylink.emnets.org）；②阅读 TinyLink 用户手册与 API 文档。之后：

  1. ①编写程序代码：本地文本编辑器编写（setup 里 TL_Serial.begin(9600)；loop 里 TL_PM25/TL_Temperature/TL_Humidity/TL_Light 各 .read()，打印 .data()，TL_Time.delayMillis(3000)）。
  2. ②上传代码并编译：选择待上传文件 → 提交上传文件 → 生成硬件及代码编译结果。
  3. ③获取硬件配置：得到硬件列表（例：开发板 Arduino MEGA 2560、扩展板 Mega Shield、外设 Grove Light Sensor / Grove 温湿度传感器 / SDS018，含购买链接）与硬件连接图（如 SDS018 接 UART Pin(D14,D15)，光照传感器接 Analog Port(A0,A1)）。
  4. ④组装物联网平台：购买硬件列表中的硬件，按硬件连接示意图组装。
  5. ⑤烧录应用程序：硬件平台经 USB 连电脑，点击 TinyLink 客户端一键烧写按钮。
特点小结（三条，简答必背）

开发模式转变：自顶向下 vs 自底向上。自动：自动生成硬件配置和二进制代码；自动接入物联网平台（如 IBM Watson IoT、OneNet）；并能优化指定目标（如价格、功耗）。简单：编程简单（Arduino setup/loop + TinyLink APIs）；云编译——不需要复杂的本地编译环境。客户端大小对比：Arduino IDE+LinkIt One 包 420 MB、树莓派交叉编译链 266 MB、BBB 交叉编译链 302 MB、TinyLink 客户端仅 69 MB。

推荐系统：为用户推荐可实现相同功能的不同硬件平台——上述例子选择 LinkIt One 平台后，推荐了 34 种不同可行硬件方案，其中 TinyLink 目前可支持编译的有 8 种。支持设备列表：开发板（Arduino UNO/Mega2560/DUE、LinkIt One/Smart 7688、树莓派 2/3、BeagleBone Black、Mbed TinyBLE、AliOS MK3060）；扩展板（Grove Base/WiFi/SD Shield、GrovePi+）；传感器（DHT22、DHT11、Grove UART WiFi、Grove GPS、SDS018、声音/灰尘/响度/光照传感器、Grove BLE、IMU 9DOF/10DOF、三轴加速度计/罗盘/陀螺仪等）。

三、TinyLink 1.0 系统框架：硬件生成系统（计算题核心）

两大系统：硬件生成系统——通过分析应用程序代码，结合硬件数据库的领域知识，自动生成硬件配置；软件生成系统——结合硬件配置和对应软件库，通过交叉编译链生成应用程序的二进制代码。

  • 硬件数据库：包含已有硬件的信息及其特征，作为自动生成配置的关键信息源。表 4-3 例：组件（Arduino UNO 开发板 / WiFi 扩展板 V2.0 / 基础扩展板 V1.3 / Grove 光照传感器 / Grove UART WiFi 模块）×（ID、成本￥、提供接口、占用接口、功能如 WiFi/Light/LED）。
  • 用户约束条件：来自用户需求功能，如应用用到 WiFi，则"所有包含 WiFi 功能的模块总数量应该大于 1"（含 WiFi 的模块如主板 LinkIt One、扩展板 WiFi Shield V2.0、外设 Grove UART WiFi）。
  • 接口约束条件：对 {Analog, UART, I2C, SPI, USB, …} 中每一类型的接口，要求 提供 Port 的数量 ≥ 消耗 Port 的数量（均对主板∪扩展板∪外设求和）。
  • 问题规约：在 {主板 ∪ 扩展板 ∪ 外设} 里找到一组子集，满足用户约束 + 硬件约束（满足用户需求、保证硬件选型正确有效），优化目标为价格最小化；通常生成 210 条约束条件；该问题为经典的线性规划问题，使用经典线性规划求解器 lp_solver 进行求解。

四、软件生成系统与 TinyLink 2.0

软件生成系统：以硬件配置头文件衔接——硬件无关部分是用户代码，硬件相关部分是硬件配置 + 驱动和库文件。API 来源：从 116 个网上公开的 IoT 项目中提取出 225 个常用 API，按功能种类分组，实现 24 种类别的 API（包括 LED、温湿度、显示、WiFi 等）。调试两种：基础调试——代码中写 #REQUIRE DBGPrint;，IoT 平台一定会引入额外的 UART 接口打印所有调试信息；交互式调试——代码中写 #REQUIRE DBG;，若开发板原生系统支持交互式调试则可被选入硬件平台（树莓派和 Beaglebone 平台会利用 gdb 调试；TinyLink 同时提供项目源代码供深入调试）。

TinyLink 2.0 三端开发：设备开发——基于软硬一体快速开发技术，添加领域特定元素（宏和数据类型），实现许多任务处理操作；高层 API 封装大量 1.0 的 API、隐藏不重要的细节；丰富系统功能如支持 LoRa 传输和程序并发执行。云服务开发——将云端规则转换为 JSON 格式的规则配置，把规则条件与 RESTful API 一起解释为后缀表达式；规则引擎在云端运行，可加载、解释大量规则配置并为每个规则注册触发器（触发器分基于事件和基于时间两类）；规则引擎包含三个线程，每个线程都有一个由 Redis 实现的简单 FIFO 消息队列：消息队列、规则队列、命令队列。移动端开发——客户端生成器将客户端代码（例如带 @Client 后缀的微应用）编译为 WebView 客户端程序：先构建抽象语法树，再将与其它微应用的交互转换为 JavaScript 代码，使用默认混合模板用 HTML 和 JS 表示 UI。

TinyLink 2.0 关键特性（四条）：微应用模型——定义物联网节点的功能和行为，抽象传感数据、检测到的事件及暴露给其他微应用和策略的服务调用接口，屏蔽数据传输、事件上报和服务调用的底层实现细节；隐式交互——以结构化方式与微应用模型结合，允许跨微应用查询接口中定义的数据，实现每个节点状态的自动跟踪、自动保持节点一致性（数据流和服务调用的一致性）；云定义节点行为——设计类 IFTTT 规则并添加新关键词以增强开发多应用实例的功能，控制节点根据任务计划在适当时间点执行任务；虚拟传感器——自动从多源传感器数据组合生成推理模型。
