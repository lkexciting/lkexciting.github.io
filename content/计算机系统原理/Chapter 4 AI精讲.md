# Chapter 4 AI 精讲：处理器（The Processor）

> 教材：Computer Organization and Design — RISC-V Edition, Chapter 4
> 本讲目标：从"一条指令怎么被执行"出发，构建 **单周期数据通路（single-cycle datapath）**，再改造成 **五级流水线（5-stage pipeline）**，并解决三类冒险（hazard）。这是全课程的核心章节，也是考试与面试的重灾区。

## §4.1 引言

### 4.1.1 CPU 性能的两个因子

| 因子 | 由谁决定 |
|---|---|
| **指令数**（instruction count） | **ISA 与编译器** |
| **CPI 与周期时间**（cycle time） | **CPU 硬件** ← 本章主题 |

### 4.1.2 两种 RISC-V 实现

1. **简化版**：单周期实现（single-cycle）
2. **更现实的流水线版**（pipelined）

### 4.1.3 指令子集（本章只做这些）

| 类别 | 指令 |
|---|---|
| 访存（memory reference） | `ld`, `sd` |
| 算术/逻辑（arithmetic/logical） | `add`, `sub`, `and`, `or` |
| 控制转移（control transfer） | `beq` |

> 这个小子集"展示了大多数方面"——加上 `lw/sw`、`jal/jalr`、`addi` 就覆盖了全部格式（R/I/S/B/U/J）。

### 4.1.4 指令执行的五个动作

1. **PC → 指令存储器**，取出指令（fetch）
2. **寄存器编号 → 寄存器堆**，读寄存器（read registers）
3. 根据指令类别：
	- 用 **ALU** 计算：算术结果 / 访存地址 / 分支目标地址
	- 为 load/store **访问数据存储器**
4. **PC ← 目标地址 或 PC + 4**

## §4.2 逻辑设计约定（Logic Design Conventions）

### 4.2.1 信息与元件

- 信息用**二进制**编码：低电压 = 0，高电压 = 1
- **每比特一根线**；多比特数据在**多线总线**（bus）上编码

| 元件类型 | 特点 | 例子 |
|---|---|---|
| **组合元件**（combinational element） | 对数据操作，**输出是输入的函数**（无记忆） | AND 门、加法器、多路选择器、ALU |
| **状态元件**（state/sequential element） | **存储**信息，由时钟决定何时更新 | 寄存器、存储器 |

**两种连接方式**：总线连接、分散连接。

- **数据通路**（datapath）：由操作部件与存储部件通过总线/分散方式连接而成，进行**数据存储、处理、传送**的路径
- **控制器**（control）：对指令**译码**，生成控制信号，控制数据通路的动作

### 4.2.2 组合元件

| 元件 | 表达式 |
|---|---|
| AND 门 | Y=A B |
| 多路选择器（multiplexer, mux） | Y=S ? I_1:I_0 |
| 加法器（adder） | Y=A+B |
| ALU | Y=F(A,B)，由操作码 `F` 选择功能 |

> **为什么必须用 mux？** 教材强调："**不能简单把导线接在一起**"（can't just join wires together）——两路数据同时驱动一根线会短路。必须用多路选择器**选出**一路。这是数据通路设计的铁律。

### 4.2.3 时序元件：寄存器

- **寄存器**（register）：在电路中存储数据
- 用时**时钟信号**决定何时更新存储值
- **边沿触发**（edge-triggered）：当 Clk 从 **0 → 1**（上升沿）时更新

时序参数：

| 参数 | 含义 |
|---|---|
| **建立时间**（setup time） | 时钟沿到来**之前**数据必须稳定的时间 |
| **保持时间**（hold time） | 时钟沿之后数据必须保持的时间 |
| **锁存/传播时间**（latch prop / clk-to-Q） | 时钟沿到输出有效的延迟 |

> 讲师补充：D 的信号在**建立时间**内就已存在，写进去之后还要一段延迟（保持时间）才能完全写好，否则可能写入错误值。**只有保持时间之后读取才是正确、正常的**。

**带写控制的寄存器**（register with write control）：

- 只在**写控制输入为 1** 时的时钟沿更新
- 用途：当存储的值"**后续才需要**"时使用（这正是流水线寄存器的思想——但流水线寄存器通常每拍都写）

### 4.2.4 时钟策略（Clocking Methodology）

- 组合逻辑在**时钟周期内**（两个时钟沿之间）变换数据
- 输入来自状态元件，输出到状态元件
- **最长的延迟决定时钟周期**（Longest delay determines clock period）

Cycle Time=Latch Prop+Longest Delay Path+Setup+Clock Skew

- 所有状态部件在**上升沿**写入，经过 Latch Prop 后输出有效
- **只有状态部件能存储信息**；所有操作部件都必须从状态部件接收输入，并把输出写入状态部件
	- 输入 = 前一时钟生成的数据
	- 输出 = 当前时钟所用的数据

> 这条"**状态元件为界**"的规则，是理解流水线的关键：**流水线寄存器把一个长周期切成多个短周期**，每段内的组合逻辑只需要在该段延迟内完成。

## §4.3 构建数据通路（Building a Datapath）

### 4.3.1 数据通路的组成部件

寄存器、ALU、mux、存储器……（elements that process data and addresses in the CPU）

我们**增量式**地构建：从概览图出发，逐条指令添加元件。

### 4.3.2 取指（Instruction Fetch）

- **PC**（program counter）→ **指令存储器**（instruction memory）→ 指令
- 同时用一个**加法器**计算 `PC + 4`（increment by 4 for next instruction）

> 注意 `PC+4` 的加法器是**独立的**——它不占用主 ALU，这样在流水线中取指与执行可以并行。

### 4.3.3 R 型指令的数据通路

三件事：

1. **读两个寄存器操作数**（rs1, rs2 → 寄存器堆的两个读端口）
2. **执行算术/逻辑操作**（ALU）
3. **写回寄存器结果**（rd ← ALU 结果，通过写端口）

### 4.3.4 Load/Store 指令

1. **读寄存器操作数**（rs1 = 基址，rs2 = 要存的数据）
2. 用**12 位偏移**计算地址：**用 ALU 做加法，但偏移要先符号扩展**
3. **Load**：读存储器，**更新寄存器**（rd）
4. **Store**：把寄存器值**写入存储器**

> 关键：**立即数生成单元（imm Gen）** 负责把 12 位立即数**符号扩展**到 64 位——这是第 2 章"符号扩展"的硬件落点。

### 4.3.5 分支指令

1. **读寄存器操作数**（rs1, rs2）
2. **比较**：用 ALU 做**减法**，检查 **Zero 输出**（结果是否为 0）
3. **计算目标地址**：
	- 符号扩展位移量
	- **左移 1 位**（半字位移，因为指令 2 字节对齐）
	- 加到 PC 上（PC+4 已由取指阶段算好）

> 讲师的提示（P19）：分支目标的低位加法只是"**重新布线**"（just re-routes wires），符号位则是"**复制一根线**"（sign-bit wire replicated）——**移位在硬件里就是接线，不需要逻辑门**。

### 4.3.6 拼装要素（Composing the Elements）

- **第一版数据通路一条指令一个时钟周期**（single-cycle）
- 每个数据通路元件**同一时刻只能做一件事**
- 因此**必须把指令存储器与数据存储器分开**（separate instruction and data memories）
	- 否则同周期内"取指"与"访存"会冲突（结构冒险）
- **不同指令的数据来源不同 → 用多路选择器选择**

![[Ch4-P21-数据通路拼装.webp]]

![[Ch4-P22-完整单周期数据通路.webp]]

> 完整单周期数据通路的关键路径：**PC → 指令存储器 → 寄存器堆 → ALU → 数据存储器 → 寄存器堆**（这正是 §4.5 的性能问题所在）。

## §4.4 简单实现方案（A Simple Implementation Scheme）

### 4.4.1 ALU 控制（ALU Control）

ALU 用于：

| 指令 | ALU 功能 |
|---|---|
| load/store | F=add（算地址） |
| branch | F=subtract（比较） |
| R 型 | F 由 **funct 字段**决定 |

**ALU 控制码**：

| ALU control | 功能 |
|---|---|
| 0000 | AND |
| 0001 | OR |
| 0010 | add |
| 0110 | subtract |

（另有 0111 用于 `slt` 等，本章子集不涉及）

### 4.4.2 两级译码：ALUOp + funct

**不要**用 opcode 直接生成 4 位 ALU 控制码，而是分级：

| opcode | ALUOp | 操作 | funct7 | funct3 | ALU function | ALU control |
|---|---|---|---|---|---|---|
| `ld` | 00 | load register | XXXXXXX | XXX | add | 0010 |
| `sd` | 00 | store register | XXXXXXX | XXX | add | 0010 |
| `beq` | 01 | branch on equal | XXXXXXX | XXX | subtract | 0110 |
| R-type | 10 | add | 0000000 | 000 | add | 0010 |
| R-type | 10 | subtract | 0100000 | 000 | subtract | 0110 |
| R-type | 10 | AND | 0000000 | 111 | AND | 0000 |
| R-type | 10 | OR | 0000000 | 110 | OR | 0001 |

**为什么要分级？**

> ALU 由 **ALUOp（2 位，来自主控制）** 和指令的 **funct7/funct3** 联合产生 ALU 控制码。
> 好处：**分级控制**，减少主控制单元的规模，减少控制单元的延迟。
> —— 这是"让常见情况快"在控制逻辑上的应用：主控制只需粗分类，细分类交给小的组合逻辑。

![[Ch4-P26-主控制单元真值表.webp]]

### 4.4.3 控制信号（必背）

| 信号名 | 0（deasserted） | 1（asserted） |
|---|---|---|
| **RegWrite** | 不写寄存器 | 把写数据写入写寄存器端口 |
| **ALUSrc** | ALU 第二操作数来自寄存器堆 Read data 2 | ALU 第二操作数是**符号扩展后的 12 位立即数** |
| **PCSrc** | PC ← PC+4 加法器输出 | PC ← 分支目标地址加法器输出 |
| **MemRead** | 不读 | 读数据存储器 |
| **MemWrite** | 不写 | 写数据存储器 |
| **MemtoReg** | 写寄存器的数据来自 **ALU** | 写寄存器的数据来自**数据存储器** |
| **Branch** | 普通 PC+4 | 分支（与 Zero 相与后控制 PCSrc） |
| **ALUOp1/ALUOp0** | —— | 2 位 ALU 粗控 |

### 4.4.4 控制信号表（按指令）

| 信号 | R 型 | `ld` | `sd` | `beq` |
|---|---|---|---|---|
| ALUSrc | 0 | 1 | 1 | 0 |
| MemtoReg | 0 | 1 | x | x |
| RegWrite | 1 | 1 | 0 | 0 |
| MemRead | 0 | 1 | 0 | 0 |
| MemWrite | 0 | 0 | 1 | 0 |
| Branch | 0 | 0 | 0 | 1 |
| ALUOp1 | 1 | 0 | 0 | 0 |
| ALUOp0 | 0 | 0 | 0 | 1 |

> **记忆法**：
> - `RegWrite=1` 只有 R 型和 load（它们要写寄存器）
> - `ALUSrc=1` 只有 load/store（它们要用立即数算地址）
> - `MemRead` 只有 load；`MemWrite` 只有 store
> - `Branch=1` 只有 beq
> - `MemtoReg=1` 只有 load（数据来自存储器）

![[Ch4-P29-带控制的数据通路.webp]]

### 4.4.5 三条指令的完整流程（在图上走一遍）

| 指令 | 数据流 |
|---|---|
| **R 型**（`add x1,x2,x3`） | PC→IM→(rs1,rs2)→RF→ALU→(rd)→RF 写回；`ALUSrc=0`, `MemtoReg=0`, `RegWrite=1` |
| **Load**（`ld x1,100(x2)`） | PC→IM→rs1→RF→ALU(+imm)→**DM 读**→RF 写回；`ALUSrc=1`, `MemRead=1`, `MemtoReg=1`, `RegWrite=1` |
| **Branch**（`beq x1,x2,L`） | PC→IM→rs1,rs2→RF→ALU(sub)→Zero→与 Branch 相与→PCSrc→PC |

## §4.5 单周期的性能问题（Performance Issues）

- **最长延迟决定时钟周期**（critical path）
	- **指令存储器 → 寄存器堆 → ALU → 数据存储器 → 寄存器堆**
- **不可能按指令类型改变周期长度**（not feasible to vary period for different instructions）
- 这**违反了设计原则 3**：**让常见情况变快**（making the common case fast）
	- 因为简单的 `add` 也要等满 `ld` 那条最长路径
- 解决方向：**流水线（pipelining）**

**为什么不能"按指令变周期"？** 因为时钟是全局的，PC 每拍递增 4；若周期可变，控制会极其复杂，且流水线无从谈起。

## §4.6 流水线概述（An Overview of Pipelining）

### 4.6.1 洗衣店类比

**流水线洗衣**（pipelined laundry）：把"洗衣 → 烘干 → 折叠 → 收纳"重叠执行。

| 场景 | 时间 | 加速比 |
|---|---|---|
| 非流水（串行）4 批 | 4 × 2 = 8 单位 | —— |
| 流水，4 批（有填充开销） | 3.5 单位 | 8/3.5≈2.3 |
| 流水，不停机（n 批） | 0.5n+1.5 | 2n/(0.5n+1.5)≈4 = **级数** |

> 关键洞察：**加速比的上限 = 流水线级数**，且需要"大量任务连续不断"才能逼近上限。

### 4.6.2 RISC-V 五级流水线

| 阶段 | 名称 | 工作 |
|---|---|---|
| 1 | **IF**（Instruction Fetch） | 从存储器取指令 |
| 2 | **ID**（Instruction Decode） | 译码 **并读寄存器** |
| 3 | **EX**（Execute） | 执行运算或计算地址 |
| 4 | **MEM**（Memory） | 访问存储器操作数 |
| 5 | **WB**（Write Back） | 结果写回寄存器 |

> **关键**：RISC-V 的**固定指令格式**允许"**译码与读寄存器同时进行**"（ID 合一）——这是 x86 做不到的（x86 指令 1~17 字节，必须先译码才知道操作数在哪）。

### 4.6.3 流水线性能

**假设**：寄存器读/写 100 ps，其他阶段 200 ps。

| 指令 | 取指 | 读寄存器 | ALU | 访存 | 写寄存器 | 总时间 |
|---|---|---|---|---|---|---|
| `ld` | 200 | 100 | 200 | 200 | 100 | **800 ps** |
| `sd` | 200 | 100 | 200 | 200 | —— | 700 ps |
| R-format | 200 | 100 | 200 | —— | 100 | 600 ps |
| `beq` | 200 | 100 | 200 | —— | —— | 500 ps |

- **单周期**：T_c=800 ps（按最长的 `ld`）
- **流水线**：T_c=200 ps（按最慢的阶段）

![[Ch4-P37-单周期与流水线性能对比.webp]]

### 4.6.4 流水线加速比公式

**若所有阶段平衡**（耗时相同）：

T_(pipelined)=T_(nonpipelined)/(Number of stages)

- 若**不平衡**，加速比更小
- 加速来自**吞吐率（throughput）提升**，而**单条指令的延迟（latency）不变**（甚至因流水线寄存器略微增加）

> 这是最容易被误解的一点：**流水线不减少一条指令的时间，只增加单位时间完成的指令数**。

### 4.6.5 流水线与 ISA 设计

RISC-V 的 ISA 是**为流水线设计的**：

| 特征 | 对流水线的好处 |
|---|---|
| **所有指令都是 32 位** | 取指与译码可在一拍完成（对比 x86：1~17 字节） |
| **指令格式少且规整** | 译码与读寄存器可合并为一步 |
| **Load/store 寻址** | 地址在第 3 级算，存储器在第 4 级访问——**结构完美对齐** |

> 结论：**ISA 的设计决定流水线实现的复杂度**（第 2 章"规整性"的回报）。

### 4.6.6 冒险（Hazards）

**定义**：阻止下一条指令在下一周期开始执行的情况。

| 类型 | 定义 | 典型原因 |
|---|---|---|
| **结构冒险**（structural hazard） | 所需**资源忙** | 单存储器同时被取指与访存使用 |
| **数据冒险**（data hazard） | 需等前一条指令完成**数据读/写** | `add x19,...` 后紧跟 `sub ...,x19,...` |
| **控制冒险**（control hazard） | 控制动作**依赖前一条指令** | 分支结果未定就要取下一条 |

## §4.7 流水线的数据通路与控制（Pipelined Datapath and Control）

### 4.7.1 结构冒险与"分离存储器"

![[Ch4-P52-流水线数据通路.webp]]

- 单存储器时，`ld/sd` 需要访存，**取指就必须停顿**（stall）→ 产生流水线"**气泡**"（bubble）
- 因此流水线数据通路**必须**有独立的**指令存储器与数据存储器**
	- 或用独立的**指令 Cache 与数据 Cache**（第 5 章）

### 4.7.2 流水线寄存器（Pipeline Registers）

**必须在各级之间插入寄存器**，保存上一周期产生的信息：

| 寄存器 | 保存内容 |
|---|---|
| **IF/ID** | PC+4、指令字 |
| **ID/EX** | PC+4、读出的两个寄存器值、立即数、rs1/rs2/rd 编号、控制信号 |
| **EX/MEM** | ALU 结果、Zero 标志、rd 编号、控制信号 |
| **MEM/WB** | 读出的存储器数据、ALU 结果、rd 编号、控制信号 |

> 讲义 P52 的重要批注：**"Right-to-left flow leads to hazards"**——数据通路中有**从右向左**的流动（WB 写回寄存器 → ID 读寄存器；MEM 的零标志 → IF 的 PC 选择），这种**反向依赖**正是冒险的根源。

### 4.7.3 逐周期的流水线图

两种画法：

| 图 | 含义 |
|---|---|
| **单周期流水线图**（single-clock-cycle diagram） | 某一**拍**内流水线的状态，高亮该拍用到的资源 |
| **多周期流水线图**（multi-clock-cycle diagram） | 随时间展开的**资源使用表**（传统形式） |

![[Ch4-P64-多周期流水线图.webp]]

> 画法规范：**行 = 指令，列 = 时钟周期**；对角线形式最直观。

**逐阶段走查（load 指令）**：

| 阶段 | 动作 | 注意 |
|---|---|---|
| IF | 取指，PC+4 | —— |
| ID | 译码，读 rs1，立即数符号扩展 | —— |
| EX | ALU 算地址（rs1 + imm） | —— |
| MEM | 读数据存储器 | —— |
| WB | 写回 rd | **⚠️ 此处易错** |

> **经典错误（P59）**：WB 阶段若直接把 **IF/ID 或 ID/EX 中的 rd** 拿去写寄存器，会写错寄存器号——因为此时流水线里已经换成了**后面指令**的字段。**写回必须用 MEM/WB 寄存器里保存的 rd**（corrected datapath P60）。

### 4.7.4 控制信号的分组

| 阶段 | 需要的控制信号 |
|---|---|
| **IF** | 无（不需要控制线） |
| **ID** | 无 |
| **EX** | `ALUOp`、`ALUSrc` |
| **MEM** | `Branch`、`MemRead`、`MemWrite` |
| **WB** | `MemtoReg`、`RegWrite` |

控制信号在 **ID 阶段产生**，然后**随流水线寄存器逐级传递**（EX/MEM/WB 各用各的那一份）。

> 为什么"传下去"而不是"用到时再产生"？因为指令字在流水线中已经走到后级，ID 阶段的译码信息必须**跟着走**。

## §4.8 数据冒险：旁路 vs 停顿（Forwarding vs. Stalling）

### 4.8.1 什么是数据冒险

```asm
add x19, x0, x1
sub x2, x19, x3      # 需要 x19，但 add 还没写回
```

时间线：

| 指令 | IF | ID | EX | MEM | WB |
|---|---|---|---|---|---|
| `add x19,...` | 1 | 2 | **3** | 4 | **5** |
| `sub x2,x19,...` | 2 | 3 | **4** ← 此处需要 x19 | 5 | 6 |

- `sub` 在 **EX**（第 4 拍）就需要 x19
- `add` 要到 **WB**（第 5 拍）才写回
- → **差 2 拍**，直接读寄存器读到的是旧值

### 4.8.2 旁路/转发（Forwarding / Bypassing）

**核心思想**：**结果一算出来就用，不必等它写回寄存器**。

- 需要数据通路中**额外的连线**（从 EX/MEM、MEM/WB 的输出接回 ALU 的输入）
- 代价：增加 mux 与连线，但**不增加周期**

![[Ch4-P75-旁路路径.webp]]

**转发路径**（三种情况）：

| 情况 | 数据来源 | 是否需要停顿 |
|---|---|---|
| 前一条指令的 ALU 结果 | EX/MEM 寄存器 | 不需要（EX→EX 转发） |
| 前两条指令的 ALU 结果 | MEM/WB 寄存器 | 不需要（MEM→EX 转发） |
| 前一条是 **load** | 数据在 MEM 末才出来 | **需要 1 拍停顿** |

### 4.8.3 如何检测"需要转发"

**做法**：让**寄存器编号随流水线传递**。

- `ID/EX.RegisterRs1` 表示"当前在 ID/EX 流水线寄存器中的那条指令的 Rs1 编号"
- EX 阶段的两个 ALU 操作数编号就是 `ID/EX.RegisterRs1` 与 `ID/EX.RegisterRs2`

**冒险条件**：

| 条件 | 转发来源 |
|---|---|
| 1a. `EX/MEM.RegisterRd = ID/EX.RegisterRs1` | 从 **EX/MEM** 转发 |
| 1b. `EX/MEM.RegisterRd = ID/EX.RegisterRs2` | 从 EX/MEM 转发 |
| 2a. `MEM/WB.RegisterRd = ID/EX.RegisterRs1` | 从 **MEM/WB** 转发 |
| 2b. `MEM/WB.RegisterRd = ID/EX.RegisterRs2` | 从 MEM/WB 转发 |

**但必须加两个限定条件**：

1. **只有当前指令会写寄存器时**才转发：`EX/MEM.RegWrite`、`MEM/WB.RegWrite` 为 1
2. **只有 Rd ≠ x0 时**才转发：`EX/MEM.RegisterRd ≠ 0`、`MEM/WB.RegisterRd ≠ 0`
	- 反例：`sll x0, x5, 2`——写 x0 等于丢弃结果，绝不能把它的"结果"转发出去

### 4.8.4 转发控制表

| Mux 控制 | 来源 | 说明 |
|---|---|---|
| `ForwardA = 00` | ID/EX | 第一 ALU 操作数来自**寄存器堆** |
| `ForwardA = 10` | EX/MEM | 来自**上一条指令的 ALU 结果** |
| `ForwardA = 01` | MEM/WB | 来自**数据存储器或更早的 ALU 结果** |
| `ForwardB = 00` | ID/EX | 第二 ALU 操作数来自寄存器堆 |
| `ForwardB = 10` | EX/MEM | 同上 |
| `ForwardB = 01` | MEM/WB | 同上 |

### 4.8.5 双重数据冒险（Double Data Hazard）

```asm
add x1, x1, x2
add x1, x1, x3
add x1, x1, x4
```

- 第三条指令的 x1 **同时**可以从 EX/MEM（第二条）和 MEM/WB（第一条）转发
- **必须用"最近"的那个**（第二条的结果）

**修正条件**：MEM 阶段冒险只在 **EX 阶段冒险不成立** 时才转发

```
if (MEM/WB.RegWrite and (MEM/WB.RegisterRd ≠ 0)
    and not (EX/MEM.RegWrite and (EX/MEM.RegisterRd ≠ 0)
             and (EX/MEM.RegisterRd = ID/EX.RegisterRs1))
    and (MEM/WB.RegisterRd = ID/EX.RegisterRs1))
      ForwardA = 01
```

> 优先级：**EX/MEM 优先于 MEM/WB**（越新越优先）。

![[Ch4-P79-带旁路的数据通路.webp]]

### 4.8.6 Load-Use 数据冒险（必考）

```asm
ld  x2, 20(x1)
and x4, x2, x5      # 需要 load 的结果
```

| 指令 | IF | ID | EX | MEM | WB |
|---|---|---|---|---|---|
| `ld` | 1 | 2 | 3 | **4**（数据此时才出） | 5 |
| `and` | 2 | 3 | **4** ← 需要 x2 | 5 | 6 |

- **不能靠转发解决**：第 4 拍 `and` 在 EX 时，`ld` 的数据还在 MEM 里**刚出来**
- **"Can't forward backward in time!"** —— 无法向"未来"转发

**解决：停顿 1 拍**

> 严格说，若允许"同一拍内 MEM→EX 的转发"（half-cycle 路径），可以不停顿；但标准五级流水线按整拍边界处理，因此需要 1 拍。

### 4.8.7 Load-Use 冒险的检测

**在 ID 阶段检测**（此时使用指令正在译码）：

- ID 阶段的操作数编号是 `IF/ID.RegisterRs1`、`IF/ID.RegisterRs2`
- **Load-use 冒险条件**：

ID/EX.MemRead ∧ ((ID/EX.RegisterRd=IF/ID.RegisterRs1) ∨ (ID/EX.RegisterRd=IF/ID.RegisterRs2))

> 注意这里用 `RegisterRd`（教材旧版写 `RegisterRt`）：因为 load 的**目的**寄存器就是它的 rd。

### 4.8.8 如何实现"停顿"（Stall）

1. **把 ID/EX 寄存器中的控制值强制为 0**
	- 使 EX、MEM、WB 阶段做 **nop**（no-operation）
2. **阻止 PC 与 IF/ID 寄存器更新**
	- 使使用指令**重新被译码**一次
	- 使后续指令**重新被取指**一次
3. **1 拍停顿让 MEM 读出 load 的数据**
	- 之后就可以从 MEM/WB **转发到 EX**

![[Ch4-P85-带冒险检测的数据通路.webp]]

> 停顿的代价：1 拍。这条"停顿"指令在流水线图中表现为一个**气泡**（bubble），它消耗一个时隙但不产生效果。

### 4.8.9 代码调度（Code Scheduling）

**编译器重排代码**，避免"load 之后立刻用其结果的指令"。

```c
a = b + e;  c = b + f;
```

| 慢代码（13 拍） | 快代码（11 拍） |
|---|---|
| `ld x1, 0(x0)` | `ld x1, 0(x0)` |
| `ld x2, 8(x0)` | `ld x2, 8(x0)` |
| **停顿** | `ld x4, 16(x0)` |
| `add x3, x1, x2` | `add x3, x1, x2` |
| `sd x3, 24(x0)` | `sd x3, 24(x0)` |
| `ld x4, 16(x0)` | `add x5, x1, x4` |
| **停顿** | `sd x5, 32(x0)` |
| `add x5, x1, x4` | |
| `sd x5, 32(x0)` | |

> 手法：**把 `ld x4` 提前**，填补停顿的时隙。这叫"**指令调度**"（instruction scheduling），是编译器优化的基本功，**需要编译器了解流水线结构**。

**讲义例题（P87）**：

```c
a = b + c;  d = e - f;
```

| 慢代码 | 快代码 |
|---|---|
| `ld x5, b` / `ld x6, c` / `add x7,x5,x6` / `sd x7, a` / `ld x8, e` / `ld x9, f` / `sub x10,x8,x9` / `sd x10, d` | `ld x5,b` / `ld x6,c` / **`ld x8,e`** / `add x7,x5,x6` / **`ld x9,f`** / `sd x7,a` / `sub x10,x8,x9` / `sd x10,d` |

> 把两条 load 都提前到 add 之前，**load-use 间隔变成 2 拍以上**，停顿消失。

## §4.9 控制冒险（Control Hazards）

### 4.9.1 问题

- 分支决定**控制流**：取下一条指令依赖于分支结果
- 流水线**常常取到错误的指令**
	- 因为分支还在 ID 阶段，结果未知

### 4.9.2 方案一：停顿等结果（Stall on Branch）

等分支结果确定后再取下一条指令。

- 缺点：惩罚（penalty）太多。若分支在 **MEM** 阶段才判定，要 **冲刷 2 条**指令

![[Ch4-P88-分支冒险冲刷.webp]]

**冲刷（flush）= 把控制值置 0**，让已取入的指令变成 nop。

### 4.9.3 方案二：把分支判定提前到 ID

![[Ch4-P91-分支判定提前到ID.webp]]

**需要两件事提前**：

1. **计算分支目标地址**
	- 把**目标地址加法器**移到 ID 阶段
2. **评估分支条件**（更难）
	- 在 ID 阶段用**寄存器比较器**直接比较读出的两个寄存器
	- 实现：先把两组寄存器**按位异或**，再把所有结果**或**起来 —— 或门输出为 0 表示相等

**引入的复杂性**：

- ID 阶段需要新的**转发逻辑**（分支操作数可能还在流水线里）
- 可能出现**数据冒险需要停顿**：
	- 若紧邻分支的 ALU 指令产生比较操作数 → **停顿 1 拍**
	- 若紧邻分支的是 load（结果为比较操作数）→ **停顿 2 拍**

**分支相关的数据冒险总结**（P94–P96）：

| 情形 | 代价 |
|---|---|
| 比较寄存器是**第 2 或第 3 条**前驱 ALU 指令的目的 | **0 拍**（靠转发解决） |
| 比较寄存器是**紧邻前一条** ALU 指令的目的 | **1 拍**停顿 |
| 比较寄存器是**第 2 条前驱 load** 的目的 | **1 拍**停顿 |
| 比较寄存器是**紧邻前一条 load** 的目的 | **2 拍**停顿 |

### 4.9.4 方案三：分支预测（Branch Prediction）

- 更深的流水线**无法**早早确定分支结果 → 停顿惩罚不可接受
- **预测**分支结果，**只在预测错误时停顿**

**RISC-V 常用：预测"不跳转"（predict not taken）**

- 直接取分支后面的指令，**无延迟**

| 情况 | 后果 |
|---|---|
| 预测正确 | 无惩罚 |
| 预测错误 | 冲刷已取指令，转去目标地址 |

### 4.9.5 静态 vs 动态预测

| 类型 | 依据 | 例子 |
|---|---|---|
| **静态分支预测**（static） | 基于**典型分支行为** | **向后分支预测跳转**（循环回边通常跳转）；**向前分支预测不跳转**（if 通常不进入） |
| **动态分支预测**（dynamic） | 硬件**测量实际行为**，记录每条分支的**最近历史** | 假设未来延续趋势；错了就停顿重取并**更新历史** |

### 4.9.6 两位预测器（2-Bit Predictor）

![[Ch4-P99-两位分支预测器.webp]]

**一位预测器的问题**：内层循环被**误预测两次**

1. 循环最后一次迭代：预测"跳转"，实际"不跳转" → 错
2. 下次进入循环第一次迭代：预测仍为"不跳转" → 又错

**两位预测器**：**连续两次误预测才改变预测方向**

状态机（4 态）：

```
        taken                taken
   ┌──────────────┐   ┌──────────────┐
   │  Predict     │   │  Predict     │
   │  Taken (11)  │◄──│  Taken (10)  │
   └──────┬───────┘   └──────┬───────┘
          │ not taken        │ not taken
          ▼                  ▼
   ┌──────────────┐   ┌──────────────┐
   │  Predict     │   │  Predict     │
   │  NotTaken(00)│──►│  NotTaken(01)│
   └──────────────┘ taken└─────────────┘
```

> 效果：循环退出时只错**一次**（而非两次），因为状态先从 11→10，还不改变预测。

### 4.9.7 分支目标缓冲（Branch Target Buffer, BTB）

**即使有预测器，仍需算目标地址** → 跳转分支有 **1 拍惩罚**。

- **BTB = 目标地址的 Cache**
- 用**取指时的 PC** 索引
- 若**命中**且该指令是"预测跳转"的分支 → **立即从目标取指**，惩罚为 0

### 4.9.8 延迟分支（Delayed Branch）

讲义补充提到：**延迟分支**——把分支指令**前面与分支无关的指令**调到分支指令**之后**执行（填"延迟槽"delay slot）。

- 优点：延迟槽里的指令总会被执行，不浪费
- 缺点：加深流水线后延迟槽变长（多个槽要填），编译器难以调度 → **现代 ISA 基本放弃**（RISC-V 没有延迟槽）

## §4.10 异常（Exceptions）

### 4.10.1 异常与中断

| 术语 | 来源 | 例子 |
|---|---|---|
| **异常**（exception） | **CPU 内部**产生 | 未定义操作码、溢出、`syscall`、缺页、地址错 |
| **中断**（interrupt） | **外部 I/O 控制器** | 磁盘完成、网络包到达、定时器 |

> 不同 ISA 用词不同（x86 统称 "interrupt"；ARM 用 "exception"）。**不牺牲性能地处理它们很难**——因为异常是"意外的、低频的"，却要求精确。

### 4.10.2 处理异常的三件事（RISC-V）

1. **保存出错/被打断指令的 PC**
	- RISC-V：**SEPC**（Supervisor Exception Program Counter）
2. **保存问题原因**
	- RISC-V：**SCAUSE**（Supervisor Exception Cause Register），64 位，多数位未用
	- **异常码字段**（exception code）：2 = 未定义操作码，12 = 硬件故障，……
3. **跳到处理程序**（handler）
	- 假设在 `0000 0000 1C09 0000₁₆`

### 4.10.3 另一种机制：向量中断（Vectored Interrupts）

- **处理程序地址由原因决定**
- 异常向量地址 = **向量表基址寄存器 + 偏移**

| 原因 | 向量偏移 |
|---|---|
| 未定义操作码 | `00 0100 0000₂` |
| 硬件故障 | `01 1000 0000₂` |

- 向量表里的指令要么**直接处理**，要么**跳到真正的处理程序**

> 对比：**统一入口**（RISC-V 默认）vs **向量表**（x86、ARM）。前者简单，后者快（省一次跳转）。

### 4.10.4 处理程序的动作

1. 读 **cause**，转到相应处理程序
2. 决定所需动作
3. 若**可重启**（restartable）：
	- 采取纠正措施
	- 用 **SEPC** 返回程序
4. 否则：
	- 终止程序
	- 用 SEPC、SCAUSE 报告错误

### 4.10.5 流水线中的异常

- 是**另一种控制冒险**
- 设 `add x1, x2, x1` 在 **EX** 阶段发生故障：

1. **阻止 x1 被破坏**（不能让它写回）
2. **完成前面已发出的指令**（更早的指令必须生效）
3. **冲刷 add 及其后续指令**
4. **设置 SEPC 与 SCAUSE**
5. **转交控制权给 handler**

> 与"预测错误的分支"极其相似——**复用大部分硬件**（冲刷逻辑）。

### 4.10.6 异常的性质

- **可重启异常**（restartable exception）：
	- 流水线冲刷该指令
	- handler 执行后**返回该指令**
	- 该指令被**重新取指、从头执行**
- **SEPC 保存的 PC 标识"肇事指令"**

### 4.10.7 多个异常与精确性

- 流水线重叠多条指令 → 可能**同时有多个异常**
- **简单做法：处理最早指令的异常**
	- 冲刷后续指令
	- 称为"**精确异常**"（precise exceptions）
- 复杂流水线（多发射、**乱序完成** out-of-order completion）中，**保持精确异常非常困难**

**非精确异常**（imprecise exceptions）：

- 直接**停住流水线并保存状态**（含异常原因）
- 让 handler 自己判断：哪些指令出了异常、哪些要完成/冲刷
	- 可能需要"**手工完成**"（manual completion）
- **简化硬件，但复杂化 handler 软件**
- 对复杂的多发射乱序流水线**不可行**

## §4.11 通过指令实现并行（Parallelism via Instructions）

### 4.11.1 ILP 与两种加深并行的方式

**流水线本身就是"并行执行多条指令"**。要进一步提升 **ILP**（instruction-level parallelism）：

| 方式 | 做法 | 效果 |
|---|---|---|
| **加深流水线**（deeper pipeline） | 每级工作更少 → 周期更短 | 提高频率 |
| **多发射**（multiple issue） | 复制流水线级 → 多条流水线；每拍启动多条指令 | **CPI < 1** → 改用 **IPC** |

**例**：4 GHz、4 路多发射 → 峰值 **16 BIPS**，峰值 CPI = 0.25，峰值 **IPC = 4**
（但**依赖关系**会使实际值下降）

### 4.11.2 静态 vs 动态多发射

| 类型 | 谁决定发射 | 冒险处理 |
|---|---|---|
| **静态多发射**（static） | **编译器**把指令编成"发射包"（issue slot） | **编译器**检测并避免冒险 |
| **动态多发射**（dynamic） | **CPU**每拍检查指令流并选择发射 | **CPU**运行时用高级技术解决；编译器可协助重排 |

### 4.11.3 推测（Speculation）

- "**猜**"指令该做什么
- **尽早开始**操作
- **检查猜得对不对**：
	- 对 → 完成操作
	- 错 → **回滚**（roll-back）并做正确的事
- 静态与动态多发射都常用

**推测的例子**：

| 推测对象 | 回滚条件 |
|---|---|
| 分支结果 | 实际路径不同 |
| load 的值 | 该地址被更新 |

**编译器推测 vs 硬件推测**：

| 主体 | 做法 |
|---|---|
| **编译器** | 重排指令（如把 load 移到 store 前）；加入"**修正指令**"（fix-up）以从错误猜测中恢复 |
| **硬件** | 前瞻（look ahead）执行；**缓冲结果**直到确定真正需要；猜测错误时**冲刷缓冲** |

**推测与异常**：

- 若**推测执行的指令**发生异常怎么办？（如空指针检查之前的推测 load）
- **静态推测**：可在 ISA 层加"**延迟异常**"支持
- **动态推测**：**缓冲异常**直到指令真正执行（也许永远不会执行）

### 4.11.4 静态多发射：发射包与 VLIW

- 编译器把指令编成 **issue packet**（一拍内可发射的指令组）
- 由**流水线资源需求**决定
- 把发射包看成一个"**超长指令**"→ **VLIW**（Very Long Instruction Word）

**调度规则**：

- 编译器必须**消除部分/全部冒险**
- 重排指令进发射包
- **包内无依赖**；**包间可有依赖**（视 ISA 而定，编译器必须知道）
- 必要时用 **nop 填充**（pad）

### 4.11.5 RISC-V 静态双发射（Dual Issue）

**两个发射槽**：

- 一个 **ALU/branch** 指令
- 一个 **load/store** 指令
- **64 位对齐**：ALU/branch 在前，load/store 在后
- 未用的槽用 `nop` 填充

| 地址 | 指令类型 | IF | ID | EX | MEM | WB |
|---|---|---|---|---|---|---|
| n | ALU/branch | 1 | 2 | 3 | 4 | 5 |
| n+4 | Load/store | 1 | 2 | 3 | 4 | 5 |
| n+8 | ALU/branch | | 2 | 3 | 4 | 5 |
| n+12 | Load/store | | 2 | 3 | 4 | 5 |

### 4.11.6 双发射的冒险

- **EX 数据冒险**：单发射时靠转发可免停顿；双发射时**同一包内不能用 ALU 结果作 load/store 的地址**
	- 例：`add x10,x0,x1` + `ld x2,0(x10)` 必须**拆成两个包**（等效于停顿）
- **Load-use 冒险**：仍是 1 拍使用延迟，但**现在影响两条指令**
- → **需要更激进的调度**

**调度示例**：

```asm
Loop: ld   x31, 0(x20)      # 取数组元素
      add  x31, x31, x21    # 加标量
      sd   x31, 0(x20)      # 存回
      addi x20, x20, -8     # 指针递减
      blt  x22, x20, Loop   # 循环
```

| ALU/branch | Load/store | 周期 |
|---|---|---|
| `nop` | `ld x31,0(x20)` | 1 |
| `addi x20,x20,-8` | `nop` | 2 |
| `add x31,x31,x21` | `nop` | 3 |
| `blt x22,x20,Loop` | `sd x31,8(x20)` | 4 |

IPC=5/4=1.25 (峰值 IPC=2)

> 注意 `sd` 的偏移从 `0` 变成了 `8`——因为指针 `x20` 已被减 8，**用新的基址 +8 才能指向原来的位置**。这是调度时的常见技巧。

### 4.11.7 循环展开（Loop Unrolling）

- **复制循环体**，暴露更多并行性
- 减少**循环控制开销**
- **每次复制用不同的寄存器** → 称为"**寄存器重命名**"（register renaming）
- 避免**循环携带的反依赖**（loop-carried anti-dependency）
	- 即"store 后紧跟同一寄存器的 load"
	- 又叫 **名称依赖**（name dependence）—— 只是**复用了寄存器名**，不是真的数据依赖

**展开 4 次的例子**：

| ALU/branch | Load/store | 周期 |
|---|---|---|
| `addi x20,x20,-32` | `ld x28,0(x20)` | 1 |
| `nop` | `ld x29,24(x20)` | 2 |
| `add x28,x28,x21` | `ld x30,16(x20)` | 3 |
| `add x29,x29,x21` | `ld x31,8(x20)` | 4 |
| `add x30,x30,x21` | `sd x28,32(x20)` | 5 |
| `add x31,x31,x21` | `sd x29,24(x20)` | 6 |
| `nop` | `sd x30,16(x20)` | 7 |
| `blt x22,x20,Loop` | `sd x31,8(x20)` | 8 |

IPC=14/8=1.75 (接近 2，但以寄存器与代码体积为代价)

### 4.11.8 动态多发射：超标量（Superscalar）

- CPU 每拍决定发射 **0、1、2、……** 条指令
	- 同时避免结构冒险与数据冒险
- **不需要编译器调度**（但仍可协助）
- **语义正确性由 CPU 保证**

### 4.11.9 动态流水线调度（Dynamic Pipeline Scheduling）

- 允许 CPU **乱序执行**（out of order）以避免停顿
- 但**按序提交**（commit）结果到寄存器（in-order commit）

**例**：

```asm
ld   x31, 20(x21)
add  x1, x31, x2      # 等 load
sub  x23, x23, x3     # 可以先执行
andi x5, x23, 20
```

> `sub` 可以在 `add` 等 `ld` 时**先开始执行**——这就是乱序执行的价值。

![[Ch4-P128-动态调度CPU.webp]]

**关键部件**：

| 部件 | 作用 |
|---|---|
| **保留站**（reservation station） | 保存待定操作数，等所需数据 |
| **重排序缓冲**（reorder buffer） | 重排寄存器写（保证按序提交） |
| **功能单元**（functional unit） | 结果不仅写寄存器，也**送到所有等待的保留站** |
| **发射单元** | 从保留站取出操作数就绪的指令发射 |

### 4.11.10 寄存器重命名（Register Renaming）

- **保留站 + 重排序缓冲**实际上实现了寄存器重命名
- 指令发射到保留站时：
	- 若操作数**已在寄存器堆或 ROB 中** → **复制到保留站**，寄存器中的值**不再需要**，可被覆盖
	- 若操作数**还未就绪** → 将来由功能单元**直接提供给保留站**，可能**根本不需要更新寄存器**

> 效果：**打破"名称依赖"**，让更多指令并行。这是现代 CPU（x86、ARM）的核心技术。

### 4.11.11 动态调度中的推测

- **预测分支并继续发射**，直到分支结果确定才**提交**
- **Load 推测**（避免 load 与 Cache 缺失延迟）：
	- 预测**有效地址**
	- 预测**载入的值**
	- 在未完成的 store 之前 load
	- 把已存的值**旁路**给 load 单元
	- **直到推测清除才提交 load**

### 4.11.12 为什么需要动态调度（而不是全交给编译器）

1. **不是所有停顿都可预测**（如 **Cache 缺失**）
2. **无法总是绕过分支**（分支结果**动态**决定）
3. **同一 ISA 的不同实现**有不同的延迟与冒险

### 4.11.13 多发射真的有效吗？

**有效，但不如期望**：

- 程序有**真实依赖**限制 ILP
- 某些依赖**难以消除**（如**指针别名** pointer aliasing）
- 某些并行性**难以暴露**（发射窗口 window size 有限）
- **存储延迟与带宽受限** → 流水线难以填满
- **推测做得好**会有帮助

### 4.11.14 能效（Power Efficiency）

- 动态调度与推测的**复杂度需要功耗**
- **多个更简单的核可能更好**

| 微处理器 | 年份 | 主频 | 流水级数 | 发射宽度 | 乱序/推测 | 核/片 | 功耗 |
|---|---|---|---|---|---|---|---|
| Intel 486 | 1989 | 25 MHz | 5 | 1 | 否 | 1 | 5 W |
| Intel Pentium | 1993 | 66 MHz | 5 | 2 | 否 | 1 | 10 W |
| Intel Pentium Pro | 1997 | 200 MHz | 10 | 3 | 是 | 1 | 29 W |
| Intel Pentium 4 Willamette | 2001 | 2000 MHz | 22 | 3 | 是 | 1 | 75 W |

> 这张表是第 1 章"功耗墙"的证据链：**复杂度换性能，最终撞上功耗天花板** → 转向多核。

## §4.13 ILP 与矩阵乘（Putting It All Together）

**展开 4 次 + AVX-512 的矩阵乘**：

```c
#define UNROLL (4)
void dgemm(int n, double* A, double* B, double* C) {
  for (int i = 0; i < n; i += UNROLL*8)
    for (int j = 0; j < n; ++j) {
      __m512d c[UNROLL];
      for (int r = 0; r < UNROLL; r++)
        c[r] = _mm512_load_pd(C+i+r*8+j*n);
      for (int k = 0; k < n; k++) {
        __m512d bb = _mm512_broadcastsd_pd(_mm_load_sd(B+j*n+k));
        for (int r = 0; r < UNROLL; r++)
          c[r] = _mm512_fmadd_pd(_mm512_load_pd(A+n*k+r*8+i), bb, c[r]);
      }
      for (int r = 0; r < UNROLL; r++)
        _mm512_store_pd(C+i+r*8+j*n, c[r]);
    }
}
```

**对应汇编（关键 4 条 FMA 并行）**：

```asm
vmovapd      (%r11),%zmm4          # 装入 8 个 C 元素
vmovapd      0x20(%r11),%zmm3      # 再装 8 个
vmovapd      0x40(%r11),%zmm2      # 再装 8 个
vmovapd      0x60(%r11),%zmm1      # 再装 8 个
vbroadcastsd (%rax,%r8,8),%zmm0    # B 的一个元素复制 8 份
vfmadd231pd  (%rcx),%zmm0,%zmm4    # 4 条 FMA 互相独立 → ILP
vfmadd231pd  0x20(%rcx),%zmm0,%zmm3
...
```

> **为什么展开能提速？** 因为 4 条 FMA 之间**没有依赖**，CPU 可以同时发射/乱序执行，把功能单元喂饱。同时 `zmm` 一次算 8 个 double（SIMD，第 3 章）。
> **两个正交的并行维度**：**SIMD（数据级）** × **ILP（指令级）**。

## §4.14 谬误与陷阱（Fallacies and Pitfalls）

### 谬误

**1. "流水线很简单"**

- 基本思想确实简单（把工作分段重叠）
- **魔鬼在细节**（the devil is in the details）：如检测数据冒险、处理异常精确性

**2. "流水线与技术无关"**

- 那为什么不是一直都有流水线？
- **更多晶体管**才使更先进的技术可行
- **流水线相关的 ISA 设计要考虑技术趋势**（如谓词指令 predicated instructions）

### 陷阱

**糟糕的 ISA 设计会让流水线更难做**：

| 例子 | 问题 |
|---|---|
| 复杂指令集（VAX、IA-32） | 要让流水线工作需付出**巨大开销**；IA-32 用**微操作**（micro-op）方案 |
| 复杂寻址方式 | **寄存器更新副作用**、**内存间接寻址**（一次指令多次访存） |
| **延迟分支**（delayed branches） | 先进流水线的**延迟槽很长**，编译器难以填满 |

## §4.15 结论（Concluding Remarks）

- **ISA 影响数据通路与控制的设计**
- **数据通路与控制反过来影响 ISA 的设计**（双向约束）
- 流水线通过**并行**提升**指令吞吐率**
	- 每秒完成的指令更多
	- **单条指令的延迟不减少**
- **三类冒险**：结构、数据、控制
- **多发射与动态调度（ILP）**
	- **依赖关系限制可达的并行度**
	- **复杂度导致功耗墙**

## §4.17 易错点清单

1. **WB 阶段必须用 MEM/WB 中的 rd**，不能用 IF/ID 的字段（P59 的经典错误）
2. **转发只对"会写寄存器且 rd ≠ x0"的指令生效**
3. **双重冒险要取"最近"的结果**（EX/MEM 优先于 MEM/WB）
4. **Load-use **不能**靠转发解决**，必须停 1 拍（"不能向未来转发"）
5. **停顿的实现**：清 ID/EX 控制 + **冻结 PC 与 IF/ID**（两者都要）
6. **分支判定提前到 ID 会引入新的数据冒险**（紧邻 ALU 停 1 拍，紧邻 load 停 2 拍）
7. **流水线提升吞吐率，不降低单条指令延迟**
8. **一位预测器在循环退出/重入时错两次**，两位预测器只错一次
9. **结构冒险**：单存储器必须拆成指令/数据两个（或两个 Cache）
10. **异常要"完成更早的指令、冲刷更晚的指令"** → 精确异常
11. **静态双发射同一包内不能用 ALU 结果作访存地址**
12. **循环展开要换寄存器名**（否则引入名称依赖）
13. **推测执行的指令若产生异常**，要能**延迟/缓冲**该异常
14. 单周期实现的时钟周期由**最长指令**决定，违反"让常见情况变快"
