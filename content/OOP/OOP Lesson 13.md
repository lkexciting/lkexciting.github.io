# Exceptions (异常)
- **Run-time error (运行时错误)**
	- C++ 的基本哲学是“形式错误的代码将不会被运行”（指编译期检查）。    
	- 但在运行时 (run-time) 总会有事情发生。    
	- 处理未来运行中所有可能的情况是非常重要的。
- **Read a file (读取文件)**![[Pasted image 20251215143207.png]]
	- 这是一个典型的操作流程，每一步都可能出错：
		- 打开文件；    
		- 确定文件大小；    
		- 分配相应大小的内存；    
		- 将文件读入内存；    
		- 关闭文件。
- **Working with exception (使用异常)**![[Pasted image 20251215143335.png]]
	- try { ... } 块：包含所有正常的业务逻辑（打开、读取、关闭），代码清晰流畅。    
	- catch (...) { ... } 块：分别处理不同类型的错误（如 fileOpenFailed, memoryAllocationFailed 等）。    
	- **优点：** 正常逻辑与错误处理分离。
- **Example: Vector**![[Pasted image 20251215143704.png]]
	- Problem：
		- 针对 operator\[] 的实现提出问题：
			- **如果索引无效（越界），\[] 运算符该做什么？**    
			- **选择 1)** 返回随机的内存对象。    
			    - return m_elements\[idx]; (不做检查，直接访问)。        
			    - 这是非常危险的。
			- **选择 2)** 返回一个特殊的错误值。    
			    - 代码演示：如果越界，new 一个带有 "magic value" 的对象并返回。        
			    - **缺点：** 这叫 "throws the baby out with the bath water"（倒洗澡水把孩子也倒了，即得不偿失）。        
			    - 原因：像 x = v\[2] + v\[4]; 这样的代码变得不再安全，因为你不知道返回的是正常值还是错误标记值。
			- **选择 3)** 直接死掉 (Just die!)。    
			    - 调用 exit(22); ==强行终止程序==。        
			- **选择 4)** ==优雅==地死掉 (带尸检报告)。    
			    - 使用 assert(idx >= 0 && ...) 断言。只在 Debug 模式有效，Release 模式通常会被忽略。
- **How to raise an exception (如何引发/抛出异常)**![[Pasted image 20251215144337.png]]
	- 在 operator\[] 中进行边界检查。    
	- 使用==关键字== **throw**。    
	- throw \<\<something>>; (在这里抛出某个东西，程序执行在此处中断并向上传播)。

- **What about your caller? (你的调用者怎么处理？)
	- **情况 1)** 不在乎 (Doesn't care)。    **![[Pasted image 20251215145324.png]]
	    - 代码根本不怀疑会有问题。        
	    - int i = v\[42]; (越界)。        
	    - 结果：控制权永远不会到达 return 语句。程序会因未捕获的异常而终止。
	- **情况 2)** 非常在乎 (Cares deeply)。   ![[Pasted image 20251215145340.png]] 
	    - 使用 try { ... } 包裹调用。        
	    - 使用 catch (VectorIndexError& e) 捕获特定异常。        
	    - 调用 e.diagnostic() 处理错误。        
	    - **结果：** 异常在此处停止传播，程序继续执行 catch 块之后的代码。
	- **情况 3)** 有点兴趣 (Mildly interested)。![[Pasted image 20251215145355.png]]    
	    - 捕获异常，做一些处理（比如打印日志 cout << err;）。        
	    - 然后使用 **throw;** (不带参数)。        
	    - **作用：** 重新抛出当前正在处理的异常（Propagate the exception），让外层继续处理。
	- **情况 4)** 不在乎细节 (Doesn't care about the particulars)。  ![[Pasted image 20251215145404.png]]  
	    - 使用 **catch (...)** (三个点，Ellipsis)。        
	    - **作用：** 捕获**所有**类型的异常。通常作为最后一道防线。
- **What happened? (发生了什么？)**![[Pasted image 20251215145601.png]]
	- 展示了异常的传播路径（Stack Unwinding 栈展开）：
		1. operator\[]() 抛出异常。    
		2. func() 没有处理，向上传播。    
		3. Outer2() 捕获并重新抛出。    
		4. Outer3() 最终捕获。  
	    - 红色箭头表示控制流直接跳跃，==忽略了正常的返回路径==。
- **Review (复习/流程)**
	- 异常处理的逻辑流程：
		- 周围有 try 块吗？    
		    - NO: 离开当前作用域（触发栈展开 stack unwinding）。        
		        - 是方法体（函数）吗？            
		            - YES: 返回给调用者，然后回到第1步。                
		            - NO: 终止程序 (terminate program)。                
		    - YES: 尝试匹配 catch。        
		        - 匹配成功？            
		            - YES: 执行 catch 子句，然后跳转到 try 块之后的语句执行。            
		            - NO: 继续隐式地抛出，回到第1步。
	- **throw 语句引发异常**    
	    - 控制流传播回该异常的第一个处理器        
	    - 传播遵循调用链        
	    - 栈上的对象被妥善销毁        
	- **throw 表达式;**    
	    - 抛出值用于匹配        
	- **throw;**    
	    - 重新引发正在处理的异常        
	    - 仅在处理器内有效
- **Try 块**  
    **try { ...}**  
    **catch { ...}**  
    **catch { ...}**    
	- 建立任意数量的处理器    
	- 如果不使用任何处理器则不需要    
	- 显示你期望处理异常的地方    
	- 消耗计算周期
- **异常处理器**
	- 通过类型选择异常    
	- 可以重新引发异常    
	- 两种形式  
	    **catch (某种类型 变量) { // 处理器代码 }**  
	    **catch (...) { // 处理器代码 }**    
	- 接受单个参数（类似于形式参数）
- **选择一个处理器**
	- 可以有任意数量的处理器    
	- 处理器按出现顺序进行检查  
	    **1. 检查精确匹配**  
	    **2. 应用基类转换**  
	    (引用和指针类型)  
	    **3. 全捕获处理器 (...)**  
	    **继承可用于组织异常结构**

- **异常规范Exception specifications**
	- 指定函数是否可能抛出异常。    
	- 是函数类型的一部分，但不是函数签名的一部分。
		```c++
		void abc(int a) noexcept 
		{ 
		// 承诺不抛出异常 ... 
		}
		```
	- 可能不会在编译时检查，但被编译器利用以启用某些优化。    
	- 在运行时：  
	    – 如果抛出了异常，则调用 std::terminate。
	    
	- 声明函数可能引发哪些异常    
	- 是函数原型的一部分
		```cpp
		void abc(int a) : throw(MathErr) 
		{ // 声明抛出数学错误
		...
		}
		```
	- 编译时不检查    
	- 在运行时：  
	    – 如果列表之外的异常传播出来，则引发意外异常    
	- throw(可选类型列表) 规范在 C++11 中被弃用并在 C++17 中移除，除了 throw()    
	- throw() 是 noexcept(true) 的别名
- **设计考量**
	- 异常应该指示错误    
	- 这里是一个不恰当的使用：
		```cpp
		try 
		{
			for (;;) 
			{
				p = list.next() // 列表下一个
				// ...
			}
		} 
		catch (List::end_of_list) 
		{ // 用异常处理循环结束
		// 在此处理列表结束
		}
		```
	- 不要用异常代替好的设计!
		```cpp
		void func() 
		{
			File f;
			if (f.open("某个文件")) 
			{
				try 
				{
					// 使用 f 工作
				} 
				catch (...) 
				{
					f.close() // 手动关闭
				}
			}
		}
		```
	- 这是使用析构函数的好地方
		```cpp
		void func() 
		{
			File f("某个文件");
			// 假设析构函数负责关闭 f
			// 即使引发异常，f 仍将被关闭！
			if (f.ok()){			
			}
		}
		```
- **总结**![[Pasted image 20251222135347.png]]
	- 错误恢复是一个困难的设计问题。    
	- 所有子系统都需要来自其客户的帮助来处理异常情况。    
	- 异常提供了这种机制：  
	    – 动态传播  
	    – 栈上对象被妥善销毁  
	    – 起到终止有问题函数的作用    
	- 另一个重要用途：  
	    – 无法完成工作的构造函数    
- **构造函数失败**
	- 不可能有返回值。    
	- 使用“未初始化标志”。    
	- 将工作推迟到 init() 函数。  
	    **更好：抛出一个异常。**
	- **如果你的构造函数无法完成，抛出一个异常。**
	- 对象的析构函数将不会被调用。    
	- 在抛出前手动清理已分配的资源，否则会发生内存泄漏。
- **两阶段构造**
	- 在构造函数中做正常工作：  
	    – 初始化所有成员对象  
	    – 初始化所有原始成员  
	    – 将所有指针初始化为 0  
	    – **绝不**请求任何资源：    
	    - 文件        
	    - 网络连接        
	    - 内存        
	- 在 Init() 中做额外的初始化工作
- **使用智能指针**
	- 标准库唯一指针 (std::unique_ptr)    
	- 标准库共享指针 (std::shared_ptr)    
	- …    
	- 析构函数在销毁时会删除原生指针。  
	    **参见 ExceptionCtor.cpp**
- **异常与析构函数**
	- **析构函数在以下情况下被调用：**
		- 正常调用结束：对象退出作用域。    
		- 抛出异常：“栈解旋”在对象退出作用域时对其调用析构函数。  
		    **如果在析构函数中抛出异常会发生什么？**
	- **在本身因异常而被调用的析构函数中抛出异常将引发 std::terminate()。**
		- 应该避免允许异常逃离析构函数，绝不要抛出它！

- **异常总结**
	- 在设计早期制定错误处理策略。    
	- 避免过度使用 try/catch 块。使用对象来获取/释放资源。    
	- 在局部控制结构足够的地方不要使用异常。    
	- 并非每个函数都能处理每个错误。    
	- 为主要接口使用异常规范。    
	- 库代码不应决定终止程序。抛出异常并让调用者决定。
