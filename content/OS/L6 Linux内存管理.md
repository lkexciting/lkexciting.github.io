# L6 Linux内存管理

> 来源：`L6 Linux内存管理.pdf`，85 页。前置 [[OS/第 8 章 · 主存管理|Chapter 8]] 与 [[OS/第 9 章 · 虚拟内存|Chapter 9]]。课件主要以 IA-32、旧式 VMA 结构及历史 Linux 实现讲解；3G/1G、页表层数、函数名和内核字段不作为跨版本不变量。

## 1. 从进程地址到物理页（Address Spaces）

课件 3–10 页。IA-32 示例中，逻辑地址经分段变成线性地址，再经分页映射物理地址。平坦分段让逻辑地址数值常与线性地址数值一致，但概念层次仍不同。

4 GiB 虚拟空间不等于机器装有 4 GiB 物理内存。课件低 3 GiB 用户空间、高 1 GiB 内核空间的划分是其配置，内核空间可见也不表示用户态有访问权限。

“内核虚拟地址减 PAGE_OFFSET 得物理地址”只适用于相应直接映射范围，不能用于所有 vmalloc、用户指针或所有架构。

## 2. mm_struct 与 VMA（Virtual Memory Area）

课件 11–28 页。

- `mm_struct`：描述地址空间整体，关联页表、代码/数据/堆栈边界及映射区域。
- `vm_area_struct`：描述一段连续虚拟地址区间，记录访问权限、映射属性和后备对象等。
- **VMA（Virtual Memory Area）** 不是一页：一个 VMA 可以跨许多页，且其中页面可能尚未分配物理帧。

![课件地址空间与虚拟内存区域](OS/pictures/L6%20Linux%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86/%E5%AD%A3%E8%80%81%E5%B8%88-p018.png)

课件用链表和红黑树组织 VMA：前者便于按地址遍历，后者便于查找；仅说明该版本机制，不推出全部 Linux 内核永远用同一数据结构。

`mmap` 类操作建立虚拟映射关系，不意味着调用返回前已经把整个映射对应的文件读入 RAM。fork 可复制映射描述与页表管理关系，并结合 COW 共享物理内容。

## 3. 页表与地址换算（Page Tables and Translation）

课件 29–36 页。32 位、4 KiB 页的示例地址拆分为 `10 位目录索引 + 10 位页表索引 + 12 位偏移`。

![课件 IA-32 二级转换](OS/pictures/L6%20Linux%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86/%E5%AD%A3%E8%80%81%E5%B8%88-p036.png)

自编例：VA=0x12345678：

1. 页目录索引 `VA >> 22 = 0x48 = 72`。
2. 页表索引 `(VA >> 12) & 0x3ff = 0x345 = 837`。
3. 偏移 `VA & 0xfff = 0x678 = 1656`。
4. 查两级表得到 PFN 后，物理地址 `PFN×4096+0x678`。

Linux 的软件抽象页表层次可以与硬件层数不同，某层可折叠；课件“三层软件结构”和 IA-32 的某种“两层硬件分页”不必矛盾。

PTE 的存在位、读写位和用户/内核权限决定映射状态；设置存在位不等于所有读写都合法。

## 4. 缺页异常（Page-Fault Handling）

课件 37–44 页。查地址、查 VMA、查权限、区分未驻留与写保护，再选择调页、零填充、COW 或错误路径。

![课件缺页处理分支](OS/pictures/L6%20Linux%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86/%E5%AD%A3%E8%80%81%E5%B8%88-p038.png)

- 无合法映射：不能凭空建立任意可访问页。
- 合法匿名区首次使用：可能分配并零填充物理页。
- 文件映射尚未驻留：需要取得文件对应内容。
- COW 写保护：需要私有化后允许写，原共享物理页可能本来就在内存。

课件 `do_page_fault`、CR2 寄存器与函数路径按其 x86 示例理解；不要把所有 Page Fault 都归为一次 swap-in。

## 5. 回收、交换与 kswapd（Reclaim and Swap）

课件 45–53 页。内存紧张时回收可重建内容、必要时写回脏页或使用交换区，使物理帧可供其他需求使用。

**交换槽（Swap Slot）** 保存被换出的相应页内容；**页框（Page Frame）** 是 RAM 中容纳页的位置，二者不能混称。

`kswapd` 是背景回收路径中的守护实体示例。不同版本的扫描策略和触发方式不同；课件“定期检查”的简述不能代替具体实现的完整触发条件。

干净文件页可丢弃后从文件恢复，不要求所有被回收页都写入 swap。页引用位、修改状态和访问历史参与选择；这些机制近似利用局部性，不代表内核保存了精确的所有历史访问顺序。

## 6. 物理页、区域与伙伴系统（Pages, Zones and Buddy）

课件 54–76 页。`struct page` 描述物理页管理信息，不是把一整页用户数据直接放进该结构体；内存区域（Zone）用来表达硬件可访问范围等分配约束。

**伙伴系统（Buddy System）** 按 order 管理 `2^order` 页的连续块。需要 3 页，最小可容纳块为 4 页（order=2）。需 9 页，则至少 16 页（order=4）。

![课件 1 MiB 伙伴拆分与回收实例](OS/pictures/L6%20Linux%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86/%E5%AD%A3%E8%80%81%E5%B8%88-p063.png)

### 6.1 按图逐步算

图中申请 A=70 KiB、B=35 KiB、C=80 KiB、D=60 KiB：

| 请求 | 实际分配块 | 内部多分配 |
| --- | ---: | ---: |
| A=70 KiB | 128 KiB | 58 KiB |
| B=35 KiB | 64 KiB | 29 KiB |
| C=80 KiB | 128 KiB | 48 KiB |
| D=60 KiB | 64 KiB | 4 KiB |

A 释放时，其另一半区域被 B/D 等使用，不能立即合成 256 KiB。B 与 D 都释放后，这两个 64 KiB 伙伴可合成 128 KiB，再与 A 所在空闲 128 KiB 合成 256 KiB。最后 C 释放后，按伙伴关系逐级合并回 1 MiB。

### 6.2 谁是伙伴

补充：在同一对齐基准的页号模型下，order=k 块的伙伴起始 PFN 可用 `PFN XOR 2^k` 求得。例：order=2 时，8 的伙伴是 12；4 的伙伴是 0，而不是相邻的 8。

合并要求：同阶、确为伙伴、对方空闲，且满足管理区域边界。两个相邻同大小块不一定是伙伴。

课件 69–70 页的“申请3帧、分配8/9/10帧”图应区分为分配与余块管理示意，不应据此说标准 order 接口直接返回任意 3 页大小块。`alloc_pages(order)` 按 `2^order` 页请求；题目若采用拆分后返还余页的变体，应另写规则。

## 7. 小对象与 Slab（Small Objects and Slab）

课件 77–83 页。只按整页给几十字节的结构分配，浪费很大；Slab 在页之上组织同类型对象缓存。

![课件对象缓存层次](OS/pictures/L6%20Linux%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86/%E5%AD%A3%E8%80%81%E5%B8%88-p079.png)

概念层次：**页分配器提供页 → slab 组织页 → cache 管理某类对象 → 分配/释放单个对象**。`kmem_cache_create/alloc/free` 表达对象缓存生命周期；课件中的扩容/回收内部接口未必适用于其他版本。

区别：`kmalloc` 类请求常用于内核小块内存；`vmalloc` 类映射可提供虚拟连续而物理不必连续的空间。连续的虚拟地址不能直接推断可供设备使用的一段连续物理内存。

## 8. 自测与来源索引（Review）

1. 一个合法 VMA 覆盖 1 MiB，是否一定占 1 MiB 物理内存？
2. 4 KiB 页，order=3，分配多少字节？
3. 相邻的 4 页块起始于 4 和 8，能直接作为伙伴合并吗？
4. COW 写异常一定需要先从磁盘读页吗？

> [!success]- 答案
> 1. 不一定，映射与实际驻留不同。
> 2. 8 页，共 32 KiB。
> 3. 不能，4 的同阶伙伴是 0，8 的是 12。
> 4. 不一定，原页可能已驻留，仅需复制或更新权限。
