# Chapter 5：CPU Scheduling（CPU 调度）

> 本章从执行时间、到达时间和调度规则出发，推导甘特图、等待时间、周转时间和响应时间。算例默认单 CPU，除非另有说明均忽略切换开销；历史系统实例用于解释机制，不代表现代系统的统一实现。

> [!abstract] 这一章到底在学什么？
> 假设只有一个 CPU，却有很多进程都想运行。操作系统必须回答：**下一刻让谁用 CPU？可以用多久？什么情况下要把 CPU 交给别人？**
> 本章先定义“调得好”的标准，再学习不同的选择规则，最后扩展到多处理器、实时系统和线程。

## 1. 先建立直觉：进程为什么需要调度

### 1.1 调度的资源和对象

| 问题 | 答案 |
| --- | --- |
| 分配什么资源？ | CPU 的执行时间 |
| 在谁之间分配？ | 已就绪的进程（Process）或线程（Thread），取决于系统实现 |
| 从哪里挑选？ | 就绪队列（Ready Queue） |
| 为什么不能随便挑？ | 会影响等待、交互响应、公平性以及整体效率 |

“一个进程在内存里”不等于“它现在就可以运行”。等待磁盘读完的进程还没有准备好，不能直接拿来执行。

![进程状态转换](OS/pictures/Chapter%205/slide-02-fig-1.webp)

**读图顺序：**

1. `new → ready`：进程被接纳，进入就绪队列。
2. `ready → running`：调度器选中它，分派程序把 CPU 交给它。
3. `running → waiting`：发起 I/O，或等待某个事件，暂时无法继续。
4. `waiting → ready`：事件完成，重新具备运行条件。
5. `running → ready`：CPU 被抢占，例如时间片用完。
6. `running → terminated`：执行结束。

> [!important] ready 和 waiting 一定要分清
> **ready：万事俱备，只差 CPU。**
> **waiting/blocked：还差某个事件，即使给 CPU 也无法继续。**
> 后面计算的 waiting time，特指在就绪队列中等待的时间。

### 1.2 CPU burst 与 I/O burst

一个进程通常不是从头到尾一直计算，而是交替经历：

```text
CPU 计算 → 等待 I/O → CPU 计算 → 等待 I/O → …… → 结束
```

![CPU 与 I/O 交替](OS/pictures/Chapter%205/slide-04-fig-1.webp)

- **CPU burst**：连续使用 CPU 的一段时间。
- **I/O burst**：进行或等待 I/O 的一段时间。
- **CPU-bound**：CPU 密集型，通常 CPU burst 较长，例如大量数值运算。
- **I/O-bound**：I/O 密集型，通常频繁执行较短的 CPU burst，然后又等待 I/O。

**为什么多道程序设计（Multiprogramming）可以提高 CPU 利用率（CPU Utilization）？**

如果只有进程 A，A 等磁盘时 CPU 可能闲着。如果还有已就绪的 B，操作系统可以让 B 在这段时间运行。因此，多道程序通过交错执行，减少 CPU 因单个进程等待 I/O 而空闲的机会。

### 1.3 CPU burst 的分布告诉我们什么

![CPU burst 长度的分布](OS/pictures/Chapter%205/slide-05-fig-1.webp)

横轴是 CPU burst 的持续时间，纵轴是出现频数。图中短 burst 多，长 burst 少。

由此得到两个设计提示：

- 短期调度可能很频繁，**调度器本身必须快**。
- 优先照顾短 burst，可能让很多进程很快完成一次计算或获得交互响应。

## 2. 调度在什么时候发生？谁做决定？

### 2.1 四类调度时机

| 编号 | 状态变化 | 例子 | 是否必须从当前进程手里抢 CPU？ |
| --- | --- | --- | --- |
| 1 | running → waiting | 请求 I/O、等待事件 | 无须抢占，当前进程已主动放弃运行 |
| 2 | running → ready | 时间片用完、发生抢占 | 属于抢占情形 |
| 3 | waiting → ready | I/O 完成，某进程被唤醒 | 可以触发抢占，但是否立即抢占取决于策略 |
| 4 | running → terminated | 进程结束 | 无须抢占，原进程已经结束 |

> [!warning] 不要机械理解示例的简写
> 仅在 1、4 这类时机重新分配 CPU，是典型的非抢占式调度。允许在 2、3 这类情况下重新选择，则可以实现抢占式调度。
> **I/O 完成只表示进程重新就绪，并不表示它一定立刻获得 CPU。**

### 2.2 抢占式与非抢占式

**非抢占式调度（Nonpreemptive Scheduling）：**一个进程拿到 CPU 后，只要它没有阻塞或结束，就继续运行当前 CPU burst。别人更紧急、更短，也不能强行赶它下来。

**抢占式调度（Preemptive Scheduling）：**系统可以在进程仍能继续运行时，收回 CPU 并交给另一个进程。例如，RR 在时间片到期时抢占，SRTF 在有更短剩余时间的进程到达时抢占。

抢占有助于响应，但需要保存和恢复上下文，也要处理共享数据更新期间被打断的问题。

### 2.3 Scheduler 与 Dispatcher

| 组件 | 职责 | 类比 |
| --- | --- | --- |
| CPU scheduler，短期调度器 | 决定下一个运行谁 | 老师点名 |
| Dispatcher，分派程序 | 把 CPU 控制权实际交过去 | 被点到的人走上讲台开始讲 |

分派通常包括：

1. 保存当前执行上下文（Execution Context），恢复新进程的上下文。
2. 在需要时切换到用户态（User Mode）。
3. 从新进程应继续的位置恢复执行。

不是每次调度决策都会切换到不同进程；如果仍选中原进程，就不一定需要完整的进程上下文切换（Context Switch）。

![分派程序与上下文切换](OS/pictures/Chapter%205/slide-07-fig-1.webp)

**分派延迟（Dispatch Latency）：**从停止一个执行者到让另一个执行者开始运行所需的时间。它越大，调度额外开销越明显，实时任务的响应也越难保证。

进一步指出，实时场景中的冲突处理可能涉及：使正在内核（Kernel）中运行的低优先级执行者能够被抢占，以及等待或促使其释放高优先级任务需要的资源。这部分延迟不能简单等同于几个寄存器（Register）的保存时间。

## 3. 五大指标：先会算，再比较算法

### 3.1 用一张时间轴记住三个“时间”

```text
到达 A ── 就绪等待 ── 首次运行 S ── 执行/再次等待/可能 I/O ── 完成 C
       <── 响应时间 R ──>
       <──────────────── 周转时间 T ─────────────────>
```

统一记号：

| 记号 | 含义 |
| --- | --- |
| Aᵢ | arrival time，到达时间 |
| Bᵢ | CPU burst / 本题所需 CPU 服务时间 |
| Sᵢ | 第一次开始使用 CPU 的时刻 |
| Cᵢ | completion time，完成时刻 |
| Tᵢ | turnaround time，周转时间 |
| Wᵢ | waiting time，在就绪队列等待的总时间 |
| Rᵢ | response time，响应时间 |

### 3.2 定义与优化方向

| 指标 | 含义与公式 | 通常希望 |
| --- | --- | --- |
| CPU utilization，CPU 利用率 | CPU 忙碌时间 / 观察总时间 | 大 |
| Throughput，吞吐量 | 观察期内完成的进程数 / 观察时间 | 大 |
| Turnaround time，周转时间 | 从到达到最终完成，Tᵢ = Cᵢ − Aᵢ | 小 |
| Waiting time，等待时间 | 所有就绪等待片段之和 | 小 |
| Response time，响应时间 | 从请求提交到首次响应；CPU 调度算例通常用 Rᵢ = Sᵢ − Aᵢ | 小 |

需要注意 response 是 **first response**，不是最终结果全部输出。做题时通常把第一次得到 CPU 当作响应时刻；真实应用中，第一次运行到实际生成响应之间仍可能有执行时间。

对只有一个 CPU burst、无 I/O 的常见算例：

T_i=C_i-A_i, W_i=T_i-B_i=C_i-A_i-B_i, R_i=S_i-A_i

如果题目包含 I/O，周转时间还包括 I/O 等待，不能直接用“周转减 CPU 时间”当作就绪等待时间。

### 3.3 带权周转时间（Normalized Turnaround Time）

还可使用“带权周转时间”，用于观察相对于自身服务需求的耗时：

带权周转时间_i=T_i/B_i

例如，一个需要 2 单位 CPU 时间的任务，8 单位时间后才完成，带权周转时间是 4。另一个需要 20 单位的任务，26 单位后完成，带权周转时间是 1.3。后者绝对周转更长，但相对其工作量的额外等待较少。

**平均带权周转时间要逐个求比值再平均，不能直接用总周转时间除以总服务时间。**

### 3.4 一个最小算例

A 在 t=2 到达，t=5 首次运行，运行 2 单位后被抢占，t=10 再运行 3 单位并完成。

```text
2────等待────5──运行──7────等待────10───运行───13
```

- A = 2，S = 5，C = 13，B = 2 + 3 = 5。
- 周转 T = 13 − 2 = **11**。
- 响应 R = 5 − 2 = **3**。
- 等待 W = (5 − 2) + (10 − 7) = **6**。
- 校验：T − B = 11 − 5 = **6**。

> [!important] 高频区别
> 非抢占、单 CPU burst 算例中，等待时间通常等于响应时间。
> 抢占式算例中，进程得到第一次响应后还可能继续排队，所以二者通常不同。

## 4. FCFS：先来先服务（First-Come, First-Served）

**先来先服务（First-Come, First-Served，FCFS）：谁先进入就绪队列，谁先运行。**通常用先进先出（First-In, First-Out，FIFO）队列实现，是非抢占式算法。

### 4.1 例题：长任务先到

假设三个进程都在 t=0 已就绪，按 P1、P2、P3 的顺序入队：

| 进程 | CPU 服务时间 B |
| --- | ---: |
| P1 | 24 |
| P2 | 3 |
| P3 | 3 |

```text
0                  24   27   30
|        P1         | P2 | P3 |
```

读甘特图（Gantt Chart）时，**边界数字表示时刻，段的长度才是运行时间**。

| 进程 | 首次运行 S | 完成 C | 等待 W = C − A − B | 周转 T = C − A |
| --- | ---: | ---: | ---: | ---: |
| P1 | 0 | 24 | 0 | 24 |
| P2 | 24 | 27 | 24 | 27 |
| P3 | 27 | 30 | 27 | 30 |

W=(0+24+27)/3=17,
T=(24+27+30)/3=27

吞吐量为 3/30 = 0.1 个进程/时间单位。忽略开销且 CPU 全程工作时，CPU 利用率为 100%。

### 4.2 同样的任务，改变入队次序

换成 P2、P3、P1：

```text
0    3    6                  30
| P2 | P3 |        P1         |
```

- P2 等待 0，P3 等待 3，P1 等待 6。
- 平均等待 = (0 + 3 + 6)/3 = **3**。
- 周转时间分别为 P2=3、P3=6、P1=30，平均为 **13**。
- 总服务时间仍为 30，吞吐量仍为 0.1。

**结论：同样的工作量，仅仅改变顺序，就能显著改变平均等待时间；吞吐量却不一定改变。**

### 4.3 Convoy effect：护航效应

想象一个长 CPU burst 排在许多短任务前面。短任务只能一起等，像很多小车跟在慢车后面。

如果这些短任务本来要频繁发起 I/O，它们拿不到 CPU，就无法及时提交 I/O，请求不足时设备可能空闲。等长任务终于去做 I/O，短任务很快各自提交 I/O 后又阻塞，CPU 也可能出现空闲。

FCFS 的特点：实现简单、按到达顺序公平；但对短任务和交互任务可能很不友好。典型有限服务、持续前进的 FIFO 队列不会让后来者插队造成饥饿，但等待仍可能很长。

## 5. SJF 与 SRTF：优先服务短任务（Shortest Job / Remaining Time First）

### 5.1 先分清两个版本

| 算法 | 比较什么 | 能否抢占 |
| --- | --- | --- |
| SJF，Shortest-Job-First | 已就绪进程的下一段 CPU burst 长度 | 通常指非抢占版本 |
| SRTF，Shortest-Remaining-Time-First | 已就绪进程当前 burst 的剩余时间 | 可以抢占 |

这里的“短”通常指**下一段 CPU burst**，不是整个程序从创建到退出的总寿命。

### 5.2 非抢占 SJF：一步步算

的数据：

| 进程 | 到达 A | CPU 服务 B |
| --- | ---: | ---: |
| P1 | 0 | 7 |
| P2 | 2 | 4 |
| P3 | 4 | 1 |
| P4 | 5 | 4 |

**第 1 步，t=0：**只有 P1 到达。即使知道 P3 以后会到，也不能把未来任务当成当前可选任务。运行 P1。

**第 2 步，t=2、4、5：**其他任务陆续到达，但 SJF 非抢占，P1 继续运行。

**第 3 步，t=7：**P1 完成，比较 P2=4、P3=1、P4=4，选择 P3。

**第 4 步，t=8：**P2 与 P4 一样长，按先到先服务打破平局，先运行 P2。

**第 5 步，t=12：**运行 P4，t=16 全部结束。

```text
0          7   8       12      16
|    P1    |P3 |   P2   |   P4   |
```

| 进程 | S | C | T = C − A | W = T − B | R = S − A |
| --- | ---: | ---: | ---: | ---: | ---: |
| P1 | 0 | 7 | 7 | 0 | 0 |
| P2 | 8 | 12 | 10 | 6 | 6 |
| P3 | 7 | 8 | 4 | 3 | 3 |
| P4 | 12 | 16 | 11 | 7 | 7 |

平均等待 = **4**，平均周转 = **8**，平均响应 = **4**。

### 5.3 抢占 SRTF：每次到达都重新比较剩余量

使用同一组数据：

| 时刻 | 当前状态 | 决策 |
| --- | --- | --- |
| 0 | 只有 P1，剩余 7 | P1 运行 |
| 2 | P1 已跑 2，剩余 5；P2 到达，需要 4 | 4 < 5，P2 抢占 |
| 4 | P2 已跑 2，剩余 2；P3 到达，需要 1 | 1 < 2，P3 抢占 |
| 5 | P3 完成，P4 到达；P1=5、P2=2、P4=4 | 选择 P2 |
| 7 | P2 完成；P1=5、P4=4 | 选择 P4 |
| 11 | P4 完成，P1 剩余 5 | P1 运行至 16 |

```text
0    2    4   5    7       11       16
| P1 | P2 |P3 | P2 |   P4   |   P1   |
```

| 进程 | 首次运行 S | 完成 C | 周转 T | 等待 W | 响应 R |
| --- | ---: | ---: | ---: | ---: | ---: |
| P1 | 0 | 16 | 16 | 9 | 0 |
| P2 | 2 | 7 | 5 | 1 | 0 |
| P3 | 4 | 5 | 1 | 0 | 0 |
| P4 | 7 | 11 | 6 | 2 | 2 |

W=(9+1+0+2)/4=3,
T=7, R=0.5

单独检查 P1：它第一次在 t=0 就运行，所以响应时间为 0；但被抢占后从 t=2 等到 t=11，等待时间为 9。这正是“等待不等于响应”的例子。

### 5.4 为什么短任务优先能减少平均等待

**理解补充：交换论证（Exchange Argument）。**假设 A、B 同时可运行，服务时间分别是 a、b，且 a > b。先忽略共同的前置等待时间。

- A 后 B：两人的等待之和是 0 + a = a。
- B 后 A：两人的等待之和是 0 + b = b。
- 交换后减少了 a − b 的等待；后面其他任务的开始时刻不变，因为这两人的总运行时间仍是 a + b。

所以，在**一组同时可用、服务时间已知、单 CPU、忽略切换开销**的任务中，按服务时间升序执行能得到最小平均等待时间。

> [!warning] “SJF 最优”有适用条件
> SJF 的最优性依赖具体假设。不要据此断言任何有到达时间、抢占代价、I/O 和预测误差的真实系统中，非抢占 SJF 都全局最优。
> 它优化的是特定模型下的平均等待，不保证每个进程都等得最少，也不保证公平。

### 5.5 实际不知道下一段 CPU burst 怎么办

用历史 burst 做**指数平均（Exponential Averaging）**。

τ_(n+1)=αt_n+(1-α)τ_n, 0≤α≤1

| 符号 | 含义 |
| --- | --- |
| tₙ | 刚刚发生的第 n 次实际 CPU burst |
| τₙ | 对该次 burst 的旧预测 |
| τₙ₊₁ | 对下一次 burst 的新预测 |
| α | 对最新实际值的重视程度 |

老师式记法：**新预测 = 最新实测的一部分 + 旧预测的一部分。**两项权重加起来为 1。

![指数平均预测 CPU burst](OS/pictures/Chapter%205/slide-16-fig-1.webp)

例如 α=0.5，初始预测 10，实际 burst 依次为 6、4、6、4：

| 已观察到的实际 burst | 更新过程 | 下一次预测 |
| ---: | --- | ---: |
| 6 | 0.5×6 + 0.5×10 | 8 |
| 4 | 0.5×4 + 0.5×8 | 6 |
| 6 | 0.5×6 + 0.5×6 | 6 |
| 4 | 0.5×4 + 0.5×6 | 5 |

- α=0：预测永远不变，最新实测不起作用。
- α=1：完全使用最近一次实际 burst。
- α 较大：更快追踪变化，但更容易受短期波动影响。
- α 较小：变化较平缓，但适应新情况较慢。

展开公式：

τ_(n+1)=αt_n+α(1-α)t_(n-1)+⋯+
α(1-α)ⁿ t_0+(1-α)^(n+1)τ_0

当 0<α<1，越旧的实测值权重越小，这就是“指数”衰减。

### 5.6 SJF 的问题：饥饿

如果短任务不断到达，一个长任务可能一直排不上，形成 **饥饿（Starvation）**。因此，平均等待时间很好，不代表每个个体都得到合理照顾。

## 6. Priority：优先级调度（Priority Scheduling）与老化（Aging）

每个进程有一个优先级，调度器选择优先级最高的已就绪进程。优先级调度既可以是抢占式，也可以是非抢占式。

本节约定：**数值越小，优先级越高**。这只是本节约定，后面的 Windows、Solaris 实例未必沿用。

| 类型 | 含义 |
| --- | --- |
| 静态优先级（Static Priority） | 创建时确定，之后基本不变 |
| 动态优先级（Dynamic Priority） | 随运行、等待或交互行为等因素调整 |

SJF 可以看成优先级调度的特例：用预测的下一段 CPU burst 长度作为优先级值，长度越小越先执行。

### 6.1 饥饿与 Aging

问题：低优先级进程可能长期被高优先级进程压住。

解决思路是 **老化（Aging）**：等待越久，逐渐提高优先级。

**补充例子：**初始优先级为 10，每等待 5 个时间单位就将数值减 1，那么等待 20 个单位后优先级变为 6。按“数值越小越优先”的约定，它更有机会运行。

> [!tip] 饥饿与死锁的区别
> 饥饿：系统整体可能一直向前推进，但某个进程总是分不到机会。
> 死锁（Deadlock）：一组进程相互等待资源或事件，无法继续。

## 7. HRRN：最高响应比优先（Highest Response Ratio Next）

**最高响应比优先（Highest Response Ratio Next，HRRN）：每次选响应比最大的任务。**标准 HRRN 是非抢占式。

响应比=(W+B)/B=1+W/B

其中 W 是当前已等待时间，B 是预计服务时间。响应比没有时间单位。

> [!warning] 名字很像，含义不同
> **响应比（Response Ratio）** 是用来选进程的优先级指标。
> **响应时间（Response Time）** 是从到达到首次响应的时间指标。
> 两者不能互换。

### 7.1 它为什么能兼顾长短任务

- 等待 W 相同时，B 小的任务比值大，照顾短任务。
- 对同一个任务，W 越来越大，响应比也会增长，照顾等得久的任务。
- 相比 SJF，它把等待时间也纳入了决策。

### 7.2 补充例题：沿用 SJF 的四个进程

t=0 只有 P1，运行到 t=7。此时：

| 进程 | 到达 A | 服务 B | t=7 的等待 W | 响应比 |
| --- | ---: | ---: | ---: | ---: |
| P2 | 2 | 4 | 5 | (5+4)/4 = 2.25 |
| P3 | 4 | 1 | 3 | (3+1)/1 = 4 |
| P4 | 5 | 4 | 2 | (2+4)/4 = 1.5 |

选 P3，运行 7～8。**到 t=8 必须重新计算**：

- P2：等待 6，响应比 (6+4)/4 = 2.5。
- P4：等待 3，响应比 (3+4)/4 = 1.75。

因此先选 P2，再选 P4。本例恰好与非抢占 SJF 的甘特图一致，但不能据此认为两个算法总相同。

### 7.3 做题步骤

1. 等 CPU 空出来，收集所有已到达且未完成的任务。
2. 计算这些任务在**当前时刻**的 W。
3. 计算 1+W/B，选最大者。
4. 非抢占地执行到当前服务完成。
5. 下一次调度时重新计算，平局按题目指定规则处理。

HRRN 需要估计服务时间，也需要计算比值。由于它不抢占，长任务运行期间仍可能让新到达的交互任务等待，不能保证很短的首次响应。

## 8. RR：时间片轮转（Round Robin）

**时间片轮转（Round Robin，RR）：每人轮流用一小段 CPU，时间到了还没完成，就去队尾继续排。**

时间片（Time Quantum / Time Slice）记为 q，作为示例的典型量级是 10～100 ms。这是教学材料中的经验范围，不是所有系统的固定设置。

### 8.1 队列如何变化

```text
队头 [P1, P2, P3]
P1 运行 min(q, P1 的剩余时间)
如果 P1 尚未完成：队列变成 [P2, P3, P1]
如果 P1 已经完成：队列变成 [P2, P3]
```

新就绪任务通常加入队尾。如果它恰好在时间片边界到达，和被抢占任务谁先入队，必须按题目约定；未说明时应明确自己的平局规则。

### 8.2 例题：q=20

四个任务都在 t=0 到达，初始顺序 P1、P2、P3、P4。

| 进程 | CPU 服务 B |
| --- | ---: |
| P1 | 53 |
| P2 | 17 |
| P3 | 68 |
| P4 | 24 |

逐片执行：

| 时间段 | 运行谁 | 运行后剩余 | 接下来怎么处理 |
| --- | --- | ---: | --- |
| 0～20 | P1 | 33 | 回队尾 |
| 20～37 | P2 | 0 | 完成，只用了 17，不必凑满 20 |
| 37～57 | P3 | 48 | 回队尾 |
| 57～77 | P4 | 4 | 回队尾 |
| 77～97 | P1 | 13 | 回队尾 |
| 97～117 | P3 | 28 | 回队尾 |
| 117～121 | P4 | 0 | 完成 |
| 121～134 | P1 | 0 | 完成 |
| 134～154 | P3 | 8 | 时间片结束，系统只剩它 |
| 154～162 | P3 | 0 | 继续完成 |

```text
0   20  37  57  77  97  117 121 134 154 162
|P1 |P2 |P3 |P4 |P1 |P3 |P4 |P1 |P3 |P3 |
```

最后两个 P3 在甘特图中可以分开表示时间片边界；如果没有其他可运行任务，不必因为时间片到期就切换到另一个进程。

| 进程 | 完成 C | 周转 T | 等待 W = C − B | 首次运行 S / 响应 R |
| --- | ---: | ---: | ---: | ---: |
| P1 | 134 | 134 | 81 | 0 |
| P2 | 37 | 37 | 20 | 20 |
| P3 | 162 | 162 | 94 | 37 |
| P4 | 121 | 121 | 97 | 57 |

W=73, T=113.5, R=28.5

快速校验：总服务时间 53+17+68+24=162，和最后完成时刻一致。

### 8.3 时间片太大或太小会怎样

![时间片与切换次数|700](OS/pictures/Chapter%205/slide-26-fig-1.webp)

图中一个需要 10 单位时间的任务：

- q=12：一次就能跑完。
- q=6：分两段执行。
- q=1：被拆成很多片段，时间片边界显著增加。

**q 很大：**如果每个 burst 都能在时间片内结束，RR 就退化为 FCFS。

**q 很小：**任务很快轮到，但上下文切换开销更突出。

**理解补充：**若每次有效执行 q 后都发生耗时 s 的切换，粗略的有效计算时间占比是：

q/(q+s)

例如 s=1 ms：q=1 ms 时约 50%，q=20 ms 时约 95.2%。这只是说明开销比例的简化模型；CPU 在执行调度代码时也可能处于忙碌状态，因此它不等同于“CPU 忙碌率”。

### 8.4 最长多久能再轮到自己

若始终有固定 n 个就绪任务，使用相同时间片 q，且忽略切换开销，一个任务一轮结束后，通常最多等其他 n−1 个任务各跑一个时间片：

一轮内的等待上界≤(n-1)q

**这是固定队列条件下两次机会之间的等待，不是任务从到达到完成的总等待上界。**任务可能轮转许多轮，新任务、优先级和切换开销也会改变具体结论。

同等优先级下，有限时间片的 FIFO 轮转通常能避免一个就绪任务一直没有运行机会。

### 8.5 时间片与平均周转时间不一定单调变化

![时间片改变时的平均周转时间](OS/pictures/Chapter%205/slide-28-fig-1.webp)

图中进程服务时间为 P1=6、P2=3、P3=1、P4=7。曲线说明：**时间片变大，平均周转时间可能上升也可能下降**，因为任务完成顺序和时间片分割会变化。

思考题“SJF 的周转时间是多少”：若都在 0 到达，SJF 顺序为 P3、P2、P1、P4，完成时刻为 1、4、10、17。

T_SJF=(1+4+10+17)/4=8

还给出一条经验：可考虑让约 80% 的 CPU burst 在一个时间片内完成。它是选择时间片的经验规则，需要结合切换代价和交互需求使用。

## 9. 多级队列（Multilevel Queue）与多级反馈队列（Multilevel Feedback Queue）

### 9.1 Multilevel Queue：多级队列

把就绪队列按任务类型分成多个队列，例如前台交互任务和后台批处理任务。

![多级队列示意](OS/pictures/Chapter%205/slide-30-fig-1.webp)

要分别决定两个层次：

| 层次 | 要决定什么 | 例题 |
| --- | --- | --- |
| 队列内部 | 同一类进程怎么排 | 前台 RR，后台 FCFS |
| 队列之间 | 哪个队列先用 CPU | 固定优先级，或队列间分配 CPU 份额 |

两种队列间策略：

- **固定优先级：**只要前台有任务，就先运行前台。后台可能饥饿。
- **CPU 时间份额：**例如前台获得 80%，后台获得 20%，然后各自按内部算法调度。

传统多级队列中，进程所属队列通常固定，分类不合适时适应性较差。

### 9.2 Multilevel Feedback Queue：多级反馈队列，MLFQ

关键变化：**进程可以在队列之间移动。**系统根据它的实际运行行为调整待遇。

![三级反馈队列](OS/pictures/Chapter%205/slide-33-fig-1.webp)

例题：

| 队列 | 优先级 | 内部策略 |
| --- | --- | --- |
| Q0 | 最高 | RR，q=8 ms |
| Q1 | 次高 | RR，q=16 ms |
| Q2 | 最低 | FCFS |

运行规则：

1. 新任务先进入 Q0，优先获得一次短时间片。
2. 用完 8 ms 仍未完成，降到 Q1。
3. 在 Q1 再用完 16 ms 仍未完成，降到 Q2。
4. 高优先级队列非空时，优先服务高队列。是否立即抢占低队列执行者，要看具体规则；常见的优先级抢占实现会这样做。

**补充例子：**一个需要连续运行 30 ms 的任务，在没有其他任务干扰时，会在 Q0 用 8 ms，在 Q1 用 16 ms，在 Q2 用剩余 6 ms。

注意 Q1 给的是**额外 16 ms**，不是累计运行到 16 ms。

### 9.3 为什么这种反馈有用

- 短任务可能在高队列很快完成。
- 长 CPU 密集型任务逐步下沉，减少其长期占据最高优先级的机会。
- 可以通过老化、周期性提升等规则，让低队列任务重新获得机会。

说队列内“采用 FCFS”，可理解为队列按先后顺序取任务；**设有时间片且会抢占的上层队列，完整运行规则仍是 RR**，不是允许一直跑到结束的普通 FCFS。

### 9.4 一道 MLFQ 题必须给哪些参数

- 队列数量与优先顺序。
- 每队列的内部算法和时间片。
- 新任务从哪一层进入。
- 什么情况下降级。
- 什么情况下升级，以及等待多久会老化。
- 高队列出现任务时是否抢占，抢占后剩余时间片怎样处理。
- 阻塞后重新就绪时进入哪一层。

**不能只看到“MLFQ”四个字就擅自补出唯一规则。**不同实现可以有不同反馈策略。

## 10. 多处理器调度（Multiple-Processor Scheduling）

单 CPU 只需要问“谁先运行”。多个 CPU 还要问：**谁放在哪个 CPU 上？如何让各 CPU 都有活干？迁移是否值得？**

### 10.1 ASMP 与 SMP

| 方式 | 示例中的基本模型 | 主要考虑 |
| --- | --- | --- |
| Asymmetric multiprocessing，ASMP | 主处理器负责关键系统活动或共享系统结构，其他处理器主要执行用户代码 | 协调相对集中，但主处理器可能成为瓶颈 |
| Symmetric multiprocessing，SMP | 各处理器自行调度，可访问共享系统结构 | 并行性强，但需要同步来保护共享结构 |

本节以同构处理器（Homogeneous Processors）为主要讨论背景，即各处理器具有相同或相近的执行能力。

### 10.2 Processor affinity 与 Load balancing

**处理器亲和性（Processor Affinity）：**尽量让线程留在原来的 CPU 上，因为它刚使用过的代码和数据可能仍在该 CPU 的缓存中。

**负载均衡（Load Balancing）：**当某 CPU 很忙、另一 CPU 空闲时，迁移一些工作，避免资源闲置。

二者有时冲突：迁移能平衡工作量，但可能损失缓存局部性（Cache Locality），并引入迁移和通信代价。

**理解补充：**软亲和性（Soft Affinity）是尽量留在原 CPU，硬亲和性（Hard Affinity）则对允许运行的 CPU 集合施加明确限制。

![物理 CPU 与逻辑 CPU](OS/pictures/Chapter%205/slide-50-fig-1.webp)

图中一个物理 CPU（Physical CPU）可以向调度器呈现多个逻辑 CPU（Logical CPU）。逻辑 CPU 不意味着拥有完全独立的全部硬件资源，因此“逻辑 CPU 数翻倍”不等于所有负载性能都翻倍。

## 11. 实时调度（Real-Time Scheduling）

普通调度常关心平均等待、吞吐或交互体验。实时调度首先关心：**任务能不能在截止时间（Deadline） 之前完成。**

### 11.1 硬实时与软实时

| 类型 | 目标 | 理解方式 |
| --- | --- | --- |
| Hard real-time，硬实时 | 对关键任务给出截止时间保证 | 必须证明在规定条件下能按时完成 |
| Soft real-time，软实时 | 优先照顾有时限的任务，允许一定程度的延误 | 延误会降低服务质量 |

实时不等于单纯“越快越好”，**可预测、可保证**往往比平均很快更重要。可调度性（Schedulability）还取决于任务执行需求、到达模式、资源阻塞和调度开销。

### 11.2 EDF：最早截止时间优先

**最早截止时间优先（Earliest Deadline First，EDF）：在已就绪任务中选绝对截止时刻最早的。**通常讨论抢占式实现。

**补充例子：**A 在 t=20 前完成，B 在 t=12 前完成，只看 EDF 时先选 B。选择依据是 deadline，不是服务时间。

### 11.3 LLF：最低松弛度优先

**最低松弛度优先（Least Laxity First，LLF）：选择松弛度最小的任务。**

L_i(t)=D_i-t-C_i^(remaining)(t)

| 项 | 含义 |
| --- | --- |
| Dᵢ | 必须完成的绝对时刻 |
| t | 当前时刻 |
| 剩余执行时间（Remaining Execution Time） | 从现在起还需要多少 CPU 时间 |
| Lᵢ(t) | 还能容忍多少额外等待 |

例题：deadline=400 ms，需要运行 150 ms，当前 t=100 ms：

L=400-100-150=150 ms

- L>0：还有等待余量。
- L=0：在单 CPU 且不能并行加速的模型下，必须连续执行，才能刚好赶上。
- L<0：在该执行需求假设下，即使现在就运行也来不及。

> [!important] 已运行过的任务要用“剩余时间”
> 不能每次都把最初总执行时间代进去，否则会低估它的松弛度。

EDF 与 LLF 可能选不同任务。例如在 t=0，A 的 D=10、剩余=1，B 的 D=12、剩余=11。EDF 选 A；LLF 比较 9 和 1，选 B。

### 11.4 RMS：速率单调调度

**速率单调调度（Rate Monotonic Scheduling，RMS）：周期越短，固定优先级越高。**标准讨论对象是周期任务，通常采用抢占式固定优先级调度。

例如 A 每 20 ms 来一次，B 每 50 ms 来一次，则 A 的优先级高于 B。这里“速率高”就是“来得更频繁”。

| 算法 | 主要依据 | 优先级性质 |
| --- | --- | --- |
| EDF | 当前任务的绝对 deadline | 动态 |
| LLF | 当前时刻的剩余松弛度 | 动态 |
| RMS | 任务周期（Period） | 固定 |

> [!warning] 优先规则不等于按时完成的保证
> 如果 CPU 工作量超过可用能力，或阻塞时间太长，仅仅使用 EDF、LLF、RMS 都不能让所有任务自动按时完成。未给出的可调度性定理不能无条件套用。

## 12. 线程调度（Thread Scheduling）与 Pthread 示例

### 12.1 PCS 与 SCS：竞争范围

| 名称 | 谁和谁竞争 | 谁来做选择 |
| --- | --- | --- |
| 进程竞争范围（Process-Contention Scope，PCS） | 同一进程中的用户线程，竞争其可用执行实体 | 用户级线程库（User-level Thread Library） |
| 系统竞争范围（System-Contention Scope，SCS） | 系统范围的内核可调度线程（Kernel Thread），竞争 CPU | 内核 |

这里把 PCS 与多对一（Many-to-One）、SCS 与一对一（One-to-One） 联系起来。理解时要把“竞争范围（Contention Scope）”和“映射模型（Mapping Model）”分开：前者说明调度竞争发生在哪个范围，后者说明用户线程怎样映射到内核执行实体。

**轻量级进程（Lightweight Process，LWP）：**在讨论的线程模型中，可把它理解为供用户线程获得内核执行能力的中间执行实体；具体含义随系统模型变化。

### 12.2 通过示例代码理解 API

排版把部分下划线与声明拆开了。下面恢复为便于阅读的教学骨架，保留原例的调度意图：

```c
#include <pthread.h>
#include <stdio.h>

#define NUM_THREADS 5

void *runner(void *param) {
    (void)param;
    printf("I am a thread\n");
    return NULL;
}

int main(void) {
    pthread_t tid[NUM_THREADS];
    pthread_attr_t attr;

    pthread_attr_init(&attr);
    pthread_attr_setscope(&attr, PTHREAD_SCOPE_SYSTEM);
    pthread_attr_setschedpolicy(&attr, SCHED_OTHER);

    for (int i = 0; i < NUM_THREADS; ++i)
        pthread_create(&tid[i], &attr, runner, NULL);

    pthread_attr_destroy(&attr);

    for (int i = 0; i < NUM_THREADS; ++i)
        pthread_join(tid[i], NULL);

    return 0;
}
```

| 调用 | 做什么 |
| --- | --- |
| pthread_attr_init | 初始化线程属性对象 |
| pthread_attr_setscope | 请求竞争范围，PROCESS 或 SYSTEM |
| pthread_attr_setschedpolicy | 设置属性对象中的调度策略 |
| pthread_create | 按属性创建线程，并让它从 runner 开始执行 |
| pthread_join | 等待指定线程结束 |
| pthread_attr_destroy | 释放属性对象占用的资源 |

> [!note] 代码边界
> 这是便于对照示例的简化骨架，未加入返回值检查，未验证编译运行。真实程序需要检查每个调用的结果；平台未必支持所有竞争范围。
> 设置属性对象不必然意味着新线程会按这些属性运行，调度属性还受继承设置影响。若要显式采用所设策略，需要配合 `pthread_attr_setinheritsched(..., PTHREAD_EXPLICIT_SCHED)`，并处理策略支持和权限等条件。

这里列出 FIFO、RR、OTHER 等策略。不要因为名称有 FIFO 就直接把 POSIX 实时策略与本章所有普通进程的 FCFS 等同；它还涉及优先级和系统策略。

## 13. 操作系统实例：按示例的历史版本理解

> [!warning] 这一节是历史实现案例
> 明确包含 Solaris 2、Windows XP，以及旧 Linux 调度结构。以下用于理解“课堂算法如何组合成系统”，不代表当前所有版本的具体行为。

### 13.1 Solaris：调度类与动态调整

![Solaris 调度类](OS/pictures/Chapter%205/slide-41-fig-1.webp)

图把实时类（Real-time Class）、系统类（System Class）、交互/分时类（Interactive / Time-sharing Class）等映射到全局优先级（Global Priority），调度器先比较最终的全局优先级。

![Solaris 分派表](OS/pictures/Chapter%205/slide-42-fig-1.webp)

分派表的列应这样读：

- `priority`：当前优先级。
- `time quantum`：该级允许的时间片。
- `time quantum expired`：用完整个时间片后调整到的优先级。
- `return from sleep`：从睡眠/等待返回时调整到的优先级。

例如图中的 priority=0 行：时间片 200；用完时间片后仍为 0；从 sleep 返回则可调整为 50。图中较高优先级常有较短时间片。

背后的意图是：持续用满 CPU 的任务可能降低优先级，而等待后返回的任务获得更快响应。应按这张表自身的编号方向理解，不能套用“数值越小越高”的通用假设。

### 13.2 Windows XP：优先级类与线程相对优先级

![Windows XP 优先级表](OS/pictures/Chapter%205/slide-43-fig-1.webp)

读表方法：**列是进程优先级类（Priority Class），行是线程相对优先级（Relative Priority），交点给出该组合的优先级。**

例如 normal 类中的 normal 相对优先级对应 8，above normal 相对优先级对应 9。不能把“进程类 normal”和“线程相对 normal”当成同一层概念。

本图中数值较大通常表示更高优先级，正好提醒我们：**先看编号约定，再比较数值。**

### 13.3 Linux：不同历史调度机制

介绍基于 credit 的分时调度：

1. 倾向选择 credit 最高的任务。
2. 时钟中断（Timer Interrupt）消耗 credit。
3. credit 用尽后选择其他任务。
4. 当所有任务 credit 都用尽时，根据优先级、历史等因素重新计算。

同时，这里介绍软实时优先级策略，包含 FIFO 和 RR，高优先级任务先执行。

![中的 Linux 优先级与时间片关系](OS/pictures/Chapter%205/slide-45-fig-1.webp)

![旧 Linux runqueue 的 active 与 expired 数组](OS/pictures/Chapter%205/slide-46-fig-1.webp)

结构按优先级组织任务链表（Task List），并区分 active 和 expired 两组任务。作为该图对应历史调度器的理解补充：任务用完本轮额度后进入 expired，active 用尽时可通过交换两组角色开始下一轮。

 credit 描述与 active/expired 图来自不同历史机制的讲解，**不要强行拼成同一套算法**。做本章题时按题目给出的规则分析。

## 14. Java 线程调度：调度语义与使用边界

一种模型是了一种抢占、基于优先级的 Java 虚拟机（Java Virtual Machine，JVM）调度模型，同优先级可能按 FIFO 组织。学习时把它作为本节模型，不能据此写出依赖确定执行顺序的 Java 并发程序。

### 14.1 需要注意的调度时机

- 当前线程离开 runnable 状态，例如阻塞或结束。
- 更高优先级线程进入 runnable 状态。

同时明确指出：JVM 不保证一定按某个固定时间片机制调度线程。

### 14.2 yield 的意义和局限

```java
while (true) {
    // 执行一段计算
    Thread.yield();
}
```

这里把它解释为给同优先级线程让出机会。需要保留的边界是：**不能依赖 yield 保证另一个指定线程立即运行，也不能用它保证公平、同步或执行先后关系。**

### 14.3 线程优先级常量

| 常量 | 传统 Java 线程模型中的值 |
| --- | ---: |
| Thread.MIN_PRIORITY | 1 |
| Thread.NORM_PRIORITY | 5 |
| Thread.MAX_PRIORITY | 10 |

示例 `setPriority(Thread.NORM_PRIORITY + 2)` 即请求优先级 7。优先级设置不能替代锁、条件等待或其他同步机制，也不能被当作确定的运行顺序保证。

## 15. 如何评价调度算法

### 15.1 四种评价方法

| 方法 | 怎么做 | 能说明什么、局限在哪里 |
| --- | --- | --- |
| 确定性模型（Deterministic Modeling） | 固定一组输入，逐个算法手算指标 | 结果具体易比较，但只代表该工作负载（Workload） |
| 排队模型（Queueing Models） | 用到达率、服务率、队列等建模 | 可分析平均行为，但结论依赖模型假设 |
| 模拟（Simulation） | 用合成负载或实际记录驱动模拟器 | 可比较复杂策略，但取决于负载与模拟准确性 |
| 实际实现（Implementation） | 在真实系统中实现并测量 | 更接近实际，但成本高、干扰因素多 |

### 15.2 利特尔定律（Little’s Law）：L = λW

L=λW

| 符号 | 含义 |
| --- | --- |
| L | 所选系统边界内长期平均任务数量 |
| λ | 长期有效到达率（Effective Arrival Rate），单位如“任务/秒” |
| W | 任务在该边界内平均停留时间（Mean Time in System），单位如“秒” |

**理解补充例题：**稳定系统每秒平均进入 5 个任务，每个任务平均停留 2 秒，则平均在系统中的任务数 L=5×2=10。

> [!warning] 边界和单位必须一致
> 若统计整个系统，W 包括其中的服务与等待；若只统计就绪队列，则应使用就绪队列对应的任务数、进入率和等待时间。
> 这里的 W 是 Little 定律的通用“停留时间”记号，不能不加区分地和前面的调度等待时间 Wᵢ 混用。使用长期平均关系需要稳定、平均量有意义等条件。

### 15.3 模拟图怎么看

![调度算法模拟评价](OS/pictures/Chapter%205/slide-48-fig-1.webp)

从真实进程执行记录中提取 CPU/I/O 轨迹（Execution Trace），再用同一份记录驱动 FCFS、SJF、RR 等模拟器，最后比较统计结果。

**为什么用同一份输入？**否则观察到的差异可能来自工作负载不同，而不只是调度算法不同。

## 16. 算法对照与做题模板

### 16.1 核心算法对照

| 算法 | 选择依据 | 抢占？ | 主要优点 | 主要问题 |
| --- | --- | --- | --- | --- |
| FCFS | 就绪入队次序 | 通常否 | 简单，顺序直观 | 护航效应，短任务可能等很久 |
| SJF | 最短下一段 CPU burst | 否 | 特定模型下平均等待最小 | 长度需预测，长任务可能饥饿 |
| SRTF | 最短剩余 CPU 时间 | 是 | 让新到达的短任务较快完成 | 可能频繁抢占，长任务可能饥饿 |
| Priority | 最高优先级 | 两种均可 | 可体现任务重要程度 | 低优先级任务可能饥饿 |
| HRRN | 最大 1+W/B | 标准形式否 | 同时考虑短任务和等待时间 | 需估计服务时间、重算比值 |
| RR | 队头运行至完成或片到期 | 是 | 同优先级轮流获得机会 | 时间片选择影响响应和开销 |
| 多级队列 | 类别与队列间规则 | 依规则 | 不同任务可采用不同策略 | 固定分类适应性弱，低队列可能饥饿 |
| MLFQ | 队列优先级与运行反馈 | 常见实现是 | 不预知完整长度也能偏向短任务 | 规则复杂，需要避免低队列饥饿 |

### 16.2 所有计算题都按这套步骤

1. **抄输入表。**列出 A、B、优先级、时间片，明确优先级编号方向。
2. **写规则。**是否抢占，平局怎么处理，同刻到达和时间片到期谁先入队。
3. **维护状态。**未到达、就绪、运行、完成分别记，抢占算法额外记录剩余时间。
4. **推进到事件。**下次到达、完成、时间片耗尽或其他会改变决策的时刻。
5. **只在当前可选任务中比较。**不能提前选尚未到达的短任务。
6. **画甘特图。**就绪队列为空时必须写 idle，并跳到下个到达时刻。
7. **记首次运行 S 和最终完成 C。**第一次运行后，后续片段不再覆盖 S。
8. **逐个算 T、W、R，再求平均。**不要只给平均值。
9. **校验。**所有运行片段的长度之和应等于总 CPU 服务时间；每个任务的剩余量最终为 0。

### 16.3 最容易扣分的地方

| 错法 | 正确检查方式 |
| --- | --- |
| 周转时间直接写完成时刻 | 先减到达时间，只有 A=0 时数值才相同 |
| RR 每片强行跑满 q | 实际执行 min(q, 剩余时间) |
| SRTF 比较原始 B | 比较当前剩余时间 |
| HRRN 到达时算一次就不更新 | 每次真正选择下一任务时重算 |
| 响应时间算到最后完成 | 只算到首次响应，算例通常到首次运行 |
| 把 I/O 等待算成就绪等待 | 分开记录 ready 与 blocked |
| 认为优先级数字大一定优先 | 先读题目约定 |
| 空闲阶段在甘特图中消失 | 写 idle，后面时间边界才不会错 |
| RR 的 (n−1)q 当成总等待上界 | 它针对固定队列里一轮之间的等待 |
| 认为抢占一定比非抢占好 | 说明优化指标，并考虑开销与公平性 |

> 6. MLFQ 允许任务根据反馈在队列之间移动。

> 8. 不一定。FCFS 两种入队顺序就是反例。

### 17.3 考前速记

- 周转：完成减到达。
- 响应：首次运行减到达，注意应用层响应的语义边界。
- 等待：无 I/O 的单 burst 算例中，周转减服务。
- SRTF：每次比较**剩余**时间。
- HRRN：**1 + 等待/服务**，取最大。
- RR：执行不超过一个时间片，未完成回队尾。
- Aging：等待越久，逐渐提高优先级。
- MLFQ：行为反馈决定队列移动。
- EDF 看 deadline，LLF 看 deadline − 当前时刻 − 剩余执行，RMS 看周期。
- Little：L = λW，注意系统边界和单位。
