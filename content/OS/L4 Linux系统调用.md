# L4 Linux系统调用

> 来源：`L4 Linux系统调用.pdf`，38 页。对应 [[OS/第 2 章 · 操作系统服务与结构|Chapter 2]]，进程结构见 [[OS/L5 Linux进程管理|L5 Linux进程管理]]。核心代码以旧式 x86 32 位 `int 0x80` 路径为例，寄存器、编号和入口均不能直接套到其他 ABI。

## 1. 为什么需要系统调用（Purpose）

课件 3–11 页。用户程序不直接操纵任意内核数据和设备；通过受控入口请求内核服务，由内核检查参数、权限与对象状态。

| 概念 | 含义 |
| --- | --- |
| API（Application Programming Interface） | 程序员使用的调用接口 |
| 库函数（Library Function） | 用户空间的实现或封装，可能调用零次或多次系统调用 |
| 系统调用（System Call） | 跨越用户/内核边界的受控服务请求 |
| 内核函数（Kernel Function） | 在内核内部执行的实现函数，不是每个都公开给用户 |
| Shell 命令（Command） | 用户启动的程序或 Shell 内建功能 |

`printf` 是库接口，可能缓冲输出后才调用写服务；“调用一个库函数”不能直接等同“一次系统调用”。

## 2. 模式、上下文与地址空间（Mode, Context and Address Space）

课件 7–8、16–17 页。系统调用进入内核态，通常仍在**当前进程的执行上下文（Process Context）** 中；模式切换（Mode Switch）不必然发生进程切换（Context Switch）。如果服务阻塞，调度器才可能换到另一进程。

需要保存寄存器与返回位置，使用相应内核栈（Kernel Stack）；不能让用户程序随意指定内核执行栈。

![课件系统调用时的内核栈](OS/pictures/L4%20Linux%E7%B3%BB%E7%BB%9F%E8%B0%83%E7%94%A8/%E5%AD%A3%E8%80%81%E5%B8%88-p016.png)

课件 3 GiB 用户区、1 GiB 内核区属于其 32 位配置示例；用户指针仍需按内核接口安全访问与检查，不能把“已在内核态”理解成任意指针都有效。

## 3. 旧式 x86 调用路径（Legacy x86 Call Path）

课件 12–26 页。

```text
用户程序调用库封装
  设置调用号与参数寄存器
    int 0x80
      system_call 入口保存现场、检查编号
        根据 sys_call_table 找服务例程
          执行服务并写入返回值
            处理必要的返回前工作、恢复现场
              返回用户态封装，交给调用者
```

![课件跨越用户态和内核态的调用链](OS/pictures/L4%20Linux%E7%B3%BB%E7%BB%9F%E8%B0%83%E7%94%A8/%E5%AD%A3%E8%80%81%E5%B8%88-p012.png)

**调用号（System-Call Number）** 用于选服务；**调用表（System-Call Table）** 关联编号与服务入口。不能把函数名地址直接由用户任意传给内核去执行。

课件 `call *sys_call_table(,%eax,4)` 中比例因子 4 来自其 32 位指针表项大小。若 eax=24，表内偏移是 `24×4=96 B`；不是“调用第 96 号服务”。

## 4. 参数与返回值（Arguments and Return Value）

课件 27–32 页。

| 角色 | 课件示例寄存器 |
| --- | --- |
| 调用号 | eax |
| 前五个参数 | ebx、ecx、edx、esi、edi |
| 返回值 | eax |

![课件参数寄存器表](OS/pictures/L4%20Linux%E7%B3%BB%E7%BB%9F%E8%B0%83%E7%94%A8/%E5%AD%A3%E8%80%81%E5%B8%88-p031.png)

课件的“总共不超过6个，包含调用号”表述与其他 x86 32 位完整 ABI 描述不能混用；这里仅按展示的五参数表追踪示例，不把它当全部架构的参数上限。系统调用号也不是函数签名中的用户业务参数。

用户缓冲区可通过“指针＋长度”传入，但内核必须处理地址合法性、权限、复制与访问期间的异常。把大量参数打包后传指针，不意味着可以跳过检查。

内核错误返回与 libc 对外的 `-1/errno` 约定是不同层；课件无效编号路径使用 `-ENOSYS`，不能据此说所有用户 API 直接返回同一个负数。

## 5. getuid 示例逐步追踪（Worked Trace）

课件 33–38 页。按课件旧 ABI：

1. 用户调用 `getuid()` 封装，将对应调用号置入 eax。
2. 通过 `int 0x80` 进入统一入口，保存用户现场。
3. 检查编号，查表并执行用户标识相关服务例程。
4. 服务取得当前进程的相应 UID 信息并形成返回值。
5. 把结果写回保存现场中的返回寄存器位置。
6. 恢复现场、返回用户态，封装把结果交给程序。

“getuid 编号 24”、`sys_getuid16`、`_syscall0` 宏是所展示旧版本的具体代码。学习重点是封装、入口、分派、服务、返回这五层，不把旧汇编直接复制到其他体系结构。

课件目录提到添加 `mysyscall`，正文主要追踪 getuid，并未提供完整跨版本添加指南。补充的实施检查项应包括：确定实验内核/架构、定义 ABI、处理参数与错误、注册入口、构建部署、用户态验证；不能只改调用表就宣称完成。

## 6. 自测与术语（Review）

1. 执行系统调用一定切换进程吗？
2. 保存返回值后再恢复旧 eax，为什么不会把结果覆盖？
3. 同名 getuid 在不同 ABI 上必须同编号吗？

> [!success]- 答案
> 1. 不一定，进入内核与换进程是不同事件。
> 2. 应更新将被恢复的保存现场中相应位置，让恢复动作取得新返回值。
> 3. 不要求，编号取决于体系结构和 ABI。

术语：应用二进制接口（Application Binary Interface，ABI）、陷入（Trap）、服务例程（Service Routine）、寄存器现场（Register Context）、用户缓冲区（User Buffer）。
