# 第 7 章 · 应用层

> 重点是把一次真实访问串起来：DNS找服务→传输层建立通信→应用协议交换数据→浏览器或邮件客户端解释内容。术语使用English，原理与计算用中文逐步说明。

## 1. DNS（Domain Name System）：名字怎样对应地址？

IP便于路由，名字便于人记忆。单一hosts文件在小网可用，但全网规模下会遇到更新、冲突、分发和管理问题。DNS采用hierarchical namespace（分层名称空间）和distributed database（分布式数据库），支持分权管理与缓存。

### 1.1 Name Space、Domain、Zone

```text
                    .  (root)
                  /       \
                com       edu
               /           \
           example       washington
              |               |
             www             cs
                              |
                            robot
```

`robot.cs.washington.edu.`从右向左逐层定位，末尾`.`表示root。Absolute domain name / FQDN表示完整名称；省略终止点的写法在某些resolver配置下可能被加search suffix。普通DNS名称比较通常不区分字母大小写。

Top-level domains有generic（如com、org）和country-code（如cn、uk）等。每层管理者决定其子域分配。命名对应组织/管理边界，不直接等同于物理LAN边界。

单个label最多63 octets，完整线格式名称最多255 octets，包含长度标记和根；不要把“最多255个可见字符”当成任意情况下的精确表示限制。

**Domain**是树中的子树；**Zone**是某authority直接负责的数据范围，可将子域delegate给其他服务器，所以domain与zone不是同义词。

![DNS namespace and delegated zones](计算机网络/pictures/Chapter7/dns-zones.png)

### 1.2 Resource Records（RR）五元组

`(Name, TTL, Class, Type, Value)`。TTL控制缓存寿命，Class常为IN。

| Type | Value主要含义 | 例子与用途 |
|---|---|---|
| A | IPv4 address | www.example.test → 192.0.2.10 |
| AAAA | IPv6 address | 同名可同时有IPv6记录 |
| NS | authoritative name server | 指定某zone的权威服务器 |
| CNAME | canonical name | alias.example.test → www.example.test |
| MX | preference + mail exchanger | 邮件域的收信服务器，不是发信用户个人IP |
| SOA | zone管理信息 | primary server、serial、refresh等 |
| PTR | reverse lookup name | 反向区域中IP相关名字 |
| TXT | text strings | 验证或应用策略数据 |
| SRV | service location | priority、weight、port、target |

![DNS resource record types](计算机网络/pictures/Chapter7/dns-records.png)

同一名字可有多个A/AAAA，用于多接口、多实例或负载分配；不保证每个resolver永远按同样次序返回。CNAME是别名，不等于一条A记录塞进另一个名字；通常该别名节点不能同时放普通其他记录。

Authoritative answer来自负责该数据的authority，cached answer来自缓存。权威性描述责任来源，不保证管理员绝不会配错。Root server系统有13个传统逻辑标识（A–M），不是世界上只有13台物理服务器。

### 1.3 Recursive vs. Iterative Query

递归：请求者让对方代自己完成解析，返回最终结果/错误。迭代：对方可能只返回referral，告诉请求者下一步问谁。

```text
Host → Local recursive resolver       （recursive）
          ↓ query root
          ← referral to .edu
          ↓ query .edu
          ← referral to washington.edu
          ↓ query authoritative server
          ← A / AAAA or further referral
Host ← final answer
```

Root一般不替本地resolver一路递归到底；普通host通常不自己逐个询问根/TLD。delegation深度、CNAME、缓存、重试都会改变具体消息数，不要死背固定“10步”。

![Recursive lookup and iterative referrals](计算机网络/pictures/Chapter7/dns-query.png)

### 1.4 DNS Delay与Cache

若查询必须顺序访问$n$台服务器、往返时间$RTT_i$，忽略处理/传输，则：

$$T_{DNS}=\sum_{i=1}^n RTT_i$$

缓存命中可能只需要访问local resolver甚至无需网络；TTL从记录进入缓存后递减，不能把上次缓存的新TTL永远重新开始。例：TTL300s，120s后剩180s；过期后需重新获取/验证，不能无条件继续当新鲜数据。

普通DNS可用UDP53，也可用TCP53，如截断后重试、大响应或zone transfer等场景；不能断言DNS只用UDP。DNSSEC验证数据来源/完整性，不负责把查询名称保密。

命令识读：`nslookup -type=A example.com`查A，`nslookup -type=MX example.com`查邮件交换；`dig @server name type`显式指定server。命令示例用于理解接口，不需要在笔记学习时实际向外发查询。

## 2. Electronic Mail：一封邮件的完整路线

### 2.1 Architecture and Services

```text
Sender MUA
  └─ SMTP submission → Sending MTA
                         └─ SMTP transfer → Receiving MTA / mailbox
                                               ↑ POP3 / IMAP / Webmail
                                           Recipient MUA
```

MUA（Mail User Agent）负责用户操作；MTA（Message Transfer Agent）传送；mailbox存储待取邮件。发信与收信协议不是同一个方向：SMTP push，POP3/IMAP主要用于访问邮箱。

基本服务：composition（撰写）、transfer（传输）、reporting（投递结果报告）、displaying（显示）、disposition（保存/删除/回复等处置）。还可支持forwarding、mailing list、Cc、Bcc、priority、privacy等。

![Electronic mail architecture](计算机网络/pictures/Chapter7/email-architecture.png)

### 2.2 Envelope vs. Message

SMTP envelope是投递所需的外层信息，例如`MAIL FROM`、`RCPT TO`；message自身是RFC5322式headers加body。Envelope收件人与可见`To:`不必相同，Bcc能投递给不显示在To/Cc中的收件人。

| Message header | 含义 |
|---|---|
| From | 作者 |
| Sender | 实际发送者，在与作者不同等场景使用 |
| To / Cc / Bcc | 可见主要收件人/抄送/密送相关信息 |
| Date | 写信/提交的日期时间语义 |
| Subject | 主题 |
| Reply-To | 希望回复的地址 |
| Message-ID | 消息标识 |
| In-Reply-To / References | 关联会话线程 |
| Received | 沿途邮件服务器添加的处理记录 |

Header与body用空行分开。Header是结构化信息，不能凭“显示出来的From”证明发件人真实性；SMTP投递成功也不等于人已阅读。

## 3. MIME 与 Base64：二进制如何放进邮件？

### 3.1 MIME（Multipurpose Internet Mail Extensions）

传统ASCII格式难以直接表达中文、其他字符集、音频和图片。MIME描述内容类型、字符集、编码方式及multipart结构，不是独立邮件传输协议，也不是加密。

| MIME header | 作用 |
|---|---|
| MIME-Version | 版本，如1.0 |
| Content-Type | media type、subtype、charset、boundary等 |
| Content-Transfer-Encoding | base64、quoted-printable等 |
| Content-ID | 部件标识 |
| Content-Description | 部件说明 |

类型例：text/plain、text/html、image/jpeg、image/png、audio/mpeg、video/mp4、application/pdf、multipart/mixed、multipart/alternative。

`multipart/mixed`把正文和附件组合；`multipart/alternative`提供同内容的不同表示，如纯文本与HTML，通常选择适合客户端的版本，不是把两个版本连续当正文。

```text
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="part-boundary"

--part-boundary
Content-Type: text/plain; charset=UTF-8

这是一段正文。
--part-boundary
Content-Type: application/octet-stream
Content-Transfer-Encoding: base64

TWFu
--part-boundary--
```

边界行、每部分首部和空行都有意义；最后边界多两个`--`表示结束。

### 3.2 Base64编码逐位做

3个byte=24bit→分成4组6bit→各映射一个ASCII字符。

| Index | Character |
|---|---|
| 0–25 | A–Z |
| 26–51 | a–z |
| 52–61 | 0–9 |
| 62、63 | +、/ |

ASCII `Man`：M=77、a=97、n=110。

```text
原byte： 01001101 01100001 01101110
拆6bit： 010011 010110 000101 101110
十进制：    19     22      5     46
字符：       T      W      F      u
```

因此`Man → TWFu`。解码反向操作：查6bit→拼接→每8bit恢复byte。

只剩1B时补成两个有效6bit组，再用`==`补足4字符：`M → TQ==`；只剩2B时3组加`=`：`Ma → TWE=`。这些零填充位与字面`=`不同，`=`是输出padding标记，不是额外原数据。

### 3.3 长度题：先算编码，再算换行

原数据$n$B、不计折行：

$$L_{64}=4\left\lceil\frac n3\right\rceil$$

4560B文件：$4560/3=1520$组，输出6080字符。每110个输出字符插入CR+LF，最后一行也加：

$$N_{line}=\lceil6080/110\rceil=56$$
$$L_{total}=6080+56\times2=6192\text{ B}$$

55个满行共6050字符，末行30字符，所以换行共56对。这里110是题设，不是MIME通用行长规范。若长度恰好整除，要确认“结尾”是否已由该行终止CRLF满足，避免无依据重复追加一对。

Base64约膨胀4/3；不隐藏内容，没有key，任何人可解码，因此**encoding is not encryption**。

## 4. SMTP / ESMTP / POP3 / IMAP

### 4.1 SMTP（Simple Mail Transfer Protocol）对话

```text
S: 220 mail.example.test ready
C: EHLO sender.example.test
S: 250 ... capabilities ...
C: MAIL FROM:<alice@example.test>
S: 250 OK
C: RCPT TO:<bob@example.test>
S: 250 OK
C: DATA
S: 354 End with <CRLF>.<CRLF>
C: From: alice@example.test
C: To: bob@example.test
C: Subject: Test
C:
C: Message body
C: .
S: 250 Accepted
C: QUIT
S: 221 Bye
```

DATA里的headers不是SMTP命令，结束标记是独立的一点行；正文若某行以`.`开头要dot-stuff，避免混淆结束标记。可以有多个RCPT TO，同一DATA投递给多个接收者。

ESMTP用EHLO协商extensions，如SIZE、AUTH、STARTTLS等。SMTP submission与MTA间relay是不同角色；25常用于服务器间传递，587常用于提交，不能把所有SMTP通信都固定成同一端口和认证方式。

![SMTP extensions and purposes](计算机网络/pictures/Chapter7/smtp-extensions.png)

### 4.2 POP3 vs. IMAP

| 维度 | POP3 | IMAP |
|---|---|---|
| 常见模型 | 下载邮箱中的消息 | 服务器保存状态，客户端同步访问 |
| 多文件夹与flags | 基本模型较有限 | 支持folder/mailbox与flags |
| 部分获取/检索 | 基本机制较简单 | 可检索、按需获取部分内容 |
| 多设备体验 | 需额外协调副本和删除 | 更适合保持服务器端一致状态 |
| 是否一定删除服务器副本 | 不是，可配置保留 | 按协议/客户端操作处理 |

常见命令：POP3的USER、PASS、STAT、LIST、RETR、DELE、QUIT；IMAP的LOGIN、SELECT、FETCH、SEARCH、STORE、COPY、EXPUNGE、LOGOUT等。Webmail是浏览器与Web应用通信，再由服务端处理邮箱，不是浏览器必然直接运行POP3。

## 5. WWW Architecture：点击链接后发生什么？

WWW是运行在Internet上的一类应用，不等同于整个Internet。Browser处理用户界面、HTML/CSS/JavaScript、网络请求和内容显示；server处理访问控制、查缓存、读文件或生成内容、形成response并写log。

### 5.1 URL / URI / URN

URL=Uniform Resource Locator，描述资源位置与访问方案；URI=Uniform Resource Identifier是更一般的标识概念，URL属于其中；URN按名字标识资源。

```text
https://www.example.test:8443/course/ch7?q=http#timing
\___/   \______________/ \__/\_________/\____/\_____/
scheme        host       port   path     query fragment
```

缺省port可由scheme决定；query在`?`后，fragment在`#`后。Fragment通常由client解释，不随普通HTTP请求目标直接送给server。HTTPS不是“把DNS也一起自动加密”，DNS是否加密由其自身机制决定。

### 5.2 一次访问的操作链

1. 解析URL，判断scheme、host、port、path。
2. DNS得到IP，或使用缓存。
3. 选路并找到next-hop，必要时ARP/邻居发现。
4. 按HTTP版本建立TCP/TLS或QUIC。
5. 发送request，server检查权限、缓存并获取/生成资源。
6. 返回status、headers、body。
7. Browser解析HTML，发现CSS/JS/image等额外资源并发起相应请求。
8. 构造DOM与样式，布局、绘制，并执行相应脚本。

连接可保持和复用，不是每拿一个文件就必然断开。浏览器可通过Content-Type决定解释方式，特定类型可交给外部helper application；历史plug-in机制与现代浏览器内建能力要区分。

多线程Web服务器常由front end接受请求，再交worker处理磁盘、程序或cache，避免一个慢请求阻塞全部服务。

## 6. Cookies、Session 与 Privacy

HTTP消息交换本身不要求server记住前一次请求，但应用可利用cookie/session维持状态。IP不能可靠代表用户：多人可共享NAT地址，同一用户也会换IP。

```http
HTTP/1.1 200 OK
Set-Cookie: sid=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
```

后续符合范围的请求带`Cookie: sid=abc123`，server据此查session。Cookie可存identifier，不必把整个购物车直接塞进其中。

- Domain、Path约束发送范围。
- Expires/Max-Age控制寿命。
- Secure限制通过安全传输发送；不等于cookie内容本身加密。
- HttpOnly限制普通JavaScript读取。
- SameSite参与控制跨站请求携带行为。

历史的“域、路径、内容、过期、安全标志”是概念模型，不是所有cookie只能恰有5字段。Cookie的domain/path规则与Web same-origin policy有关联但并不相同，不能笼统说“任何另一个域都绝不可能收到相关cookie”。

Third-party tracking可跨站关联访问；canvas/device fingerprinting利用字体、渲染或设备特征形成指纹。删除cookie不必然清除所有可关联线索，HTTPS也不阻止终点网站看到自己收到的请求内容。

## 7. HTML / CSS / Forms：看懂静态页面

HTML描述结构，CSS描述表现，JavaScript实现行为。Static page指响应内容通常已存在，并非“不能包含图片或链接”；dynamic page可能在server或client动态生成。

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <title>Network Course</title>
  <style>body { color: navy; } h1 { font-size: 2rem; }</style>
</head>
<body>
  <h1>HTTP</h1>
  <p>Study <a href="/notes">course notes</a>.</p>
  <a href="/topology"><img src="network.png" alt="Network topology"></a>
</body>
</html>
```

点击图片的做法是**把img放进a元素**，不是给img写一个不存在的通用`href`属性。`alt`用于替代文本，`src`是资源位置，a的`href`是点击目的。

常用标签：h1–h6、p、br、a、img、ul/ol/li、table/tr/th/td、div、span、form、input、textarea、select。`<html>`包含head和body，不是head/body各自再套独立html。`&nbsp;`是字符实体表示不换行空格；显示`<`可用`&lt;`。

### 7.1 Forms中的GET与POST

```html
<form action="/search" method="get">
  <input name="q" type="text">
  <button type="submit">Search</button>
</form>
```

提交可形成`/search?q=TCP`。POST通常把表单编码数据放入body；password输入框仅改变屏幕显示，不负责传输加密。textarea是独立元素，checkbox是input的type，不能把所有控件都写成任意字符串type。

CSS可写在style或外部stylesheet，通过selector选择元素并设置property:value；结构与样式分离便于统一修改。HTML版本演进中新增语义和媒体能力，旧font标签不应视作必需的现代排版方式。

## 8. Dynamic Web、CGI、AJAX 与 DOM

### 8.1 Server-side vs. Client-side

| 技术 | 执行位置 | 典型职责 |
|---|---|---|
| CGI | Server上的外部程序接口 | 接收参数，查数据库，生成response |
| PHP / JSP / ASP.NET | Server | 动态模板/程序、业务逻辑 |
| JavaScript | Browser为常见场景 | 事件响应、DOM更新、异步请求 |
| DOM | Browser中的文档对象结构 | 通过节点表示并修改文档 |
| XML | 数据格式 | 自定义标签表示结构化数据 |

server-side代码通常不直接发送源码让浏览器执行，而是先产生结果；client-side脚本在用户设备运行，不能仅靠它保护server敏感操作。JavaScript与Java是不同语言。

CGI流程：填写表单→发送输入→Web server交给CGI程序→程序查询DB→生成HTML→响应→browser显示。

![CGI form processing](计算机网络/pictures/Chapter7/cgi-flow.png)

历史上也有VBScript、Java applets、ActiveX等client侧技术，它们说明可执行内容的发展，不能当作普通现代网页所需依赖。

### 8.2 AJAX（Asynchronous JavaScript and XML）

组合HTML/CSS展示、结构化数据、DOM局部更新、异步I/O、JavaScript协调。名字含XML不意味着必须用XML，也可交换JSON/text等。

```text
User event → JS sends request → Browser stays responsive
                                ↓ response arrives
                         JS updates part of DOM
```

异步强调等待网络期间不冻结整个交互，而不是“服务器一定不按顺序处理”或“消息没有延迟”。地图拖动时可请求下一块数据，同时保留当前交互。

XML允许定义标签，用来表达结构；XSLT可把XML转换为HTML等表示。DOM是文档的对象树，不是网络层的树路由算法。

![DOM tree](计算机网络/pictures/Chapter7/dom-tree.png)

## 9. HTTP：请求、响应与语义

HTTP（Hypertext Transfer Protocol）是应用层协议。层次由功能决定，不因HTTP/3运行于QUIC或HTTP承载RPC就变成普通传输层协议。

### 9.1 HTTP/1.1文本消息格式

```http
GET /course/ch7?mode=read HTTP/1.1
Host: www.example.test
Accept: text/html
Connection: keep-alive

```

第一行是method、request target、version；后面是headers；**空行结束header section**。响应：

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 13

Hello, world!
```

body长度按实际byte计；上例正文`Hello, world!`恰13B，不包括为了展示代码块而可能出现的结尾换行。真实消息分界还可能用chunked transfer或连接关闭等机制，不能把每个body都按“下个空行”截断。

### 9.2 Methods 与Status Codes

| Method | 主要语义 |
|---|---|
| GET | 获取资源表示 |
| HEAD | 获取与GET相关的response headers，不返回该表示的body |
| POST | 由目标资源处理提交内容 |
| PUT | 以提交表示创建/替换目标资源 |
| DELETE | 请求删除目标资源关联 |
| OPTIONS | 查询通信选项 |
| TRACE | 诊断性回显请求 |
| CONNECT | 建立隧道，常见于代理 |

Method名称区分大小写，如GET；HTTP header field name不按同样规则区分大小写。GET/HEAD是safe语义；PUT/DELETE具idempotent语义，重复请求的预期状态效果相同，不等于响应一定完全相同。POST不保证幂等，但应用可用额外机制实现重试安全。

| Status class | 意义 | 例子 |
|---|---|---|
| 1xx | Informational | 100 Continue |
| 2xx | Success | 200 OK、201 Created、204 No Content |
| 3xx | Redirection / cache等后续处理 | 301、302、304 Not Modified |
| 4xx | Client-side request error | 400、401、403、404 |
| 5xx | Server-side failure | 500、502、503 |

401与认证相关，403通常表示服务器拒绝；404不表示TCP没有建立。304用于条件请求验证，不携带所缓存表示的完整body。

### 9.3 常见Headers

| Request / Response field | 作用 |
|---|---|
| Host | 区分同IP上的虚拟主机 |
| User-Agent | client软件信息 |
| Accept / Accept-Language / Accept-Encoding | 可接受的表示/语言/内容编码 |
| Authorization | 认证凭据 |
| Cookie / Set-Cookie | 发回cookie / 设置cookie |
| Content-Type | body媒体类型 |
| Content-Length | 消息body长度相关定界 |
| Content-Encoding | 内容已施加的编码，如gzip |
| Cache-Control | 缓存指令 |
| ETag / If-None-Match | 实体验证器及条件 |
| Last-Modified / If-Modified-Since | 修改时间及条件 |
| Location | 重定向/新资源位置等 |

为什么网页前有MIME式首部？接收者需要知道类型、字符集、压缩、长度等，才能正确解释body；不能仅靠URL后缀，因为同一路径可生成不同表示。

## 10. HTTP Caching：Freshness与Validation

第一问“缓存还新鲜吗？”若可直接复用，就无需请求源站。过期不等于内容必定变了，可用conditional GET验证。

```text
Client: If-None-Match: "v7"
Server: 304 Not Modified     → 继续使用已缓存body
或      200 OK + new body    → 更新缓存
```

`Cache-Control: max-age=60`规定可复用寿命；`no-cache`通常意味着使用前必须验证，不等于完全禁止存储；`no-store`要求不要存储相关响应。private限制共享缓存，public允许共享缓存范围内使用，仍需符合其他规则。

![HTTP cache freshness and conditional validation](计算机网络/pictures/Chapter7/http-cache.png)

**期望时延例：**命中率$h=0.8$，本地命中5ms，未命中端到端100ms，则$E[T]=0.8\times5+0.2\times100=24$ms。若未命中100ms不包含先查缓存的5ms，则分母模型应改为$5+0.2\times100=25$ms。先明确两个时延定义，别混算。

## 11. HTTP Connection Timing：一步一步数RTT

统一假设：对象很小，传输/处理时间忽略，DNS依次访问$n$个server，$D=\sum RTT_i$，Web服务器RTT为$r$，不计TLS、关闭握手、丢包和慢启动。

### 11.1 只有一个HTML对象

DNS耗时$D$；TCP handshake耗时$r$；GET到response再耗时$r$：

$$T=D+2r$$

不是DNS+r，因为连接建立与请求响应各有一次往返。若已有可复用连接，则可能只需D+r或更少，必须按题设。

### 11.2 HTML再包含3个很小的对象

对象必须等HTML到达、解析出引用后才能请求。画时间线：

```text
DNS → TCP setup → GET HTML → discover 3 objects → fetch objects
```

| 方式 | 额外3对象时间 | 总时间 |
|---|---|---|
| Nonpersistent，逐个新建连接 | $3\times2r$ | $D+8r$ |
| Persistent，不pipeline，顺序请求 | $3r$ | $D+5r$ |
| Persistent，pipeline三请求 | $r$ | $D+3r$ |
| Nonpersistent，3条并行连接 | 一批建连$r$+一批请求$r$ | $D+4r$ |

例：DNS总40ms、$r=50$ms，则分别440、290、190、240ms。这里的pipeline假设允许连续发请求；多个大对象共享链路时还要计传输与拥塞，不能永远把并发对象传输耗时忽略。

### 11.3 有实际对象大小时

对于单对象$L$bit、有效发送率$R$，最基本追加$L/R$。多个对象串行时追加各对象发送时间之和；并行不意味着每个对象都独占整个R。DNS、TLS、TCP slow start、server processing是否计入必须由题目明确。

## 12. HTTP/1.1、HTTP/2、HTTP/3

| 特征 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 底层传输 | TCP | TCP | QUIC over UDP |
| 消息表示 | 文本式首部/消息结构 | binary frames | HTTP语义映射到QUIC streams |
| 并发 | 多连接或pipeline等 | 单连接多stream复用 | QUIC多stream |
| 首部压缩 | 无HTTP/2式压缩 | HPACK | QPACK |
| HOL主要限制 | pipeline response顺序等 | TCP丢失字节阻塞所有stream交付 | 减少跨stream传输层HOL |

HTTP/2允许不同stream的frame交错，不要求严格按request顺序完成全部response；有优先级/流量控制和历史server push设计。规范中的push能力不应被当作每个browser必定启用的功能。HTTP/3的QUIC带可靠传输与安全功能，不能因用UDP就说“网页可能任意丢字节”。

HTTP/2仍是一个TCP有序字节流，某个丢失segment后的数据在TCP层可能全部等待；QUIC使一个stream的缺口不会自动阻断其他stream交付，但同一stream内部仍有有序约束，共享拥塞也仍存在。

## 13. Worked Questions 与英文考试自测

**Q1: Can a single DNS name have multiple IP addresses?** 可以。多个A/AAAA、多接口或多服务实例均可；DNS响应可能返回地址集合，客户端再选择/尝试。

**Q2: A 4560-byte file is Base64 encoded with CRLF every 110 output bytes and at the end.** 编码6080B，56行×2B，共6192B。

**Q3: Why are Web objects preceded by MIME-style headers?** 为描述media type、encoding和其他消息元数据，让client正确解释body。不是说HTTP必须通过SMTP才能发送。

**Q4: Make an image clickable.** `<a href="/target"><img src="photo.png" alt="Photo"></a>`。

### 自测

1. 100B原文件Base64后不计换行多长？$4\lceil100/3\rceil=136$字符，末尾`==`。
2. 两次迭代DNS RTT分别20、30ms，Web RTT40ms、1小HTML：$20+30+2(40)=130$ms。
3. 浏览器收到304但没有原body，能只凭304显示完整对象吗？不能，它依赖已有缓存表示。
4. CNAME的Value是IP地址吗？不是，是另一个规范名称。
5. Cookie的Secure保证任何网站都不能读取它吗？不能，它主要限制安全通道发送，其他属性和作用域仍各有作用。
